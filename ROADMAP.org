#+TITLE: org-pwa roadmap
#+STARTUP: overview

Where org-pwa still differs from Emacs org-mode, with a suggested priority. A is next, B follows, C waits for demand. Priorities rank how often the gap meets everyday use (agenda, diary, sync, capture), not effort. This is a plan, not a promise.

* Agenda and diary
** [#C] Refile and Replace into =local:= files from the web, and from GitHub or WebDAV documents
The Android app writes into =local:= agenda files while a local file is open. In a browser, and from a document on another backend, those files stay read-only: the browser asks for permission per file, and the other adapter doesn't know them. The diary file is read for the agenda in the same way; its rows are changed by opening it.
*** Design
- Org: nothing to match; refile writes to any file Emacs can reach. The gap is only that our target adapter is the open document's.
- Today: =writeToOtherFile= (buffers.js) writes through =activeDiskAdapter()=, the open document's backend, and opens the target as an unsaved tab buffer. =local:= entries are =readOnly= unless =localAgendaFilesWritable()= (Android folder and an open =filesystem= document).
- Change: (1) route a write by the target's scheme, not the open document's: =local:= goes to a local-file adapter, =github:= and =webdav:= to theirs. (2) Key each open session by (kind, fileId), so two files of the same name on different backends cannot meet. (3) In a browser, the first Refile or Replace into a =local:= file calls =requestPermission({mode:'readwrite'})= inside the tap, and remembers the handle. (4) Keep the transaction order: write the target first, remove the source only after it succeeded; on a failed write leave the source untouched and say which file refused.
- Edge cases: permission denied or revoked (keep read-only, show why); iOS and Firefox have no File System Access, so the entry stays read-only there and the panel says so; the target changed on disk since it was read (compare modified time, offer reload); the same file open in another tab.
- Tests: refile into each of the three backends with fake adapters; denied permission leaves both files unchanged; source removed only after target write; Android assertion in smoke stays.
- Questions: should a denied permission fall back to copying the subtree to the clipboard? Is a single "Allow writing" button in Settings (per file) better than asking at the tap?
- Effort: L (adapter routing is M; permission flow and session keys are the rest). Impact: M, mostly for people with a browser-only setup.
** [#C] Row actions on the current Find match
Find on the Agenda, TODO, Match and Keyword search screens marks the current match, but keys such as =t= (change state) and =RET= (go to the heading) do not act on it, as they do on the row under point in an Emacs agenda buffer. Needs a keyboard-focused row on those screens. Effort: M. Impact: S.
** [#C] Match and Keyword search views: possible updates
Where the two views and agenda commands differ from Emacs, or stop short of it:
- Rows show the matching words marked and one matching line of text; Emacs shows the heading line only.
- The Keyword search box does not read the Search panel's =tag:=, =todo:= and =key:value= tokens; the panel does not read the Emacs grammar. They are two grammars.
- Custom commands: only =tags=, =tags-todo=, =search=, =agenda= and =alltodo=, with the setting =org-agenda-sorting-strategy=. Missing: =todo= and =stuck= commands, composite blocks, other per-command settings (=org-agenda-files=, filter presets), and Lisp functions as commands.
- =org-agenda-search-view-max-outline-level= is not read; the Search panel's =tag:= filter and Agenda tag chips do not yet count =#+FILETAGS:= tags as inherited (the Match view does).
- Effort: M. Impact: S.
** [#C] =setq= and =defun= in the sexp evaluator
Alone they add little: each diary entry is evaluated by itself, so a =defun= vanishes after it, and without loops =setq= is =let*= by another name. They matter together with the interpreter in [[#appendix-lisp][Appendix: a Lisp interpreter]], which also settles where shared definitions live.
** [#C] More calendars in the diary
=diary-coptic-date=, =diary-ethiopic-date= and =diary-mayan-date= are plain arithmetic (S). =diary-persian-date=, =diary-french-date= and =diary-chinese-date= need equinox and new-moon calculation (L). Hebrew, Islamic, Bahá'í, Julian, ISO and astronomical day numbers are done.
** [#C] Chinese holidays
=holiday-oriental-holidays= and =diary-chinese-date= need the Chinese calendar's new-moon and solar-term calculation, which the solar holidays' equinox and solstice code does not cover. Effort: L. Impact: S.

* Tables and clocking
** [#C] A field's name as a formula target, and the =%= default format parameter
Org's =_= and =^= rows name fields for use on the right of a formula; naming one on the left, and a =%= parameter for the default format, are not read yet.
** [#C] Symbolic algebra from Emacs Calc: the rest
Display (v614), intervals, chained comparisons, =simplify=, =esimplify=, =expand=, =solve= and =fsolve= are done and checked against Emacs 29.3 (about 390 cases in =test/calc-oracle-cases.mjs=). What is left:
- =solve= and =fsolve=: cubic and quartic polynomials (they stop with an error), a polynomial in an expression other than the variable (=(x+1)^2+1=5= is solved as a quadratic in x, so the written form can differ), =fsolve= of =sin=, =cos= and =tan=, complex roots in =fsolve=, a float exponent (=x^(1/3)=2= gives =8.= where Calc gives =8.0000000=, because Calc works in 12-digit decimals), =roots=.
- Other algebra: =factor=, =apart=, =collect=, =poly=, =nrat= and the calculus functions (=deriv=, =integ=, =sum=, =taylor=).
- =simplify=: the rules for =sec=, =csc=, =cot=, the hyperbolic and inverse trig functions, =%=, and angles that are whole multiples of 30 or 45 (=sin(x + 30)=).
- Intervals: =ln=, =exp=, =sin= and =max= of an interval, =[a, b .. c]= forms.
- Effort: M for the cubic and quartic solvers, S for each of the others. Impact: S.

* Export
** [#C] Slides as HTML, printable to PDF
- Why: there is no TeX in the app, so Beamer stops at a =.tex= file. An HTML slide export turns into a PDF with the browser's Print → Save as PDF, on a phone too.
- Not in Emacs: =ox-beamer= writes LaTeX only; HTML slides come from outside packages (=org-re-reveal=). So this is a separate entry, *Slides (HTML)*, in the Export menu. *Beamer* keeps meaning what Emacs's Beamer means.
- Change: a second back end over the Beamer walk in =src/export-latex.js= (the frame, section, block and column decisions are reused as they are). A frame is one page, a block a box, columns are side by side by =BEAMER_col=. =@page= sets the page size (16:9) and a page break follows each frame. Title slide, outline frame, =note= (left out of the page), =againframe=, =appendix= and =ignoreheading= follow the Beamer rules. Contents come from the HTML exporter, so links, tables, code and math look as they do in HTML export.
- Differences from Beamer to state in the README:
  - Themes: =\usetheme= names cannot be reproduced. A few names map to built-in looks and the rest use a plain one.
  - Overlays (=<+->=, =<2->=, =BEAMER_act=): a choice to make. Beamer's PDF has one page per step. Either match that (one printed page per step) or flatten (everything on one page). Matching is the larger part of the work.
  - =\setbeamertemplate=, =#+BEAMER_HEADER:= and other raw LaTeX are not used.
  - Page breaks inside a frame that is too long are the browser's, not =allowframebreaks=.
- Effort: M for the flattened version, L with a page per overlay step. Impact: S to M for those who give talks from a phone.

** [#C] ODT export: what is left after the port
=src/ox-odt.js= follows ox-odt on the files checked with Emacs 29.3 (headings, lists, tables, blocks, links, footnotes, timestamps, table of contents, captions, planning, options). What is left:
- =#+TOC: tables= and =listings= are ignored, as in Emacs. =org-odt-preferred-output-format= (docx, pdf conversion) has no counterpart: the file is always =.odt=.
- Source coloring is the app's own highlighter, for the languages it knows; Emacs colors through =htmlfontify= and the major mode, so the faces can differ.
- Impact: S.
** [#B] LaTeX export: where it differs from Emacs
Found by about 375 small probes run through Emacs 29.3 and the app and compared line by line; the wrong or lost output and the =#+OPTIONS:=, property and figure differences are fixed and kept as fixtures. What is left:
- Links: =~/= paths are not expanded to the home directory and =docview:= links are not written as Emacs writes them (both depend on the machine Emacs ran on).
- Text: the macro =(eval ..)= (it needs the Lisp interpreter). =input-file= and =modification-time= are written in LaTeX export only.
- Variables not read: =org-latex-format-headline-function= (a Lisp function, so it waits for the interpreter).
- Small: =creator:t= writes "Org Mode PWA", not Emacs's version string.
- Impact: S.

* Appendix: a Lisp interpreter
:PROPERTIES:
:CUSTOM_ID: appendix-lisp
:END:

What it would take for small standalone programs to run, in the diary and in =emacs-lisp= Babel blocks. The diary evaluator stays as it is; the interpreter is a separate module (=src/elisp.js=), so nothing in the diary can regress. Each feature is marked *Lisp* (any Lisp has it) or *Emacs* (specific to Emacs Lisp, and what makes a program read as Emacs's).

** Stage 1: the language
| Feature | Kind | Why it is needed |
|---+---+---|
| Reader: symbols, ='x=, backquote and =,=, comments, floats, strings with escapes | Lisp (backquote and =?c= characters are Emacs-flavored) | Programs are text; today's reader handles numbers, strings and parentheses only |
| Lexical environments, =lambda=, =funcall=, =apply=, closures | Lisp | Functions as values |
| =defun=, =defvar=, =defconst=, =setq= | Lisp (=defvar= and =defconst= semantics are Emacs) | Named helpers and state |
| =while=, =dolist=, =dotimes= | =while= is Lisp; =dolist= and =dotimes= are Emacs (cl-style macros) | Loops; with =defun= they replace recursion |
| =cons=, =append=, =reverse=, =mapcar=, =push=, =nreverse=, =assoc=, =assq=, =delq=, =sort= | Lisp, except =push=, =assq= and =sort='s argument order, which are Emacs | Building and searching lists |
| =concat=, =substring=, =string=, =upcase=, =downcase=, =split-string=, =mapconcat=, =string-to-number=, =number-to-string= | Emacs (strings are an Emacs-Lisp data type with these names) | Text handling |
| =null=, =listp=, =stringp=, =numberp=, =symbolp=, =functionp= | Lisp | Type tests |
| =condition-case=, =error=, =signal=, =user-error= | Emacs (Common Lisp has a different system) | Errors that can be caught and read |
| =message=, =print=, =princ=, =prin1= | Emacs | Output, captured for a Babel block |
| =max-lisp-eval-depth= limit and a step budget | Emacs (the variable); the budget is this app's | Stops runaway programs with a message |

** Stage 2: Babel
| Feature | Kind | Notes |
|---+---+---|
| =emacs-lisp= source blocks run, result is the last value | Emacs | Printed with =prin1= rules, as Emacs prints it |
| =:var name=value= bound as variables | Org | Same as the =js= blocks |
| =:results=, =:wrap=, =:cache=, =:noweb= | Org | Shared with the =js= runner |
| Runs when =(emacs-lisp . t)= is in =org-babel-load-languages= | Org | That is already the default, so a stricter switch may be wanted |
| Worker sandbox, timeout, no I/O | App | Same sandbox as =js= blocks |

** Stage 3: settings that call a function
Each of these is complete in the app except for the function it calls, and needs stage 1 plus the shared definitions below.
| Setting | What it needs | Today |
|---+---+---|
| =user-defined-up= and =-down= in =org-agenda-sorting-strategy= | =org-agenda-cmp-user-defined=, a function of two agenda lines that returns =-1=, =1= or =nil= | The keys are read and have no opinion, as in Emacs when the function is =nil= |
| =%(function)= in =org-agenda-prefix-format= | A function called for each agenda line, its result put in the prefix | The other =%= forms work; this one adds nothing |
| =org-priority-get-priority-function= | A function of no arguments that returns a heading's priority number | The priority comes from the cookie and the default |
| A =holiday-sexp= expression beyond the subset in the table above | The full evaluator, with =date= bound | The app's own Lisp subset |

** Later: Emacs and Org specific
These need Emacs's own libraries and are not part of "small standalone programs":
- Buffer and Org functions: =org-map-entries=, =org-element-parse-buffer=, =org-entry-get=, =org-todo=.
- =format-time-string=, =decode-time=, =encode-time= and other time functions.
- =cl-lib= (=cl-loop=, =cl-defun=), =seq-*= and =string-*= libraries.
- Regular expressions the Emacs way (=string-match=, =re-search-forward=, match data).
- Files and network (=insert-file-contents=, =url-retrieve=): left out on purpose.

** Shared definitions for the diary
A section in Extensions for Lisp that runs once per session and defines functions that diary entries can call. This is what makes =defun= worth having in the diary.

** Order of work
1. The interpreter core (stage 1), as its own module, with tests against Emacs 29.3.
2. Move the diary evaluator (=src/sexp-eval.js=) onto it. The diary layer keeps the =date= binding, the diary and calendar functions as native builtins, and a tolerant mode in which a failing entry shows nothing, as today. The Emacs-checked sexp tests and the existing suite must pass unchanged. This replaces the hard-coded list of line forms with one reader, and gives diary entries real errors, =defun=, =setq= and loops.
3. The =calendar-*=, =holiday-fixed=, =holiday-float= and =holiday-easter-etc= functions as builtins, under Emacs's names.
4. =emacs-lisp= source blocks in Babel (stage 2).
5. Shared definitions for the diary.
6. The settings that call a function (stage 3).

What stays in JavaScript: the calendar grid and its layout (UI, redrawn often), and the agenda's per-day effort total and =+N?= count (computed while drawing, with no Org equivalent). A hook the interpreter can call may be added to the latter later.

Emacs's own =calendar.el=, =holidays.el= and =solar.el= are not run: they need macros, =cl-lib=, =defcustom=, =require= and buffer functions. The library is written for this interpreter, under Emacs's function names.
