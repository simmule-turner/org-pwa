* Testing

org-pwa's engine code (~src/~) and browser-specific adapters (~src-browser/~) are unit tested with Node's built-in test runner, zero external dependencies:

#+BEGIN_SRC
node --test
#+END_SRC

This file is the detailed record of what that coverage actually includes — every real bug it caught along the way, not just a pass/fail count. See [[../README.org][README.org]] for what the app itself actually does; this file is purely about how it's verified.

** Footnotes and iCalendar export

Footnote support (~[fn:label]~ references, ~[fn:label:definition]~/~[fn::anonymous]~ inline definitions, and the separate-definition-line convention) is covered end to end: the inline parser (correct bracket-depth tracking so a definition containing its own ~[[link]]~ finds the right closing bracket rather than stopping at the link's own), the body parser's definition-line detection, ~findFootnoteDefinition~'s search across paragraphs/list items at any nesting depth/table cells (a real bug this coverage caught: nested list items are structured as nested list *nodes*, not a flat array, and the first version of this search didn't account for that), tap-to-jump navigation through the real app (a real bug this coverage caught: jumping to a definition only correctly re-expanded a *collapsed ancestor* of the target heading, not the target heading itself when the definition lived directly in its own body — ~navigateToHeading~'s ~revealOwnBody~ flag exists for exactly this and simply hadn't been passed), and export to both Markdown (GFM's own ~[^label]~/~[^label]: text~ syntax, including anonymous-footnote synthetic labeling and same-label deduplication) and HTML (jump-linked superscripts with a back-linked Footnotes section, including HTML-escaping verified specifically).

The iCalendar (.ics) exporter is covered for RFC 5545 conformance (line folding at 75 octets, CRLF endings, text escaping, UTC ~DTSTAMP~ vs. floating-time ~DTSTART~), correct ~RRULE~ generation from org repeaters (including that all three repeater marks produce identical output, matching this app's own agenda semantics), ~VALARM~ generation from a DEADLINE's delay/warning-period suffix, ~org-contacts-anniversaries~ becoming yearly-recurring events, and the same exclusion rules as the Agenda view (archived/commented/completed). Two real bugs this coverage caught: a UID-collision case where two headings sharing a title produced identical calendar-item IDs (fixed by folding the item's own date into the UID basis, chosen specifically to stay stable across re-exports rather than a position-based counter that would shift if an unrelated heading were inserted elsewhere in the file), and — found only through actual end-to-end UI testing, not the engine in isolation — the "this file + Agenda Files" export option silently producing an incomplete calendar if the user hadn't visited the Agenda view earlier in the session, since nothing had triggered the other files' fetches yet; fixed by making the export explicitly wait for every configured file to finish loading rather than exporting whatever happened to already be cached.
