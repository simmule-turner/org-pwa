* Testing

org-pwa's engine code (~src/~) and browser-specific adapters (~src-browser/~) are unit tested with Node's built-in test runner, zero external dependencies:

#+BEGIN_SRC
node --test

This file is the detailed record of what that coverage actually includes — every real bug it caught along the way, not just a pass/fail count. See [[../README.org][README.org]] for what the app itself actually does; this file is purely about how it's verified.

** god-mode chords for file/refile/attach/clocking/export, the C-f/C-/ redo technique, and a real Escape-to-close gap found along the way

Every new chord (~C-x C-s~, ~C-x C-w~, ~C-x C-f~, ~C-c C-w~, ~C-c C-a~, the four ~C-c C-x C-*~ clocking chords, ~C-c C-e~) was checked against the real Emacs manual or source before writing any code, not assumed from memory -- ~org-refile~'s and ~org-attach~'s own bindings confirmed directly against orgmode.org's own manual pages. Each sequence was then verified empirically against the actual translator (~src/god-mode.js~'s ~processKey~), which caught a real mistake in the plan before it reached any code: the intuitive-looking "space the letters out with SPC" (e.g. ~x SPC s~ for ~C-x C-s~) is wrong -- SPC toggles *literal* mode, un-Controlling the key that follows it, the opposite of what two Controlled letters in a row need. The correct sequence is simply the two letters typed plainly (~x s~), since the translator's own default rule already Controls every plain letter regardless of chain state.

The redo mechanism (~C-f~ arms the next ~C-/~ to redo instead of undo, matching real Emacs's own actual undo-of-undo-via-broken-chain technique) is genuinely new logic, not a lookup-table entry, so it got the most scrutiny: a browser check makes two edits, then walks undo, undo, ~C-f~ then ~C-/~ (redo #1), ~C-/~ again with no further ~C-f~ (redo #2, confirming the arming persists across repeated presses, not just one), then ~C-/~ a third time with nothing left to redo (confirming the fall-back to plain undo). All four steps are asserted against the actual document text, not just a status message.

Finding this out cost more debugging than the feature itself, and every dead end turned out to be a wrong assertion, not a wrong app: checking a row-level ~.priority-badge~ for a running clock that's actually shown in the modeline; checking ~#status~ for a clock-out/cancel confirmation that ~commitAndRender~ never actually writes there, while god-mode's own status indicator re-asserts itself on literally every dispatch (so *any* status-text check after a god-mode action needs to account for this, not just this one); and a test helper that pressed ~Escape~ unconditionally at the start of every chord, which works fine for the first chord in a test but *exits* an already-active god-mode on the second one, since god-mode deliberately stays engaged across dispatches rather than being a one-shot mode -- each dead end was chased with real instrumentation (a targeted ~console.log~ at the exact suspected point, forwarded via ~page.on('console', ...)~, removed again once resolved) rather than more guessing.

One genuine app bug did turn up, independent of any of the above: ~openTextFieldPopup~ and ~openButtonChoiceModal~ had no ~Escape~-to-close handling at all, and weren't tracked by ~anyOverlayPanelOpen()~ either -- unlike ~confirmDialog~, which already handles this correctly with its own dedicated flag and capture-phase keydown listener. Found because a smoke check's ~Escape~ press, meant to close the Attach modal and move on, silently did nothing -- the modal just sat open, absorbing every subsequent keystroke the test sent it. Both now follow ~confirmDialog~'s own established pattern exactly (a new ~S.textFieldPopupOpen~ / ~S.buttonChoiceModalOpen~ flag each, checked at the very top of the global keydown handler). This is a real, user-facing fix independent of the test that found it: those two dialogs were silently un-closeable via ~Escape~ before, on any device with a keyboard.

** Retiring the More menu's Capture/Clocking/History steps, the View menu's read-only toggle, and the toolbar's ⊕/❓/🔍 buttons, now that the command palette covers all of it

This round removed UI that the command palette had already made redundant, and fixed a real bug found along the way. None of it is unit-testable (all browser wiring): the two genuinely new checks (the add-heading fix, the god-mode Help/Search bindings) went through this project's usual discipline of confirming a check actually *fails* against a reverted copy of the code before trusting it; five other, pre-existing checks were updated to go through the palette instead of a since-removed menu step or button and re-verified to pass, keeping whatever coverage they already had.

*A real, shipped bug*: "Add heading after" (~M-RET~) silently did nothing on an empty document or when invoked from the palette with no heading selected, because it required ~keyboardFocusedHeading~ unconditionally and the palette's own ~needs: HEAD~ dimmed the command entirely rather than letting it run. Fixed with a shared ~insertHeadingSmart~ helper: a focused heading gets a sibling right after it (unchanged, the common case); a genuinely empty document (no headings at all) gets one at the top, matching what real ~M-RET~ does at position 1 of an empty buffer; a document that already has headings but nothing selected gets one appended at the bottom rather than silently doing nothing. One check covers all four cases, including the ordinary sibling-insertion case explicitly, so the refactor couldn't have quietly broken the most common path while fixing the edge ones. Only once this was verified did the ⊕ toolbar button (a separate, inferior implementation of the same idea, always inserting at the bottom regardless of selection) get removed.

*The ~C-s~ investigation*, worth recording for the debugging path more than the bug, because there wasn't one: adding a god-mode binding for search (~s~ → ~C-s~ → ~searchBtn.click()~) appeared broken -- the check waited on ~#searchPanel~ becoming visible and timed out, with the minibuffer showing a lone "⋯" that looked exactly like a stuck god-mode prefix state. Four rounds of instrumentation (a console.log at the god-mode dispatch site, inside ~searchBtn~'s own click handler, inside ~renderSearchPanel~, inside ~renderMinibuffer~) traced ~S.searchOpen~ staying correctly ~true~ throughout, which didn't fit a "search never opened" theory at all -- the trace was the thing that turned the investigation around. It turned out ~renderSearchPanel~'s normal path never sets ~searchPanel.style.display~ (only its query-replace sibling does; the actual live search UI is ~#minibufferSearch~), and the "⋯" was ~#search-options-btn~'s own real, working label (U+22EF, deliberately distinct from the More button's vertical U+22EE, per its own code comment) -- meaning search had been opening correctly the entire time and the check was asserting against the wrong element. Fixed the assertion, not the app; removed all the debug logging afterward and reran everything clean.

*The More menu's Capture and Clocking steps* (~S.moreMenuStep === 'capture'~ / ~'clocks'~, their own sub-panels rendered in place within the More popup) turned out to be a completely separate, parallel mechanism from what the palette's own Capture/Clocking commands already used (~S.captureOpen~ for Capture; direct function calls -- ~clockInHeading~ and so on -- for Clocking, with no shared state at all). Removing the two menu buttons made ~renderCaptureFlow~ and ~renderClockOptionsFlow~ fully orphaned (each had exactly one caller, the branch just removed), so both were deleted outright along with every import that became unused as a result, rather than left as dead code nothing could ever reach again. History's removal was simpler -- the palette's own History command already used the same direct mechanism (~S.historyOpen~) the menu button did, so nothing was orphaned by removing just the button.

*Scope surfaced mid-task, resolved by asking rather than assuming*: removing the Clocking sub-panel exposed that ~src/menu-alias.js~ treats ~clocking~ as one of five documented, first-class menu categories with its own alias namespace, README table row, and worked examples -- a considerably bigger piece of surface area than "remove a menu button." Flagged to the person rather than silently cutting it or silently leaving it; the answer was to keep clocking actions in the palette (already true, untouched) while removing every other reference to the retired menu completely, including the "here's what changed and why" narration a first pass had written into the docs -- the person's own correction was specifically that this kind of change-narration doesn't belong in reference documentation, only the current, accurate state does.

The README pass this forced was larger than the code change itself: the menu-customization section's own five-menu, ~clocking:~-namespace documentation, two full worked examples, and its labels table all needed rewriting for four menus instead of five; separate stale references turned up in the Clocking feature section proper, the Capture Templates section, the History paragraph, the Effort_ALL paragraph, the command palette's own "what it acts on" paragraph, the Keybindings table and its surrounding prose (~C-h i~ → ~C-h m~, matching real Emacs's actual ~describe-mode~ binding and manual wording, verified by fetching the real Emacs manual text rather than assumed), and the toolbar-button paragraphs for Help and Search, none of which had been caught by grepping for the obvious "More →" phrasing alone -- found only by a second, broader sweep for the icons and button IDs themselves. Every rewritten line was re-checked against the inline-markup parser for balanced tilde markers, and the whole file's parse-then-serialize round-trip was confirmed identical before and after.

** Sync conflicts, the precache list, and the browser smoke test

~merge3.test.js~ covers the three-way merge. The Myers diff is checked two ways on hundreds of small random inputs: applying its hunks must reproduce the target, and the edit must be /minimal/ — its removed and added line counts must equal what a brute-force longest-common-subsequence says they should be. Merge behavior is covered case by case (edits in different places, identical edits, the same line changed two ways, adjacent edits counting as a conflict, insertions at the same spot, a deletion against an edit inside it, trailing newlines and CRLF preserved exactly) and by property tests (widely separated edits always merge cleanly into both sets; merging against a base equal to one side always yields the other). The tests were themselves mutation-checked: deliberately breaking the clustering rule, the Myers backtrack, or the identical-change rule makes them fail, so they aren't passing vacuously. A 20,000-line file with an edit at each end merges in well under a second, and versions too different to diff give up cleanly rather than hanging. ~sync-engine.test.js~ and ~document-store.test.js~ cover recording the common ancestor, the ~{ merged }~ and ~'cancel'~ resolutions, and that a cancelled Save leaves the disk, the pending edit, and the sync metadata untouched.

~sw-precache.test.js~ exists because of a real bug that was found by accident: five modules the app imports (~history-store~, ~query-replace~, ~emacs-regex~, ~export-org~, ~org-plot~) were never in the service worker's precache list, and its fetch handler doesn't cache at runtime, so a cold start with no network failed to load the app at all. Nothing in the unit suite could see it, since ~app.js~ isn't importable. The test crawls the app's real import graph and fails if any module is missing from the list. Reproducing the bug properly took care: Playwright's offline switch doesn't reach the service worker (a control fetch for a file that was certainly not cached still succeeded), so the first "offline" run passed for the wrong reason — the check has to actually stop the server.

~tools/smoke.mjs~ drives the real app in headless Chromium against a built-in static server and an in-memory WebDAV server (see [[../README.org][README.org]]'s Development section for how to run it). It covers the flows that have really broken: a cold start with no network, the read-only toggle across Text and Org views, effort estimates, refile targets, and the sync-conflict path end to end — automatic merge, the region-by-region resolver, Cancel, and the banner's Merge — plus narrowing surviving a reload. It was mutation-checked too: putting three earlier bugs back into a copy of the app (a module missing from the precache list, the Text-view read-only flag never syncing, Save never merging) makes exactly the corresponding checks fail.

KILL(k@)~) reproduced as literal test cases, not just described: WAIT to DONE correctly producing no redundant second entry since DONE already logs on its own entry, and WAIT to TODO correctly firing the leaving-log since TODO has no logging of its own -- verified twice, once at the pure decision-engine level and again end to end through the real app (a heading actually cycled through WAIT and DONE via the real TODO badge, confirming the LOGBOOK drawer ends up with exactly the entries real org itself would produce, note text and all). ~src/logbook.js~'s own parser is covered separately -- every real shape org's own default log-note format actually produces (state changes with and without a "from" clause, multi-line note continuations via the trailing-backslash convention, CLOCK lines recognized structurally though not acted on), plus round-trip safety specifically: an unrecognized LOGBOOK line a future version of this parser doesn't understand yet is still preserved verbatim, never dropped.

Two real, general parser bugs this work found while writing README.org's own documentation for the feature, independent of progress logging itself: a blank line between a list item and its nested sub-list (an extremely common, legitimate org style this app's own README uses throughout) was causing the sub-list to be parsed as a separate, un-nested sibling instead of a real child -- confirmed to affect the main outline's own rendering identically to the read-only Docs view, not a Docs-specific bug, and fixed with its own dedicated test coverage including three-level-deep nesting and the exact mixed ordered/unordered case that surfaced it. And a "::" character appearing inside a ~code~ or =verbatim= span (e.g. a list item whose own prose demonstrates description-list syntax, "(~term :: description~)") was being matched as if it were that item's own real tag separator, corrupting the item -- fixed with proper span-boundary awareness rather than a one-off workaround, verified a legitimate tag separator appearing AFTER such a literal-span example is still correctly found.

Real org's own border-character rules for inline markup (documented in this app's own README.org, under "Inline text markup") were also verified systematically against the actual README.org content itself, not just unit-tested in the abstract: a full-file automated scan checked every single ~...~ span's opening and closing characters against the documented valid-border sets, catching 34 separate occurrences of adjacent code spans concatenated with a bare "/" (invalid on both sides of the border) plus several more one-off violations (a trailing space before a closing tilde, an opening tilde immediately preceded by "/"), cross-checked against the actual rendered Docs-view output down to a final count of exactly the intentional literal-tilde cases (verbatim-wrapped syntax demonstrations, and real home-directory-shorthand paths in file: link examples) with zero unintended ones remaining.

** Progress logging (Layer 1) and the #+TODO: parenthetical-syntax fix

A real, general parsing bug this work found and fixed: ~#+TODO:~ lines using fast-access keys or logging specs (e.g. "TODO(t) WAIT(w@/!) | DONE(d!) KILL(k@)", or even just plain "TODO(t) | DONE(d)" with no logging at all) were never having the parenthetical suffix stripped before matching against a heading's own TODO keyword -- meaning any heading using such a keyword was silently invisible to TODO-state recognition everywhere in the app (no badge, absent from the TODO view and Agenda), for what is extremely common real-world ~#+TODO:~ syntax. Fixed with a new shared ~parseTodoSpecValue~ in org-parser.js, used by both the parser's own heading matching and todo-cycle.js's sequence resolution (previously two independent, and previously-already-once-buggy-for-this-exact-reason, implementations) -- covering every parenthetical combination, multi-line ~#+TODO:~ merging of the new key/logging metadata, and round-trip safety (the ~#+TODO:~ line itself is preserved completely verbatim regardless of how it's parsed for matching).

~org-log-done~ (~#+STARTUP: logdone~ / ~lognotedone~) is covered by an 18-case state-transition matrix in progress-logging.test.js -- exactly the kind of decision logic that's easy to get subtly wrong: entering DONE with each setting, already-done-to-different-done-keyword correctly NOT re-triggering, leaving DONE unconditionally removing a stale CLOSED timestamp regardless of the CURRENT logging setting (cleaning up after an earlier session), and ~org-closed-keep-when-no-todo~'s carve-out applying only to the "cycled to no keyword at all" case specifically, never to cycling toward a different TODO keyword. The full app.js wiring (all three real TODO-transition call sites -- keyboard shortcut, tap-to-cycle badge, action-menu toggle -- confirmed to be the only mutation paths in the app before rewiring them) was additionally verified end to end through the real app: ~'time~ mode inserting and later removing a CLOSED timestamp, ~'note~ mode showing the prompt immediately without blocking the TODO badge's own instant state change, Save correctly filing the note under a timestamped Closing Note child heading, and Skip correctly declining to add one without reverting the state change that already happened.

** Footnotes and iCalendar export

Footnote support (~[fn:label]~ references, ~[fn:label:definition]~ / ~[fn::anonymous]~ inline definitions, and the separate-definition-line convention) is covered end to end: the inline parser (correct bracket-depth tracking so a definition containing its own ~[[link]]~ finds the right closing bracket rather than stopping at the link's own), the body parser's definition-line detection, ~findFootnoteDefinition~'s search across paragraphs/list items at any nesting depth/table cells (a real bug this coverage caught: nested list items are structured as nested list *nodes*, not a flat array, and the first version of this search didn't account for that), tap-to-jump navigation through the real app (a real bug this coverage caught: jumping to a definition only correctly re-expanded a *collapsed ancestor* of the target heading, not the target heading itself when the definition lived directly in its own body — ~navigateToHeading~'s ~revealOwnBody~ flag exists for exactly this and simply hadn't been passed), and export to both Markdown (GFM's own ~[^label]~ / ~[^label]: text~ syntax, including anonymous-footnote synthetic labeling and same-label deduplication) and HTML (jump-linked superscripts with a back-linked Footnotes section, including HTML-escaping verified specifically).

The iCalendar (.ics) exporter is covered for RFC 5545 conformance (line folding at 75 octets, CRLF endings, text escaping, UTC ~DTSTAMP~ vs. floating-time ~DTSTART~), correct ~RRULE~ generation from org repeaters (including that all three repeater marks produce identical output, matching this app's own agenda semantics), ~VALARM~ generation from a DEADLINE's delay/warning-period suffix, ~org-contacts-anniversaries~ becoming yearly-recurring events, and the same exclusion rules as the Agenda view (archived/commented/completed). Two real bugs this coverage caught: a UID-collision case where two headings sharing a title produced identical calendar-item IDs (fixed by folding the item's own date into the UID basis, chosen specifically to stay stable across re-exports rather than a position-based counter that would shift if an unrelated heading were inserted elsewhere in the file), and — found only through actual end-to-end UI testing, not the engine in isolation — the "this file + Agenda Files" export option silently producing an incomplete calendar if the user hadn't visited the Agenda view earlier in the session, since nothing had triggered the other files' fetches yet; fixed by making the export explicitly wait for every configured file to finish loading rather than exporting whatever happened to already be cached.

The god-mode key-translation engine (~src/god-mode.js~) is covered for every row of its own reference table across all six sections, plus the underlying rule mechanics in isolation (the "c c" chain, punctuation-vs-letter handling within it, ~g~ clearing the chain, state threading between keystrokes). Two real bugs this coverage caught before the feature ever shipped: bare named keys (arrows, Tab, RET, Space) defaulting to Control the same way letters do, which would have made ordinary cursor movement impossible while god-mode was active — caught by direct comparison against the reference table's own "Shift date" and "Tab" rows, where the god-mode sequence is identical to the standard binding; and Emacs's own unbracketed ~RET~/~TAB~/~SPC~ notation being wrongly bracketed as ~<RET>~ etc.

Export's ~#+TITLE~/~#+AUTHOR~/~#+DATE~/~#+OPTIONS:~ support (~src/export-options.js~, wired into all four formats) and ~#+INCLUDE~ (~src/export-include.js~) are both covered with every semantic verified directly against real Emacs org-mode's own actual export output before being trusted, not assumed from the Org manual's own wording — which for ~:lines~ specifically is genuinely misleading (its own phrasing for "lines 5-10" reads as inclusive on both ends; real org's actual behavior is inclusive-start, exclusive-end). A real, pre-existing bug this work found and fixed: the ASCII exporter's own ~toc:~ and ~num:~ were wrongly coupled into one combined toggle, when real org treats them as fully independent (a depth-limited Table of Contents listing still coexists with full section numbering throughout the body). Two further bugs caught during this same work: an infinite-recursion crash in the Markdown Table-of-Contents builder (a wrapper function recursing into itself with the same "top-level" signal instead of progressing, caught immediately via 10 cascading test failures), and a malformed section number (~.1.~ instead of ~1.1.~) produced when a ~#+INCLUDE~ ~:minlevel~ shift left an intermediate heading level unset — a sparse-array gap silently joining as an empty string, fixed across all three numbering implementations (ASCII/HTML/ODT).

The Settings UI's popup-based field editor (a shared ~openTextFieldPopup~ used for every longer Quick Settings field, Global Variables, and Capture Templates) surfaced a real, quietly-serious gap while being built: the new field type's own save path never applied ~normalizeSmartQuotes~ at all, meaning a smart-quote auto-substitution (routine on iOS) typed into an ~org-xx-extra-menu~ or ~org-xx-menu-aliases~ entry — both genuinely quote-delimited syntax — would silently fail to parse, exactly the failure mode ~text-normalize.js~'s own docs describe as a confirmed, serious bug elsewhere in the app. Fixed by applying it at both of the new popup's own save paths.
