* org-pwa
:PROPERTIES:
:CUSTOM_ID: org-pwa
:END:

A single-file, offline-capable, mobile-first outliner for editing ~.org~ files in the browser. No server, no account required to use it locally — just a static site you can install as a PWA and point at a file.

This document describes what org-pwa actually does today, how to use it, and — since that's usually the more useful question for anyone coming from Emacs — *where it deliberately or incidentally diverges from real org-mode.*

** What org-pwa is (and isn't)
:PROPERTIES:
:CUSTOM_ID: what-org-pwa-is-and-isnt
:END:

org-pwa is a *touch-first outline editor*, not a port of Emacs. It reads and writes real ~.org~ files — round-trip fidelity is a hard requirement, so content it doesn't specifically understand is preserved verbatim rather than mangled or dropped. But the /editing model/ is built from scratch around tapping and gestures, not Emacs keybindings, and it deliberately implements a useful subset of org-mode rather than all of it.

If you're looking for org-mode-in-the-browser with full parity — babel, capture templates, the agenda, LaTeX export — this isn't that (yet, and possibly not ever; see [[#known-limitations--not-built-yet][Known limitations]]). If you want to open a real org file on your phone, reorganize your outline, check off tasks, edit tables, and get it saved back to disk, GitHub, or a WebDAV server, that's what this is for.

** Getting started
:PROPERTIES:
:CUSTOM_ID: getting-started
:END:

1. Open the app. If no file is open, tap *File → Open*.
2. Choose where to open from:

   - *Local file* — uses the browser's native file picker and keeps a live handle, so Save writes straight back to the same file. Requires a browser with File System Access support (Chrome/Edge on desktop and Android).
   - *GitHub* — browse folders and ~.org~ files in a repo you've configured in Settings, tap one to open it. A "Type a path instead…" option is always available too, for a path that doesn't show up in the listing (e.g. permissions on a specific subfolder) or if listing fails outright.
   - *WebDAV* — same idea, browsing a WebDAV server you've configured in Settings via the standard ~PROPFIND~ directory-listing method. Same "Type a path instead…" fallback available here too.
   - *Import file* (shown instead of "Local file" on platforms without File System Access, i.e. everything on iOS) — picks a file once and reads it; there's no live link back to the original, so Save downloads a new copy you place back manually. See [[#platform-support][Platform support]].

1. Edit. Every edit is applied instantly to an in-memory copy and cached locally in the background — nothing is lost if you close the tab, even before you hit Save.
2. Tap *Save* when you want it written back to wherever it came from. *Save As* lets you choose a different destination or backend.

The header shows the current filename and which backend it came from, turning *red* whenever there are edits that haven't been saved yet (normal color otherwise).

** Editing your outline
:PROPERTIES:
:CUSTOM_ID: editing-your-outline
:END:

- *Headings*: tap the title text to reveal a row of twelve actions — edit title, edit the heading's own body text, edit details (the general editor, including TODO state — see below), add a sub-heading, move up/down, clock in/out (see [[#clocking][Clocking]]), archive, attach (see [[#attachments][Attachments]]), delete, promote/demote. Nothing is shown until you tap; this keeps the row itself uncluttered. Most actions close the row back up after running; Move up/down and Promote/Demote deliberately don't, since repeating one of those a few times in a row is a normal thing to want to do — tap elsewhere on the row (or in the empty space after the buttons themselves) to close it manually when you're done. *Delete* always confirms before anything's actually removed, listing what would be lost (scheduled/deadline dates, tags, properties, a state-change history) when there's something to lose.
- *TODO state*: tap the TODO badge to cycle through the sequence defined by ~#+TODO:~ (or ~TODO~ / ~DONE~ by default).
- *Fold/unfold*: tap the chevron to toggle a heading's whole subtree, or swipe left on a heading to cycle through collapsed → children-only → fully expanded → collapsed.
- *Archive* (becomes *Unarchive* once a heading is already archived, a different icon for each): moves the whole subtree to its configured ~org-archive-location~, or back to its original location — real org's ~org-archive-subtree~, not just a tag added in place. Always confirms first, naming the actual destination. See [[#archiving][Archiving]] for the full behavior, the ~org-archive-location~ syntax, the transaction-safety guarantee, and the platform limitation for local files. The ~:ARCHIVE:~ tag and every ~ARCHIVE_*~ property (~ARCHIVE_TIME~ / ~ARCHIVE_FILE~ / ~ARCHIVE_OLPATH~ / ~ARCHIVE_CATEGORY~ / ~ARCHIVE_TODO~ / ~ARCHIVE_ITAGS~) are all still just an ordinary tag and ordinary properties once the move lands — editable or removable by hand from the general editor like any other, if you ever need to.
- *The general editor* (📋 *Edit details*): one structured form covering everything that used to be spread across several separate actions:
  - *TODO state* — a row of buttons for every keyword in the file's own ~#+TODO:~ workflow (both the TODO-type and DONE-type states together, plus *None* for clearing it entirely), the currently-set one highlighted. A file with more than one parallel workflow shows one row per sequence. Saving applies whatever CLOSED-timestamp/logbook logging the transition calls for, exactly the same as the quicker single-tap cycle (~C-c C-t~, still available — see the keyboard shortcuts table) already does.
  - *SCHEDULED / DEADLINE / plain timestamp* — real date and time pickers, a repeat selector (mark + amount + unit: every N hours/days/weeks/months/years), and an optional "warn ahead by" delay (real org syntax, e.g. ~-3d~, for seeing a deadline coming a few days early instead of only on the day it's due). These three are independent instances of the same field group — set any combination; each has its own *Clear* button for explicitly removing that one timestamp, separate from the form's overall Save/Cancel. See [[#agenda][Agenda]] for how a plain timestamp differs from SCHEDULED/DEADLINE (it doesn't carry forward, and lives in the title rather than a planning line).
  - *Tags* — existing tags shown as removable chips (tap a chip to remove it), plus an input and Add button for a new one. Not a raw space-separated prompt.
  - *Priority* — a row of buttons (A / B / C / None), the currently-set one highlighted. Covers real org's own conventional default range directly with one tap; anything outside A–C isn't reachable from this UI, a stated scope limit rather than a full A–Z picker for a rarely-used case.
  - *Properties* — each existing property as its own editable key/value row, with a per-row remove button and an "Add property" row to append a new, initially-blank one. A row left with a blank key is silently dropped on save. This is also how you set a ~CUSTOM_ID~ for ~[[#id]]~-style linking (see [[#links-and-images][Links and images]]).

  All fields across all five sections are committed together on *Save*, or discarded together on *Cancel* — nothing is written until you actually save. Two immediate, standalone action buttons sit above Save/Cancel, sharing one row: *▦ Add table* inserts a table into the heading's body right away, closing the editor; *🗑️ Delete table* removes the heading's own table (its most recently added one, if it has more than one — matching Add table's own "append at the end" convention symmetrically) after a confirmation prompt, since this can't be undone. Delete table is disabled — nothing to confirm or act on — when the heading has no table at all. Neither commits alongside the five field sections above, since neither interacts with TODO state/scheduling/tags/priority/properties at all. When not editing, existing properties still show as a small read-only line under the heading, but only when drawers are actually visible for that heading (~#+STARTUP: showeverything~, or manually cycled to "fully expanded" — see [[#folding-and-startup][Folding and #+STARTUP]]); tapping it opens the same general editor as tapping the title. Collapsing the heading again correctly hides them too, whether via swipe or chevron.

- *Block content* (~#+BEGIN_SRC~ / ~#+BEGIN_QUOTE~ / ~#+BEGIN_EXAMPLE~ /etc.): shown read-only, gated by the same drawer-visibility rule as properties above. When folded, an honest "collapsed block" label is shown rather than nothing — tap it to reveal the actual content; tap the label again once expanded to re-fold it. No in-app editing of block content yet — this is visibility only. Recognition itself is fully generic — *any* ~#+BEGIN_NAME~ / ~#+END_NAME~ pair round-trips correctly and gets this same tap-to-reveal treatment, not a fixed list of specific names. Three names get real, distinct display treatment though, matching real org's own actual behavior — content isn't just shown literally for every block name the same way:

  - ~QUOTE~ — inline markup (bold, italic, links, everything) is interpreted, not shown literally, since a quote is meant to hold normal prose. Indented on *both* the left and right margins with a left border, a conventional blockquote treatment — this is a real, distinct visual difference from every other block type, not just a label change.
  - ~VERSE~ — inline markup interpreted, same as ~QUOTE~, but every source line stays its own visual line exactly, never reflowing into or merging with an adjacent line the way ordinary paragraph text (or ~QUOTE~ itself) does — real org's own defining characteristic of a verse block.
  - ~CENTER~ — inline markup interpreted, its own paragraphs centered.

  Everything else — ~SRC~, ~EXAMPLE~, ~COMMENT~, or any other/custom name — stays literal and verbatim, shown byte-for-byte with no markup interpretation at all, exactly as before.

  On export (see [[#export][Export]]), a further, separate three-way distinction applies: ~SRC~ becomes a real fenced code block with its language parameter preserved (~#+BEGIN_SRC python~ → ```python), ~QUOTE~ becomes a blockquote, and ~COMMENT~ is dropped from the output entirely, matching real org's own export behavior exactly. Every other name — ~EXAMPLE~, ~CENTER~, ~VERSE~, or anything custom — exports as a plain, language-less fenced/preformatted block, its content otherwise untouched (export doesn't currently mirror ~VERSE~'s own line-preserving or ~CENTER~'s own centering treatment — a stated, current gap). A ~SRC~ block's language parameter (and any other text after the block name) is parsed and preserved for round-trip either way, but isn't used for anything beyond that export-time language hint — no in-app syntax highlighting, and no Babel-style execution of any kind (see [[#known-limitations--not-built-yet][Known limitations]]).
- *Moving headings* (↑ / ↓ / ← / → in the action row): ↑ and ↓ reorder a heading among its own siblings without touching its level or its subtree — everything nested under it moves as one unit automatically. ← (promote/outdent) moves a heading up one level, making it a sibling of its former parent, inserted right after it. → (demote/indent) moves it down one level, making it the last child of whichever heading immediately precedes it. All four are no-ops at a natural boundary (already first/last, already top-level, no preceding sibling to demote under) — tapping one there shows a brief status message rather than silently doing nothing or corrupting the outline. This is the actual replacement for switching to Text view and cutting/pasting raw lines, which used to be the only way to reorder anything.

*** A heading's "text"
:PROPERTIES:
:CUSTOM_ID: a-headings-text
:END:

Org has no separate description field — anything following a heading (until the next heading) belongs to it, and that can include multiple paragraphs, lists, and tables in any order. The *Edit text* action opens all of that heading's content as one editable block of raw org syntax, not just the first paragraph. Typing ~- [ ]~ at the start of a line turns it into a checklist item on save, exactly as it would in the underlying file.

** Undo/redo and History
:PROPERTIES:
:CUSTOM_ID: undoredo-and-history
:END:

Every edit in this app — heading/paragraph/list-item/table-cell text, TODO/priority/tags/properties, moving, promoting, archiving, capturing, all of it — can be undone and redone. *More (⋮) → History* opens a panel with three things: quick *‹ Undo* / *Redo ›* buttons for stepping one change at a time, a scrollable list of every step taken since the file was opened (oldest to newest, with the current position marked), and a *diff* toggle on each entry showing exactly what that one step changed — added lines and removed lines, color-coded, diffed against the step right before it.

The list isn't just for stepping through one at a time — tap *any* entry to jump straight there, forward or back, skipping however many steps are in between. Entries past your current position (available to redo) show dimmer than the ones already applied. Making a genuinely new edit from a point you'd undone to discards whatever was ahead of it, the same way undo/redo works in virtually every editor — but simply /browsing/ the history list, including jumping backward and then forward again, never discards anything.

Each step is a full snapshot of the document's text at that point. One step per /completed/ edit action (finishing typing in a title and tapping away, toggling a checkbox, archiving a heading), not per keystroke — matching how this app already treats a "finished edit" everywhere else (a title commits on blur, not per character). An edit that turns out not to have changed anything at all (toggling something and toggling it back) doesn't get its own step.

History is kept for as long as the current file stays open — unlimited steps, no cap — and is *not* persisted or carried over if you close the file and reopen it later. Undoing or redoing reapplies the file's own ~#+STARTUP~ visibility fresh each time, rather than trying to preserve exactly how things were folded/collapsed across the jump.

Landing on a step whose text is byte-identical to whatever's actually confirmed saved (the version this app last read from or wrote to disk/GitHub/WebDAV) clears the filename's modified indicator. The baseline this compares against updates on every successful Save during the session, not just at open.

*If the filename shows modified (red) but nothing you did explains why*, check the very first entry in the history list — if it reads "Opened (resumed unsaved local version)" instead of plain "Opened," this file had an edit from an earlier session that was never saved before the tab/app closed, and reopening it resumed that unsaved version rather than starting fresh from what's actually on disk/GitHub/WebDAV. Save to make the resumed version the real one, or use the History list to jump back to a specific earlier point if the resumed content wasn't what you wanted.

** Lists, tables, and body text
:PROPERTIES:
:CUSTOM_ID: lists-tables-and-body-text
:END:

- *Lists*: ordered, unordered, checkboxes (tap to cycle unchecked → in-progress → done), description lists (~term :: description~), and nested sub-lists. Tap a list item's text to reveal edit/add-item-below/delete actions.
- *Checkboxes*: cycle through the three states org supports. Progress cookies in a heading's title (~[3/8]~ or ~[40%]~, including the blank ~[/]~ / ~[/8]~ form) are recalculated automatically whenever a checkbox in that heading's subtree is toggled, added, or removed — matching real org-mode's default hierarchical counting (a heading's cookie counts checkboxes in its own list /and/ every descendant heading's, not just its direct list). A heading's own ~:COOKIE_DATA:~ property (real org's own documented override) can change what actually gets counted: ~checkbox~ or ~todo~ resolve the ambiguity real org itself describes when a heading has both checkboxes and TODO-keyword child headings below it (which one the cookie should reflect); both words together count both kinds combined; ~recursive~ (alongside ~todo~) extends TODO counting to the whole subtree rather than just direct children. Absent entirely — by far the common case — nothing changes: checkbox-only counting, recursively, same as always.
- *Tables*: tap a cell to edit it directly. Row/column add and remove controls sit below the table, always visible (not tap-to-reveal, since you need them to actually use the table). ~#+TBLFM:~ formulas ARE now evaluated — see [[#table-formulas][Table formulas]] below for the full behavior. *Header row(s) render bold* — org has no separate header-row syntax of its own; a header is defined purely by position relative to the table's own FIRST horizontal rule line (~|---+---|~), matching real org's own rule ("rows before the first horizontal rule are header lines"). This is *not* the same thing as "whichever row happens to be first" — a table with no rule anywhere (a freshly-created one, or a plain data table nobody's added a header divider to) has no header at all, and none of its rows render bold, even the top one. A table can have more than one rule (a real, if less common, convention for visually grouping data into sections) — only the row(s) before the *first* rule are ever the header; a later rule is just a group separator within the data, and doesn't turn the row above it into a second header.

*** Table formulas
:PROPERTIES:
:CUSTOM_ID: table-formulas
:END:

~#+TBLFM:~ formulas are evaluated — a subset of real org's own formula language. Real org hands anything beyond trivial arithmetic to Emacs Calc, an entire separate symbolic-math package with its own operator set, number formatting, unit/date arithmetic, and function library; that isn't reproduced here. What's supported:

| Name | Kind | What it does |
|-------------+------------+----------------------------------------------------------------------|
| ~+ - * /~   | operator   | Ordinary arithmetic                                                   |
| ~^~         | operator   | Exponent, right-associative (~2^3^2~ = ~2^(3^2)~ = 512)               |
| ~sqrt(x)~   | scalar     | Square root (a negative input gives 0 — no complex-number support)    |
| ~floor(x)~  | scalar     | Round toward −∞                                                       |
| ~ceil(x)~   | scalar     | Round toward +∞                                                       |
| ~round(x)~  | scalar     | Round to nearest; an exact ~.5~ tie rounds away from zero              |
| ~trunc(x)~  | scalar     | Round toward zero                                                      |
| ~date(ref)~ | scalar     | Parses a timestamp out of a cell into a date value — see below         |
| ~date(Y,M,D)~ | scalar   | Constructs a date value directly from year/month/day numbers           |
| ~deg(x)~    | scalar     | Un-tags an HMS-formatted duration back to its own plain, still-in-days number — see below |
| ~now()~     | scalar     | The current date and time, as a date value                             |
| ~== =~      | operator   | Equal to (both spellings accepted) — 1 if true, 0 if false, matching Calc's own boolean-as-number convention |
| ~!=~        | operator   | Not equal to                                                            |
| ~< > <= >=~ | operator   | Ordinary relational comparison                                         |
| ~&&~        | operator   | Logical AND — short-circuits, the right side is never evaluated once the left side alone is false |
| OR operator | operator   | Logical OR (see below for the actual two-character syntax — shown in prose here, not this table, since a literal pipe can't appear in a table cell) — short-circuits the same way, once the left side alone is true |
| ~!x~        | operator   | Logical NOT                                                             |
| ~and(a,b)~  | scalar     | Same as ~a && b~, as a function call — doesn't short-circuit           |
| ~or(a,b)~   | scalar     | The function-call form of logical OR (see below) — doesn't short-circuit |
| ~not(a)~    | scalar     | Same as ~!a~, as a function call                                       |
| ~if(c,t,f)~ | scalar     | Evaluates ~c~; returns ~t~ if true (non-zero/non-empty), ~f~ if false — see below |
| ~string(ref)~ | scalar   | Reads a cell's own raw text as a string, bypassing the normal number coercion — see below |
| ~"text"~    | literal    | A double-quoted string literal — see below                             |
| ~vsum(range)~    | aggregate | Sum                                                                |
| ~vmean(range)~   | aggregate | Arithmetic mean                                                    |
| ~vcount(range)~  | aggregate | Count of non-blank cells                                           |
| ~vmin(range)~    | aggregate | Minimum                                                            |
| ~vmax(range)~    | aggregate | Maximum                                                            |
| ~vmedian(range)~ | aggregate | Median                                                             |
| ~vvar(range)~    | aggregate | Sample variance (÷ n−1)                                            |
| ~vpvar(range)~   | aggregate | Population variance (÷ n)                                          |
| ~vsdev(range)~   | aggregate | Sample standard deviation                                          |
| ~vpsdev(range)~  | aggregate | Population standard deviation                                      |

~floor~ / ~ceil~ / ~round~ / ~trunc~ each also accept an optional second argument — how many digits after the decimal point to keep (~round($1, 2)~). There's no plain, unqualified ~variance~ / ~stddev~ name for either the sample or population variant — real Calc doesn't have one either.

*Conditional logic.* ~if(condition, true_value, false_value)~ evaluates ~condition~ first; Calc's own boolean convention applies (a non-zero number, or a non-empty string, counts as true) — then evaluates and returns *only* the matching branch. This is genuinely short-circuiting, not just a convenience: ~if($1 != 0, 100 / $1, 0)~ never actually computes ~100 / $1~ when ~$1~ is 0, so the classic divide-by-zero guard actually works as written rather than erroring regardless of which branch gets used. ~&&~ and ~||~ both short-circuit the same way: the right side is never evaluated once the left side alone already decides the result. ~and(a,b)~ / ~or(a,b)~ / ~not(a)~ are the function-call equivalents of ~&&~ / ~||~ / ~!~ — these don't short-circuit, matching real Calc's own actual function-call semantics.

Comparisons (~==~ and ~=~ both mean equal to; ~!=~, ~<~, ~>~, ~<=~, ~>=~) return ~1~ for true or ~0~ for false, and bind tighter than ~&&~ / ~||~, which in turn bind looser than ~+ - * /~ — so ~$1 >= 50 && $2 >= 50~ parses exactly as written, ~($1 >= 50) && ($2 >= 50)~, not something else. A double-quoted string literal (~"Both Pass"~, with ~\"~ for a literal quote inside one) evaluates to text rather than a number; ~string(ref)~ reads a cell's own raw text directly as a string — bypassing the normal number coercion every other plain reference goes through — so ~string($1) == "Sales"~ compares as text even though a bare, un-wrapped ~$1 == "Sales"~ would instead try (and fail) to read the cell as a number. Nested ~if()~ calls, using the false-branch slot, give an else-if chain: ~if($1 >= 90, "A", if($1 >= 80, "B", "C"))~.

*Date and time arithmetic.* ~date(ref)~ reads a cell's own raw text — expects a standard org timestamp, ~[YYYY-MM-DD]~ or ~<YYYY-MM-DD>~, optionally with a time (~<YYYY-MM-DD HH:MM>~); the day-name real org normally writes (~<2026-08-25 Tue>~) is accepted but entirely optional here, unlike real org's own actual timestamp syntax — a plain, un-wrapped cell reference (~$1~ alone) is read as an ordinary number instead, the same as always, so wrapping in ~date()~ is what actually signals "this cell holds a timestamp, not a number." ~date(2026, 8, 25)~ builds one directly from three plain numbers instead of a cell. *Every component is range-checked* — month 1–12, day within the actual length of that specific month (leap years correctly extend February to 29, so ~date(2028, 2, 29)~ is valid while ~date(2026, 2, 29)~ isn't), hour 0–23, minute 0–59 — for both this three-number form and a raw timestamp parsed out of a cell alike; a value like ~<2026-06-34>~ produces ~#ERROR~ rather than silently rolling over into some other, unstated date.

Subtracting two date values (~date($2) - date($1)~) gives a plain integer — days elapsed — *unless either side had a time-of-day component*, in which case the result is a duration shown in Calc's own actual default HMS notation, ~H@ M' S"~ (~8@ 30' 0"~ for an 8.5-hour gap). Adding or subtracting a plain number to/from a date value shifts it by that many days, staying a date, formatted back into the cell as an org timestamp (~date($1) + 14~ → ~<2026-09-08>~ for a 14-day-out deadline). ~deg()~ un-tags an HMS duration back to its own plain, still-*in-days* number, letting it feed into further ordinary arithmetic — ~deg(date($2) - date($1)) * 24;%.2f~ turns that same 8.5-hour gap into ~8.50~ decimal hours for a timesheet, the ~;%.2f~ mode flag (above) applying normally since ~deg()~'s own result is a plain number again. ~now()~ returns the current date and time as a date value, usable the same way a cell-derived one is.

Reference syntax: ~$N~ (column N of the current row), ~@N$M~ (row N, column M, both explicit), ~@-N~ / ~@+N~ (a row relative to the current formula's own target), ~@<~ / ~@>~ / ~$<~ / ~$>~ (first/last row or column), and a range (~$1..$3~, or a full ~@1$1..@3$2~) as an aggregate function's own argument. A range (or a plain reference) can omit its own column specifier entirely — ~@2..@6~, not ~@2$2..@6$2~ — meaning "these rows, in whichever column this formula's own result is going into." A horizontal rule (hline) never gets its own row number — ~@N~ always counts every actual row, *including the header*. The column-formula *shorthand* (~$M=~, with no ~@~ at all, applying one formula to every row in the table) skips any row before the table's own first hline, leaving that row's own text alone; an explicit, deliberately-targeted cell formula (~@1$2=~) still freely modifies that row. A table with no hline anywhere has no header, so nothing is excluded from column formulas.

~@I~, ~@II~, ~@III~, ... reference a table's own hlines directly — repeated-"I"-character notation, *not* Roman numerals (~@IIII~ is the 4th hline, not ~@IV~), optionally followed by a ~+N~ / ~-N~ offset for a data row that many positions after/before the hline itself (~@III+2~). A range spanning two hline references — ~vsum(@I..@II)~ — expands to every actual data row strictly between them. A count beyond how many hlines the table actually has clamps to the table's own actual end rather than erroring.

A formula's own target is a single cell (~@N$M=~), a range (~@N$M..@N$M=~, applying the same formula independently to every cell in that range), or, with no ~@~ at all (~$M=~), the "column formula" shorthand applying to every data row. A range target's own two endpoints need an explicit row on each side — omitting one errors. Multiple formulas in one ~#+TBLFM:~ line, separated by ~::~, are evaluated in order, each one able to see any earlier formula's own already-updated values within the same pass. Only the *first* ~#+TBLFM:~ line immediately below a table is recognized as that table's own formulas.

Recalculation is explicit, not automatic on every edit. A *🔢 Calc* button appears below any table that has its own ~#+TBLFM:~ line and recalculates just that one table. For recalculating every table in the whole document at once, bind ~'org-table-recalculate-buffer-tables~ to an [[#extras-menu][Extras menu]] entry instead; every ~#+TBLFM:~ formula in every table gets recalculated together as a single undo step. A malformed formula in one table is reported and that one table is skipped, without blocking recalculation of any other table.

A blank cell's value depends on how it's used and on the formula's own mode flags (below): by default, a *plain, direct reference* (e.g. ~$1+$2~) reads a blank as 0; used *inside a range* fed to an aggregate function, it's *omitted from the range entirely* — so ~vmean~ of a range with one blank cell averages only the non-blank values, and ~vcount~ doesn't count it. Non-blank text that isn't a valid number reads as ~nan~ by default (not 0) and propagates through arithmetic, so a formula referencing a stray label cell visibly shows something's wrong rather than silently computing a plausible-looking but wrong number; the ~N~ flag below restores the "read as 0" behavior.

A formula's own trailing mode string (~;flags~ after the expression) supports:

- ~%.Nf~ / ~fN~ — fixed, N decimal places (~%0.Nf~ also recognized). ~4.85;f2~ → ~4.85~.
- ~%d~ — truncates to a plain integer toward zero, not rounding (~4.85~ → ~4~; ~-4.85~ → ~-4~).
- ~nN~ — normal notation, N significant figures. ~3.14159265;n5~ → ~3.1416~.
- ~sN~ — scientific notation (one digit before the decimal), N significant figures. ~123456.789;s3~ → ~1.23e5~.
- ~eN~ — engineering notation (exponent always a multiple of 3), N significant figures. ~123456.789;e3~ → ~123e3~.
- ~pN~ — precision; accepted but has no effect on the displayed result (matching real org, where ~p~ alone doesn't change the display format either).
- ~E~ — keeps a blank cell in a range instead of omitting it (shown as ~nan~), and makes a blank plain reference read as ~nan~ instead of 0.
- ~N~ — non-numeric text (and, combined with ~E~, a blank field too) reads as 0 instead of ~nan~.
- ~T~ / ~U~ / ~t~ — duration mode. Operand cells matching ~HH:MM[:SS]~ are read as total seconds (a bare integer is also read as seconds, real org's own "integers are considered as seconds" rule); without one of these three flags, ~HH:MM~ text isn't treated as a duration at all. The result is written back as ~HH:MM:SS~ (~T~), ~HH:MM~ (~U~), or fractional hours to 2 decimal places (~t~). Negative durations are supported. Hour zero-padding is controlled by ~org-table-duration-hour-zero-padding~ (see [[#local-variables][Local Variables]], default on) — minutes and seconds are always 2-digit padded regardless.

An unrecognized flag is ignored, falling back to whatever was already parsed. Example:

#+begin_example
|  Task 1 |   Task 2 |    Total |
|---------+----------+----------|
|    2:12 |     1:47 | 03:59:00 |
|    2:12 |     1:47 |    03:59 |
| 3:02:20 | -2:07:00 |     0.92 |
#+TBLFM: @2$3=$1+$2;T::@3$3=$1+$2;U::@4$3=$1+$2;t
#+end_example

*A formula that fails at evaluation time* — an out-of-range reference, a range used where a single value is expected, and similar — writes the literal text ~#ERROR~ into just that one cell, matching real org's own actual behavior: every other formula in the same ~#+TBLFM:~ line still evaluates normally, and the rest of the table still updates. A malformed formula that fails to even *parse* (invalid syntax, an unknown function name) is different — that's still surfaced as an error for the whole recalculation, since there's no single cell to attribute a syntax problem in the ~#+TBLFM:~ line itself to.

Out of scope: Emacs Calc compatibility beyond what's documented above (date arithmetic, unit conversions other than duration/seconds, complex numbers, matrices, symbolic algebra); named-field references; automatic reactive recalculation on every keystroke.
- *Paragraphs*: tap text to reveal edit/add-paragraph-below/delete.

Every delete action still asks for confirmation — but is no longer irreversible: *Undo/redo now covers every edit in this app* (see [[#undoredo-and-history][Undo/redo and History]]).

** Inline text markup
:PROPERTIES:
:CUSTOM_ID: inline-text-markup
:END:

All six of org's emphasis markers work, in headings, paragraphs, and list items:

| Markup | Syntax | Renders as |
|---+---+---|
| Bold | ~*bold text*~ | *bold text* |
| Italic | ~/italic text/~ | /italic text/ |
| Underline | ~_underline text_~ | underlined |
| Strikethrough | ~+strikethrough text+~ | +strikethrough text+ |
| Verbatim | ~=verbatim text=~ | ~verbatim text~ (literal, not further parsed) |
| Code | =~code text~= | ~code text~ (literal, not further parsed) |

A marker only opens where it's preceded by the start of a line, whitespace, or one of ~-({'"~, and not immediately followed by whitespace; it only closes where it's not immediately preceded by whitespace, and is followed by the end of the line, whitespace, or closing punctuation — matching real org's own border rules for the common cases, not a full reproduction of org's complete border-character tables. Bold/italic/underline/strikethrough nest inside each other (~*bold /italic/ bold*~ works); verbatim and code never do — their content is always literal, exactly matching org's own rule that these must be the innermost markers.

*Horizontal rule*: a line consisting of only dashes, at least 5 of them (~-----~), renders as a horizontal rule. Whitespace around the dashes is fine; anything else on the line (a 6th character that isn't a dash) means it's just a paragraph, not a rule.

*** LaTeX math fragments
:PROPERTIES:
:CUSTOM_ID: latex-fragments
:END:

Math written directly in a heading, paragraph, or list item renders as actual typeset math, not raw LaTeX text — using [[https://katex.org][KaTeX]], a JavaScript rendering library, vendored locally (not a CDN). This is display-only: the underlying ~.org~ file's own text is untouched either way, and tapping into edit mode always shows the exact raw source, never the rendered version.

| Delimiter | Kind | Restrictions |
|---+---+---|
| ~\(...\)~ | Inline | None — org's own recommended form |
| ~\[...\]~ | Display | None |
| ~$$...$$~ | Display | None |
| ~$...$~ | Inline | No whitespace directly inside the delimiters; the closing ~$~ must be followed by whitespace or punctuation, but never a dash (avoiding ~$5-10~ reading as math) |
| ~\begin{env}...\end{env}~ | Display | ~\begin~ must start a line, preceded by nothing but whitespace |

~$...$~'s own restrictions avoid misreading ordinary currency text as math — ~costs $5 and $10 total~ correctly stays as plain text. The opening ~$~ may be preceded by any character at all except another ~$~ (or the start of the line). Content's first character excludes space/tab/newline/comma/semicolon/period; the character immediately before the closing ~$~ excludes space/tab/newline/comma/period — semicolon is allowed there. ~$...$~ requires *at least two characters* of content — ~$x$~ cannot match — while ~\(x\)~ has no such restriction, so that's the form for a single-character case.

~\(...\)~ / ~\[...\]~ / ~$$...$$~ / ~\begin{env}...\end{env}~ all span an unlimited number of lines, including across a blank line in the middle (e.g. an ~align~ environment with its own rows separated by a blank line for readability). ~$...$~ is the exception: it caps at 2 embedded newlines.

KaTeX does *not* strip ~%~ as a LaTeX comment character the way real LaTeX does — the text after a ~%~ renders as literal content instead of being dropped.

A fragment KaTeX can't render (an unsupported command, a genuine syntax error) shows its own raw source text with a dashed border, rather than breaking the surrounding paragraph's own render or silently vanishing. KaTeX supports a substantial subset of LaTeX, not the complete language.

Renders everywhere inline markup already does — the outline itself, the read-only Docs viewer, and HTML export (KaTeX's own CSS is inlined into an export automatically, but only for a document that actually contains math). Markdown, ASCII, and ODT export don't render math at all — the raw LaTeX source passes through as ordinary text.

*Hard line break*: a line ending in two literal backslashes (~\\~) is
real org's own explicit line-break marker. Every source line within an
ordinary paragraph or list item reflows together with a plain
space by default — matching real org's own actual documented export
behavior (~org-export-preserve-breaks~ defaults to nil: adjacent
lines flow into one continuous run unless something forces a real
break). The ~\\~ marker forces that break, exactly where it's written
and nowhere else, whether in an ordinary paragraph, a
[[#editing-your-outline][QUOTE or CENTER block]], or any of the five
export formats (HTML/Markdown/ASCII/ODT).

*Subscript and superscript*: ~_~ and ~^~ mark sub/superscript — ~x_i~ and ~x^2~ both work without braces, and braces (~x_{alpha}~, ~10^{100}~) are always accepted too, mainly useful for readability once the script itself is more than a couple of characters. Controlled by ~org-use-sub-superscripts~ (see [[#local-variables][Local Variables]]):

| Value | Behavior |
|---+---|
| ~t~ (default) | Both ~x_i~ and ~x_{i}~ are interpreted |
| ~{}~ | Only the braced form ~x_{i}~ is interpreted; a bare ~x_i~ stays literal text |
| ~nil~ | Disabled entirely; ~_~ / ~^~ are always literal characters |

~_~ doubles as both the underline marker and the subscript marker — org's own overload, not a conflict introduced here. The two are disambiguated by what comes immediately before the ~_~: underline needs whitespace/start-of-line/certain punctuation before it (~_underlined_~), subscript needs a non-whitespace character immediately before it (~a_b~) — the opposite condition, so in practice they essentially never collide. Sub/superscript content is always literal — ~x_{*bold*}~ doesn't further interpret the ~*bold*~ inside it, the same way verbatim/code content doesn't.

*Footnotes*: ~[fn:label]~ is a reference — rendered as a small tappable superscript that jumps to (and briefly highlights) wherever the actual definition lives, anywhere in the document, even under a currently-folded heading. A definition can be given inline right at the reference itself, ~[fn:label:the actual note text]~, or ~[fn::an anonymous note]~ (no label — org's own convention for a footnote that's never referenced again elsewhere) — either way, an inline definition's text renders directly, styled distinctly (smaller, italic), rather than something to tap through to. The other standard org convention also works: a separate line starting with ~[fn:label]~ (e.g. ~[fn:1] The actual definition.~) is recognized as that footnote's own definition, shown with a small label marking it as one. Exported to Markdown as GFM's own ~[^label]~ / ~[^label]: text~ footnote syntax, and to HTML as a jump-linked superscript with a back-linked Footnotes section at the end of the document.

Table cells render inline markup too, same as everywhere else — tap a cell to see/edit its raw underlying text; tap away and it shows rendered again, matching how paragraphs and list items already work.

** Searching
:PROPERTIES:
:CUSTOM_ID: searching
:END:

Tap *More → Search* to search the currently open document — headings, tags, TODO keyword, priority, properties (key or value), SCHEDULED/DEADLINE timestamps, paragraphs, list items, table cells, and block content, case-insensitively — *and*, when any are configured, every file listed in ~org-agenda-files~ too (the same aggregation Agenda itself already uses). Results show immediately from whatever's already loaded — the current document at minimum — and a file that's still fetching (the first search of a fresh session, before Agenda has ever been visited) doesn't block that; search automatically re-runs itself the moment each agenda file actually finishes loading, so results progressively fill in with that file's own matches too, rather than silently staying incomplete until some unrelated later action happens to trigger a fresh search. A file that fails to fetch is simply not included, not an error for the rest of the search. The query box itself and its *Regex* toggle live in the minibuffer at the very bottom of the screen (see [[#modeline][Modeline and minibuffer]]) — real Emacs's own convention for where a search prompt belongs — while results update live as you type and show a short snippet with the match, grouped under the heading each one belongs to, in their own results area where they were before. A result from a file other than the one currently open shows that file's own name alongside its heading, so it's never ambiguous which document a given match actually lives in.

Search looks at the entire document regardless of current fold state — a match inside a collapsed heading, inside body text hidden by ~#+STARTUP: content~, or inside properties/block content folded by ~#+STARTUP: showall~, still shows up. Tapping a result expands whatever's necessary to actually reveal it (including the target heading's own body and, for a property or block match, its drawers too — not just its ancestors) and scrolls to it with a brief highlight — switching to that file first, the same way tapping a ~file:~ / ~github:~ / ~webdav:~ link to a different document already does, if the result came from an agenda file rather than the one already open.

*Regex mode*: the *Regex* toggle next to the minibuffer's own query box switches from plain substring matching to a real regular expression, case-insensitive either way. Off (the default) is a literal, "find this exact text" search — a query containing ~.~ or ~(~ matches that character literally, with no escaping needed, which is what most searches actually want. On, the query is compiled as a JavaScript RegExp; an invalid pattern shows a clear error message in the results area rather than crashing or silently showing "no matches," so a mistyped pattern and a genuinely empty result set are never confused for each other.

*Filter tokens*: the same query box also recognizes a small set of structured tokens, plus keyword search. They combine with each other as an implicit AND:

- ~+word~ / ~-word~ / a bare ~word~ with no sign at all — keyword search across the whole entry (title, tags, TODO state, priority, properties, planning, and body text — everywhere this box has always searched). A bare word and an explicit ~+word~ mean exactly the same thing — "the entry must contain this somewhere" — there's no toggle to turn this on; every plain word in the query already works this way. ~-word~ excludes instead, with no dependency on whether any ~+~ appears anywhere else in the query. This matches real Emacs org-mode's own ~org-search-view~ (Org Agenda Search, ~C-c a s~) precisely: ~+computer +wifi -ethernet~ — or equivalently ~computer wifi -ethernet~, since a bare word already means the same as ~+word~ — finds entries containing both "computer" and "wifi" but not "ethernet." The one thing worth knowing up front: since only a bare word or a leading ~+~ (never a leading ~-~ on its own) is what "activates" as a literal keyword search term versus every other kind of stray punctuation, a query like ~-5~ is read as "exclude entries containing '5'," not a literal search for the text "-5" — regex mode is the way around that if you actually need it.
- ~tag:urgent~ — heading must have this tag (honoring tag inheritance, same as everywhere else this app applies it). ~+tag:urgent~ means the same thing; ~-tag:urgent~ excludes it. This is the only way to filter by tag specifically now — a bare ~+word~ searches the whole entry, not just its tags.
- ~todo:KEYWORD~ — heading's TODO state must equal this exactly (case-insensitive) — e.g. ~todo:WAITING~. ~-todo:KEYWORD~ excludes that state instead; a heading with no TODO keyword at all still passes an exclude filter, the same way an entry lacking a keyword already passes ~-word~ above.
- ~priority:X~ — heading's priority must equal this exactly (case-insensitive) — e.g. ~priority:A~. ~-priority:X~ excludes it, same absence-passes rule as above.
- ~key:value~ — anything else in ~key:value~ form matches a property named ~key~ whose value contains ~value~ (substring, case-insensitive) — e.g. ~spouse:Mary~. ~-key:value~ excludes it.
- ~|~ inside any of the ~tag:~ / ~todo:~ / ~priority:~ / ~key:value~ forms above means "any of these" — ~tag:urgent|blocked~, ~todo:TODO|WAITING~, ~priority:A|B~, ~assignee:Bob|Alice~ all match either alternative. Negated, it flips to "none of these" — ~-todo:TODO|WAITING~ means neither state. This only combines alternatives *within* one filter's own value list — there's no OR *between* separate filters (e.g. "tagged urgent OR priority A" isn't expressible), and no parentheses/grouping at all; a deliberate, smaller design (see the module-level comment in ~src/search.js~ for the fuller reasoning) rather than reproducing real org's own fuller boolean match-syntax.

The minibuffer's own placeholder text (~Search, +word -word, or [tag|todo|priority|key]:value…~) is a standing reminder of this exact pattern, so the syntax doesn't need to be memorized or looked up here to be usable. A matched keyword is highlighted directly within its result's own snippet, so it's immediately obvious *why* a given result matched rather than having to re-read the whole line to spot it.

Example: ~+work todo:WAITING budget~ — tagged ~work~, in WAITING state, and containing "budget" somewhere. A query with only exclude terms or structured filters and no keyword to actually find (~tag:work -someday~) returns the matching headings directly, one result each, rather than needing something to highlight.

This is not a faithful subset of real org-mode's own search, which is several separate, fragmented tools — sparse trees (~C-c /~), a boolean match-syntax with ~&~ / ~|~ / exact ~=~ matching, and ~org-search-view~ as a separate command. Here, one box reaches tags/TODO/priority/properties /and/ free text together, with AND-only combining and ~key:value~ instead of quoted ~=~. Out of scope: OR/boolean logic, exact property-value matching (always substring), and sparse-tree-style refolding — this produces a flat results list instead.

** Modeline and minibuffer
:PROPERTIES:
:CUSTOM_ID: modeline
:END:

A fixed two-row bar at the very bottom of the screen, styled after real Emacs's own frame layout — a dense modeline above a minibuffer below — rather than the status line and search box each living wherever happened to have room before this existed.

*The modeline* is read-only, monospace, and terse, matching real Emacs's own actual convention:

- *Modified indicator* — ~**~ if the buffer has unsaved changes, ~--~ if not, real Emacs's own actual convention. Real Emacs's own fuller buffer-state block also includes a coding-system and end-of-line segment; deliberately left out here rather than kept for cosmetic authenticity, since this app always writes UTF-8 and always normalizes to Unix (~\n~) line endings on save regardless of the original file's own encoding — that portion would never actually vary for anything this app could open, so it would be static decoration rather than real information.
- *Buffer name* — the exact same text shown in the header next to the folder icon, including its own ~(GitHub~ / ~WebDAV~ / ~Local~ / ~Imported)~ suffix (see ~org-xx-hide-filename-in-menu~ below if you'd rather it only appeared here).
- *Position* — ~Top~ / ~Bot~ / ~All~ / a percentage, for how far down the document the visible area currently is, plus ~L~/line-number when a heading is focused (there's no meaningful "current line" otherwise, so it's simply omitted rather than showing something arbitrary) and ~C~/column only while an actual text field is being actively edited, reading its own live cursor position — this app has no persistent, Emacs-style point/cursor concept between edits the way a plain text buffer does, so a column figure the rest of the time would be fabricated, not real information.
- *Date/time*, when ~display-time-mode~ is on (the default) — formatted per ~display-time-format~ (default ~"%H:%M"~), both real Emacs variables, using the exact same ~%<FORMAT>~ strftime-style subset [[#capture][Capture templates]] already support for date insertion, not a separate implementation. Updates at least once every 30 seconds even with nothing else happening.
- *Clocking info*, when a clock is running anywhere in the document (~C-c C-x C-i~, or the ▶ button, or the Extras menu's own ~'org-clock-out~-adjacent entries if configured) — the elapsed time on /this specific clock-in/ in brackets, then the heading's own title, e.g. ~[⏱ 0:35] Write the quarterly report~. This is the current session's own elapsed time, not the task's lifetime total across every past clock-in — real Emacs's own ~org-clock-mode-line-total~ can be configured either way; this app always shows the current session, the simpler and more common of the two.

*The minibuffer*, directly below, is where the status line, god-mode's own chord-in-progress echo, and the search box (see [[#searching][Searching]]) all now live — one shared strip for "the app is telling you something right now or wants brief input," matching what a minibuffer actually is in Emacs, rather than three separate, differently-styled elements scattered across the screen. Only one of the three shows at a time: the search box takes priority whenever search is open (an active input session), the god-mode echo next whenever a chord is in progress, and the last real status message otherwise. A status message clears itself the moment you start a new action — the next keypress or tap — the same way Emacs's own echo area clears at the start of each new command, rather than lingering indefinitely until some unrelated later message happens to overwrite it.

Three variables control this, all set via Global or Local Variables (or the friendlier *Quick Settings* controls in Settings → Quick Settings → *Modeline*, which edit the exact same baseline):

| Variable | Default | Effect |
|---+---+---|
| ~display-time-mode~ | ~1~ (on) | Real Emacs's own actual minor-mode toggle, including its own ~1~ / ~0~ convention rather than this app's usual ~t~ / ~nil~ — confirmed directly against the Emacs manual. ~0~ hides the date/time segment. |
| ~display-time-format~ | ~"%H:%M"~ | Real Emacs's own actual variable, real Emacs's own actual default. Any ~%<FORMAT>~ token [[#capture][Capture templates]] supports works here too. |
| ~org-xx-hide-filename-in-menu~ | ~nil~ | This app's own extension (not a real Emacs variable, hence the ~org-xx-~ prefix). ~t~ hides the filename from the header next to the folder icon, once the modeline is already showing it there instead. |

A word that happens to start with ~+~ / ~-~ (a negative number, a hyphenated word) or matches the ~word:word~ shape (most commonly a ~mailto:~ link) can get read as a filter token instead of literal text. ~http://~ and ~https://~ URLs are excluded from this — ~see https://example.com~ searches correctly as free text.

A ~tag:~ filter and a ~key:value~ filter both respect ancestor inheritance, matching real org's own actual defaults exactly (see [[#differences-from-emacs-org-mode][Differences from Emacs org-mode]] for the full behavior and the ~org-use-tag-inheritance~ / ~org-use-property-inheritance~ settings that control it): tag inheritance is on by default, so a parent tagged ~:work:~ makes an untagged child match ~+tag:work~ too; property inheritance is off by default, matching real org's own choice there.

** Links and images
:PROPERTIES:
:CUSTOM_ID: links-and-images
:END:

- ~[[target][description]]~ links render as tappable text.
- *A bare URL auto-links too*, matching real org's own documented behavior — ~https://example.com~ typed directly in a sentence (no ~[[...]]~ brackets at all) renders as a tappable link, same as the bracketed form. ~<https://example.com>~ (angle-bracket wrapped) works the same way, and is org's other recognized plain-URI form. Recognized schemes: ~http~, ~https~, ~ftp~, ~mailto~, ~doi~, ~file~, ~github~, ~webdav~ — a well-defined set, not arbitrary ~word:word~ text (so a time like ~10:30~ or a ratio like ~3:4~ is never misread as a link). Trailing sentence punctuation (~.~, ~,~, ~)~, etc.) is excluded from a bare match — ~see https://example.com/page.~ links just the URL, not the period; wrap it in ~<...>~ or ~[[...]]~ if a URL genuinely needs to end in one of those characters.
- ~doi:10.1145/1327452.1327492~ — a Digital Object Identifier, common in academic citations — resolves to the standard ~https://doi.org/...~ resolver URL and opens like any other external link. Works both bracketed and as a bare auto-link.
- Internal links resolve by heading title (~[[*Some Heading]]~), by ~CUSTOM_ID~ property (~[[#my-id]]~), or fall back to a title search for bare text — tapping one expands ancestors and scrolls to the target heading. Set a heading's ~CUSTOM_ID~ via the properties section of its general editor (see [[#editing-your-outline][Editing your outline]]). *A floating ⏎ button appears bottom-left* after following one, remembering wherever the tap actually happened (organic scrolling, not just a prior link jump) so a document with a table of contents — Docs' own included — is genuinely navigable on a touch device with no reliable browser Back to fall back on. Chained link-following (tap through several links in a row, from either the outline or Docs) unwinds one hop at a time, standard back-stack behavior; the button disappears once there's nowhere left to go back to. Deliberately low-opacity at rest so it doesn't compete with the content underneath (a brief, clearer flash on tap for confirmation), and colored to match the current theme — the same dark-on-light / light-on-dark contrast as ordinary text, not a fixed color of its own.
- *~http://~ / ~https://~ image links* render inline as actual images, if ~#+STARTUP: inlineimages~ is set (off by default — see below).
- *Local/relative image paths load and render on GitHub and WebDAV* — ~[[photo.png]]~, ~[[images/photo.png]]~, ~[[file:photo.png]]~, ~[[github:images/photo.png]]~ all resolve relative to the current document's own path (a bare filename lands beside it, same convention as capture-to-file and archiving below), get read as binary and base64-encoded into a ~data:~ URL, and appear as real images — same ~#+STARTUP: inlineimages~ gate as ~http(s)~ images above. Cached per session once loaded, so re-rendering the outline (any edit, anywhere) doesn't re-fetch the same image again. *Local files (File System Access) and iOS import still show the ~[image: path]~ placeholder* — same picker-permission wall as archiving and capture-to-file: reading an arbitrary sibling file needs a handle the browser hasn't granted, and can't be granted silently mid-render.
- *~file:~ / ~github:~ / ~webdav:~ links are recognized, parsed, and navigate* — absolute path (~file:/home/user/documents/notes.org~), relative path (~file:projects/todo.org~), a specific headline (=file:~/notes.org::*Project Alpha=), and a text search (=file:~/notes.org::exact phrase=) all parse correctly into a scheme, a path, and an optional in-file target, matching real org's own ~::~ convention. ~github:path/in/repo.org~ and ~webdav:path/on/server.org~ follow the same rules for their own backend. Tapping one opens the target document (the same mechanism File → Open already uses, including its own unsaved-changes handling) and jumps straight to the headline or text match if one was specified. A bare ~file:~ /relative-path link with no explicit scheme uses whichever backend the /current/ document itself came from; an explicit ~github:~ / ~webdav:~ always targets that backend directly, regardless of what's currently open. *The floating back button follows a link like this across documents too*, not just within one — tap a link, do whatever work needed doing over there, then tap back to return to the exact heading the link itself lived in, expanding whatever ancestors need expanding and that heading's own body content too (not just revealing its title row), even though the file you're returning to has long since been unloaded and would otherwise need re-opening and re-parsing from scratch to get back to at all. This restores by the heading's own title path, not a raw remembered scroll position — a re-parsed document's own fold state resets to its file's own default every time it's freshly opened, so a pixel offset alone would land somewhere different once the page's own shape had changed; falls back to the remembered scroll position only when the link had no containing heading at all (one in the document's own preamble) or that heading's since been renamed or removed. This only works when both the document you're leaving and the one it points at are on GitHub or WebDAV, though — the same picker-permission wall described below for local files means a local document can't be reprogrammatically reopened by the back button either, so returning to one shows the same clear message rather than silently failing. *Local files and iOS import are the one exception* — same picker-permission wall as archiving, capture-to-file, and image loading below: opening an arbitrary path needs a fresh picker gesture the browser requires per file, which can't happen from a link tap, so those show a clear message instead of attempting (and failing) a silent open.
- *~attachment:~ links* — real org-attach's own actual link type, produced by this app's own 📎 Attach action (see [[#attachments][Attachments]] for the full behavior: heading-relative resolution with ancestor inheritance, inline image display the same as any other image link above, an inline player for audio, an in-browser viewer for anything else that has one, falling back to a download only when it doesn't). Bracketed-only (~[[attachment:photo.jpg]]~) — unlike ~file~ / ~github~ / ~webdav~ above, ~attachment:~ isn't part of the bare/angle-bracket auto-link scheme set, so a plain ~attachment:photo.jpg~ typed directly in text (no brackets) is just ordinary text, not a link.

** Configuration
:PROPERTIES:
:CUSTOM_ID: configuration
:END:

Three separate mechanisms, all ultimately setting the same kind of thing (an Emacs Lisp variable, or an org-specific directive), at three different scopes -- resolved in the same precedence order real Emacs org-mode uses:

1. *Global Variables* (below) -- the lowest-precedence layer, an app-wide baseline that applies across every file, configured once in Settings.
2. *~#+STARTUP:~* ([[#folding-and-startup][below]]) -- a file's own directive line, overriding the global baseline for that file specifically. Only three variables have a ~#+STARTUP:~ shorthand at all -- most variables skip this layer entirely and are only ever set via Global Variables or Local Variables:

| Variable | ~#+STARTUP:~ keyword(s) |
|---+---|
| ~org-log-done~ | ~logdone~ (→ ~time~), ~lognotedone~ (→ ~note~) |
| ~org-startup-folded~ | ~overview~, ~content~, ~showall~, ~showeverything~, ~show2levels~, ~show3levels~, ~show4levels~, ~show5levels~ |
| ~org-startup-with-inline-images~ | ~inlineimages~ (→ ~t~), ~noinlineimages~ (→ ~nil~) |

3. *Local Variables* ([[#local-variables][below]]) -- a file's own "# Local Variables:" block, the highest-precedence layer. This is a general Emacs mechanism (not org-specific), processed last so a file can override anything set earlier.

In short: *Local Variables beats #+STARTUP beats Global Variables*. A variable set at a higher layer always wins over a lower one for that same file; a variable left unset at a given layer simply falls through to the next one down. Most of the variables below are only ever read from Global Variables or Local Variables directly, with no ~#+STARTUP:~ layer in between at all -- the three in the table just above are the deliberate exceptions, since they're also the only three variables real org itself gives a dedicated ~#+STARTUP:~ shorthand to.

*** Global Variables
:PROPERTIES:
:CUSTOM_ID: global-variables
:END:

Set in *Settings → Global Variables* -- the lowest-precedence layer described above, and the only one of the three that isn't stored inside any particular ~.org~ file at all. Same "name: value" per-line text format as a file's own [[#local-variables][Local Variables]] block, just without that mechanism's "# Local Variables: ... # End:" wrapper, since this text lives in a dedicated Settings field rather than inside a file's own comment syntax. Example:

#+BEGIN_SRC
org-log-done: 'time
org-agenda-start-on-weekday: 1
#+END_SRC

Every variable [[#local-variables][Local Variables]] recognizes can be set here too, at this lower, app-wide precedence -- both sections document the same variables, so see Local Variables below for the full list and what each one does; nothing here is exclusive to this layer. Takes effect immediately on *Save* -- no reload, and no need to reopen whatever document is currently open, matching how the theme and font settings already apply instantly. Included in *Export Settings* / *Import Settings…* (see [[#file-management][File management]]) along with every other setting, so this travels with a settings backup like anything else.

*Typed "smart" quotes are normalized automatically* -- iOS (and many Android keyboards, and some desktop apps) auto-substitute a typed straight quote (~"~ / ~'~) with a typographic "curly" one (~“~ ~”~ / ~‘~ ~’~) as part of ordinary autocorrect. Every quote-delimited value here -- ~org-xx-extra-menu~'s own double-quoted tokens and its ~'function-name~ single-quote sigil, ~org-xx-menu-aliases~'s own tokens, and the separate [[#capture-templates][Capture Templates]] JSON -- depends on the literal ASCII character. Both Quick Settings and this raw text box (and Capture Templates' own save) correct any curly quote back to a straight one automatically on save, in both directions (a genuine typed apostrophe/quotation mark inside ordinary prose elsewhere in the app -- a heading's title, a paragraph -- is untouched; this only applies here, where the text is always syntax, never prose).

*** Folding and ~#+STARTUP~
:PROPERTIES:
:CUSTOM_ID: folding-and-startup
:END:

org-pwa reads and applies ~#+STARTUP:~ directives, typically on the first line of the file. None, some, or both of the following can be present on one line, or spread across several — the last matching keyword wins if there's a conflict:

| Category | Keywords | Default |
|---+---+---|
| Heading visibility | ~overview~, ~content~, ~showall~, ~showeverything~, ~show2levels~, ~show3levels~, ~show4levels~, ~show5levels~ | ~showeverything~ |
| Inline images | ~inlineimages~, ~noinlineimages~ | ~noinlineimages~ |
| Progress logging on DONE | ~logdone~, ~lognotedone~ | neither (no logging) |

- ~overview~ — only top-level headings shown, everything else folded.
- ~show2levels~ / ~show3levels~ / ~show4levels~ / ~show5levels~ — the same idea as ~overview~, but the cutoff depth is configurable instead of always being 1: headings are shown down through the given level, with body text hidden at every one of those visible levels (not just the deepest) and anything deeper folded away entirely — ~show3levels~, for instance, shows levels 1 through 3 with no body text anywhere, and hides level 4 and beyond completely.
- ~content~ — every heading line unfolded, but body text (paragraphs/lists/tables) and properties stay hidden until you tap a heading open — a genuinely separate visibility axis from "is this heading's subtree folded," not just an alias for ~showall~.
- ~showall~ — body text, lists, and tables all shown. Property drawers (~:PROPERTIES: ... :END:~) and block content (~#+BEGIN_SRC~ / ~#+BEGIN_QUOTE~ /etc.) stay folded, collapsed as a single line each.
- ~showeverything~ — everything ~showall~ shows, plus property drawers and block content, both fully expanded. This is the actual, sole structural difference between the two modes.
- ~logdone~ / ~lognotedone~ — see [[#progress-logging][Progress logging]] for the full behavior; these two set ~org-log-done~ to ~time~ / ~note~ respectively.

Manually cycling a heading to "fully expanded" (the slide-left gesture, or tapping through the fold states) always reveals everything about that heading — properties and block content included — regardless of what the file's ~#+STARTUP:~ line says. So a ~showall~ file still lets you open any specific heading's properties or block content by hand; you're never stuck needing to change the file's own directive just to peek at one thing. This reverses cleanly too: collapsing the heading again — swipe, or the chevron — correctly re-hides whatever was revealed, rather than leaving it stuck visible.

These defaults match real Emacs org-mode's own out-of-the-box behavior (no ~#+STARTUP~ line means fully shown, not folded). See [[#local-variables][Local Variables]] for archived-heading cycling behavior, a separate mechanism from ~#+STARTUP:~ entirely.

The *chevron is different*: tapping it still opens an archived heading regardless of this setting — real Emacs has separate force-open mechanisms outside of TAB/cycling for this (~C-c C-TAB~, a universal-argument TAB, ~outline-show-all~); the chevron fills that role here. See [[#progress-logging][Progress logging]] for the complete behavior, including how this relates to the more general per-keyword ~!~ / ~@~ / ~@/!~ / ~/!~ logging spec.

Sets the initial heading-visibility mode when a file first opens, settable directly here rather than only via the ~#+STARTUP:~ shorthand (see the table in [[#configuration][Configuration]] above and [[#folding-and-startup][Folding and #+STARTUP]] below for what each mode actually shows). ** Progress logging
:PROPERTIES:
:CUSTOM_ID: progress-logging
:END:

Two related mechanisms, both writing into the same place — a heading's ~:LOGBOOK:~ drawer — real org-mode's own convention for keeping a running history of state changes and notes, separate from a heading's ordinary body content.

*** ~org-log-done~

Set via ~#+STARTUP: logdone~ or ~#+STARTUP: lognotedone~ (see [[#folding-and-startup][Folding and #+STARTUP]]) — controls what happens automatically whenever a heading enters a DONE-type state (tapping the TODO badge to cycle there, or the action-menu toggle), matching real org-mode's own two mutually-exclusive modes:

- ~logdone~ (~time~) — inserts a ~CLOSED: [timestamp]~ planning line the moment a heading becomes DONE. Cycling it back to a different, non-done keyword removes that timestamp again; cycling it all the way back to no keyword at all also removes it by default, unless ~org-closed-keep-when-no-todo~ is set (see [[#local-variables][Local Variables]]) — matching real org's own distinct handling of that specific case. Re-marking an already-done heading as a *different* done keyword (e.g. DONE → KILL) doesn't insert a second timestamp or disturb an existing one, since that's not "entering" DONE.
- ~lognotedone~ (~note~) — instead of (or alongside — see below) a timestamp, prompts for a note the moment a heading becomes DONE, in a small dedicated panel. The TODO badge itself flips immediately when tapped — it never waits on the note — so *Skip* simply declines to add one without reverting the state change. A saved note is filed as a new ~:LOGBOOK:~ entry, timestamped.

These two are alternatives for a *plain* DONE-type keyword with no logging spec of its own — a file has either ~logdone~ or ~lognotedone~ active as the default, never both at once for the same keyword. With neither set (the default — no ~#+STARTUP:~ line, matching real org's own out-of-the-box behavior), entering DONE inserts nothing extra on its own.

*** The per-keyword logging spec

The more general mechanism — applies to *any* keyword, not just done-type ones, and can override ~org-log-done~'s own default on a per-keyword basis. Set via the same parenthesized fast-key syntax after a keyword in ~#+TODO:~, e.g.:

#+BEGIN_SRC
#+TODO: TODO(t) WAIT(w@/!) | DONE(d!) KILL(k@)
#+END_SRC

Four possible markers, each optional, matching real org's own actual grammar exactly:

| Marker | Meaning |
|---+---|
| ~!~ | Log a timestamp when *entering* this state |
| ~@~ | Log a note (prompted for, same panel as ~org-log-done~'s own) when *entering* this state |
| ~@/!~ | Log a note when entering, /and/ a timestamp when *leaving* — conditionally, see below |
| ~/!~ | Log a timestamp only when *leaving* this state — no logging on entering it at all |

The leaving-timestamp forms (~@/!~ and ~/!~) have a real subtlety, matching real org exactly: a leaving-log only fires *if the target state doesn't already log something on its own entry*. Using the example above — ~WAIT(w@/!)~ — switching from WAIT to DONE fires nothing extra from WAIT's own ~/!~, because DONE is already configured to log a timestamp on entry (~d!~); the transition is already covered. But switching from WAIT back to TODO *does* trigger it, since TODO has no logging configured of its own — without WAIT's leaving-log, that transition would go completely unrecorded.

An explicit per-keyword spec always takes precedence over ~org-log-done~'s file-wide default for that specific keyword — ~org-log-done~ only fills in for a done-type keyword that has no spec of its own. Both mechanisms can genuinely fire together for the same transition (a ~CLOSED~ timestamp *and* a ~:LOGBOOK:~ entry), which can look redundant but is how real org itself behaves — they're separate, independent mechanisms that happen to both be configured.

*Fast-access keys* (the single letter before any ~@~ / ~!~, e.g. the ~t~ in ~TODO(t)~) are parsed correctly, so a ~#+TODO:~ line using them doesn't break TODO-state recognition. *A ~#+TODO:~ line with no ~|~ separator at all* treats the last keyword as the sole done state, matching real org's own actual documented rule.

*Multiple, parallel ~#+TODO:~ workflows in one file* (real org's own actual multi-sequence model — e.g. ~#+TODO: TODO(t) | DONE(d)~ followed by a second, separate ~#+TODO: REPORT(r) BUG(b) KNOWNCAUSE(k) | FIXED(f)~ line defines two coexisting workflows, not one overriding the other) are modeled as such. Tap-the-badge (cycling one step at a time) stays within whichever specific sequence a heading's own current keyword already belongs to. Where this surfaces most: tapping a heading's badge (or ~C-c C-t~ — see the keyboard shortcuts table) when it has no current TODO state at all. With just one workflow it behaves exactly as it always has. With more than one, this opens a picker showing every state of every workflow — one row per sequence — letting you jump directly to any state in any workflow, not just choose which one to start in. Each sequence's own first state (where a fresh heading starts) is highlighted in green; its done-type, terminal states are highlighted in red — meaningful since a workflow can wrap onto more than one visual line, so the state that actually ends it isn't always the last button in reading order. *Clear* (reset the heading back to blank) and *Cancel* (dismiss without changing anything) sit below the workflow rows as two distinct buttons. The general editor's own TODO field group (see [[#editing-your-outline][Editing your outline]]) sidesteps needing this picker at all for a heading you're already editing there — every state of every workflow is already laid out as buttons directly, nothing further to pick through.

*** The ~:LOGBOOK:~ drawer

Shown under a heading exactly like ~:PROPERTIES:~ — same visibility rule (gated by the same drawer-visibility flag, hidden by default unless ~#+STARTUP: showeverything~ or the heading is manually swiped fully open), same read-only, tap-to-open-the-action-menu treatment. A state-change entry shows the transition and its timestamp (~WAIT → DONE   [timestamp]~); a note, if one was taken, appears indented and italicized underneath.

Recognized entry formats match real org's own actual default log format exactly (not an invented convention) — including the "from" clause being correctly omitted when there was no previous state, and a multi-line note correctly recognized via the trailing-backslash continuation convention real org itself uses. ~CLOCK:~ lines are recognized structurally (so a file already using real org's clocking commands round-trips cleanly through this app without losing anything) but not acted on — clocking itself isn't built here yet.

*** Agenda: Log

The Agenda screen's date-range line has a *Log* checkbox, off by default — matching real org's own ~org-agenda-log-mode~ convention exactly (a toggle, not always-on, since showing every state change and note by default would clutter a view meant for daily task-scanning). Turned on, every ~:LOGBOOK:~ entry across the aggregated files shows up as its own dated item, interleaved by its own timestamp alongside SCHEDULED/DEADLINE/anniversaries — not clustered separately — with a 📝 icon and the note text shown underneath when there is one. Deliberately shows a DONE heading's own history even though the Agenda's normal view excludes DONE headings entirely — Log mode's whole purpose is seeing what got done, which a heading that's already been filtered out for being done would otherwise never surface at all.

** Archiving
:PROPERTIES:
:CUSTOM_ID: archiving
:END:

Tap a heading's title, then *Archive*, to move the whole subtree to its configured archive location — real org's ~org-archive-subtree~ (~C-c C-x C-s~ / the friendlier ~C-c $~), not just tagging something in place. The moved copy gets ~:ARCHIVE:~ added to its tags and up to six properties stamped on it recording where it came from — matching real org's own actual default ~org-archive-save-context-info~: ~ARCHIVE_TIME~, ~ARCHIVE_FILE~, ~ARCHIVE_OLPATH~ (the titles of its ancestor headings, joined by /), ~ARCHIVE_CATEGORY~, ~ARCHIVE_TODO~ (the heading's own TODO keyword at the moment of archiving, if it had one), and ~ARCHIVE_ITAGS~ (tags /inherited/ from its ancestors specifically, colon-delimited the same way a heading's own tags are — not its own local tags, which stay on the heading exactly as they were; omitted entirely when there's nothing inherited to record, rather than an empty value). ~ARCHIVE_TIME~'s own value is written as bare text — ~2026-07-20 Mon 14:32~, not wrapped in square brackets or angle brackets the way an ordinary org timestamp is, matching real org's own actual mechanism. The original is only removed from the current file after the move to its destination has actually succeeded — a network failure or permission problem leaves the heading exactly where it was, with a clear error shown, rather than losing it.

*Confirmation*: tapping *Archive* always shows a prompt naming the actual destination, with three choices rather than a plain OK/Cancel: *Refile…* opens the [[#refile][Refile]] picker instead, for when the actual destination isn't the archive location specifically; *Cancel* leaves everything untouched; *OK* proceeds with the archive exactly as described above. Once the move actually completes, the status line reads ~--- Archive complete.~

*Where things get archived to* is controlled by ~org-archive-location~, checked in the same priority order real org uses: a heading's own ~ARCHIVE~ property first, then the file's ~#+ARCHIVE:~ keyword, then the default ~"%s_archive::"~. The value is two parts joined by ~::~:

- *File part* (before ~::~) — the destination file. ~%s~ becomes the current file's own name, extension included (~notes.org~ → ~notes.org_archive~, matching real org's own well-known convention for the default). Left empty, archiving happens within the /current/ file instead of a separate one.
- *Headline part* (after ~::~) — a heading to file entries under, e.g. ~* Archived Tasks~ (level 1) or ~** Finished Tasks~ (level 2 specifically — the asterisk count is the target's own real, intended level, matching real org's own actual documented behavior exactly: its own example, "basement::** Finished Tasks", archives "as level 3 trees below the level 2 heading"). Left empty, entries go to that file's top level. Searched for anywhere in the target file, not only at its own top level, since a level-2+ target could itself be nested under some other heading already. A multi-segment "A/B"-style outline path isn't a real org-archive-location feature at all — the only documented "/" usage is the unrelated, special ~datetree/~ prefix (a wholly different date-tree mechanism, not supported here), not a general multi-level path syntax.

| Location | Behavior |
|---+---|
| ~%s_archive::~ (default) | Sibling file ~notes.org_archive~, top-level entries |
| ~::* Archived Tasks~ | Same file, filed under a top-level ~* Archived Tasks~ heading (created if it doesn't exist yet) |
| ~~/org/archive.org::~ | One central file, top-level entries |
| ~~/org/archive.org::* %s~ | One central file, filed under a heading named after the source file |

Set ~#+ARCHIVE: location~ at the top of a file to apply it to every heading in that file, or an ~:ARCHIVE:~ property on a specific heading to override it for just that subtree.

*Platform limitation, stated plainly rather than silently failing*: archiving to a /different/ file only works automatically on GitHub and WebDAV, which can read/write an arbitrary path directly. A local file (opened via File System Access) or an iOS import can't — the browser's own security model requires an explicit file picker gesture per file, which can't happen silently mid-archive. Attempting a cross-file archive on those backends shows a clear message instead of a confusing low-level permission error, and archiving /within/ the current file (an empty file part, e.g. ~::* Archived Tasks~) works everywhere regardless of backend.

*** Restoring (unarchive)
:PROPERTIES:
:CUSTOM_ID: restoring-unarchive
:END:

Open the archive file itself — the *File → Open* browser now shows ~_archive~ files alongside ~.org~ ones (🗄️ icon), so there's no need to already know or type the exact filename — and tap the archived heading's title. Its properties record exactly where it came from, so the action row shows *Unarchive* (📤) in place of Archive: tap it, and the heading moves back to its original file and location, ~:ARCHIVE:~ and every ~ARCHIVE_*~ property stripped, with its ~ARCHIVE_TODO~ (if it recorded one) restored as the heading's own live TODO state again.

Always confirms first (naming the actual destination this time — where it's going /back/ to), and the same *write-before-remove transaction safety*: the destination is written first, and the archived heading is only removed from the archive file once that write has actually succeeded — a network failure can't lose it partway through. Success shows ~--- Restore complete.~ A heading tagged ~:ARCHIVE:~ by hand (or via an earlier version of this app's own in-place tag toggle) with no recorded ~ARCHIVE_FILE~ has nowhere on record to go back to — restoring it just strips the tag and properties in place, at the top level of whichever file it's currently in, rather than guessing.

There's no separate "browse the archive and restore something without opening it" list view — restoring is done from within the archive file itself, the same action-row interaction as everything else in this app.

*** Refile
:PROPERTIES:
:CUSTOM_ID: refile
:END:

Tap a heading's title, then *Archive*, then *Refile…* on the confirmation prompt (see [[#archiving][Archiving]]) — not a separate action-menu button of its own — to move the whole subtree somewhere else in the outline (or a different file entirely): real org's own ~org-refile~. Not shown for a heading that's currently archived in place, the same restriction Archive/Unarchive itself already has there — every other heading always has this route available, since Archive's own confirm prompt always shows.

*Which headings are offered as destinations* is controlled by ~org-refile-targets~ (see [[#local-variables][Local Variables]] for where to set it, and [[#configuration][Configuration]] for how Global vs. Local Variables precedence works for it — there's no ~#+STARTUP:~ layer for this one, real org has none either). Left unset, the default matches real org's own documented nil-behavior exactly: the current file only, level 1 (top-level) headings only.

Real org's actual variable is a Lisp list of cons cells — not something a single plain-text line can hold directly — so this app translates it into semicolon-separated entries, each ~<file> <level-spec>~:

#+BEGIN_SRC
org-refile-targets: current maxlevel=3; notes.org maxlevel=2; agenda-files level=1
#+END_SRC

- *File* is one of ~current~ (this file only, org's own ~nil~), ~agenda-files~ (every configured [[#agenda][Agenda File]], org's own ~org-agenda-files~ symbol), or any other name — resolved exactly the same way a Capture Template's own target file is: a bare name with no ~/~ resolves as a sibling of the current file, a path containing ~/~ is used as-is.
- *Level spec* is ~maxlevel=N~ (that level and shallower) or ~level=N~ (exactly that level) — required on every entry once the variable is set at all, matching real org's own stricter requirement there; an entry missing one is skipped rather than guessed at.

The picker shows every matching heading's full outline path (~Projects / Alpha / Backlog~, not just the bare title) for disambiguation, matching real org's own completion-candidate convention — and across every configured file at once when more than one is in scope, labeled with its own filename when that file isn't the one currently open. The heading actually being refiled, and everything underneath it, never appears in its own candidate list — moving something into its own descendant would corrupt the outline, and real org refuses this too.

Picking a target moves the subtree to become that heading's *last* child — real org's own default insertion point — with every level in the moved subtree adjusted to match its new depth, the same mechanism promote/demote already use. Same-file is an in-memory move; a different file uses the identical *write-target-before-remove-from-source* transaction safety Archive already established (see above) — a failed write leaves the source completely untouched — and the same platform limitation: automatic cross-file refiling works on GitHub and WebDAV, but a local file needs to have been opened/picked at least once first, for the same File System Access security reason Archive states plainly rather than failing silently.

Not built: ~:tag~ / ~:todo~ / ~:regexp~-based target matching (only ~:level~ / ~:maxlevel~ are supported), a most-recent-targets history, and creating a brand-new heading as the destination by typing a name that doesn't exist yet — picking from the existing outline is the only way in.

** Attachments
:PROPERTIES:
:CUSTOM_ID: attachments
:END:

This app's own extension — inspired by real org's own ~org-attach~, though its exact folder-splitting convention isn't independently verified here beyond the well-known general shape (an ID split into a short directory prefix plus the rest, so attachments don't all pile into one enormous folder).

A heading's own action menu has a 📎 *Attach* action — tapping it opens a choice of five (this app's own extension beyond real org-attach's own actual ~a~ / ~o~ / ~d~ menu — recording audio in-browser, and the distinction between opening/viewing an attachment versus saving it to the device, aren't real org-attach concepts at all, added here since both are genuinely useful and the underlying mechanisms are entirely feasible):

- *📎 Attach a file* (real org's own ~org-attach-attach~) — picks any file, including gallery/library media or the camera (most mobile browsers' own general file-picker sheet offers the camera as one of its own options right alongside Photos/Files, so there's no separate, dedicated camera-only entry here — one picker covers both). The first time a heading gets an attachment at all, a fresh, random ~:ID:~ property is generated and stored (reused for every later attachment on that same heading, so they all land together); the picked file is uploaded to ~<the current document's own directory>/data/<id's first 2 characters>/<the rest of the id>/<filename>~ — relative to wherever the *document itself* actually lives, matching real org-attach's own actual convention, not always the repo/server root regardless of the document's own location — and a real ~attachment:~ link — real org-attach's own actual link type — is appended to the heading's own body. A document at ~org-pwa/foo.org~ gets its own attachments under ~org-pwa/data/...~; one at the repo/server root uses a bare ~data/...~, unchanged from before.
- *🎤 Record audio* — this app's own extension, not a real org-attach concept at all: records straight from the microphone using the browser's own real, native ~MediaRecorder~ API (a genuine capability, well-supported across current Chrome/Firefox/Edge/Safari, including iOS Safari since 14.3 — the same HTTPS-only, explicit-permission-prompt requirement every other camera/mic-adjacent feature in this app already has). A small panel walks through recording (a live elapsed-time readout while it's running), then review — real playback of exactly what was just recorded, so a mistake can be caught and re-recorded before ever being uploaded, not after. Saving uploads it through the exact same path as any other attachment. The actual recorded format genuinely differs by browser — Chrome/Firefox/Edge produce ~audio/webm~, Safari ~audio/mp4~ — so the filename's own extension (auto-generated as ~recording-YYYY-MM-DD-HHMMSS.<ext>~, since a fresh recording has no name of its own the way a picked file does) is derived from whichever format the browser actually chose, not a single fixed one.
- *📂 Open* — tries to actually *view* the heading's own current attachment, opening a new tab with the browser's own native viewer: a PDF's own built-in renderer, native video playback, plain text shown as-is, or (matching this app's own already-existing image/audio capability elsewhere) an ordinary raster image or audio file. Falls back to downloading it instead (the same thing Save below always does) only when there's genuinely no native viewer for that file type — a confirmed, deliberate fallback, not a silent failure, with its own clear status message either way. Two file types are deliberately left out of "viewable" even though a browser could technically render them: HTML and SVG, since opening either via direct navigation would actually execute any script embedded in the file — a real, meaningfully different risk from a PDF/video/image/audio file's own safe, non-executable playback, or this app's own existing, safe inline SVG display (which uses an ~<img>~ tag specifically, since that never executes embedded scripts regardless of content). ~.webm~'s own genuine ambiguity (a legitimate container for both audio-only and audio+video content) is resolved by actually reading the file's own real content — its own EBML/Matroska container structure declares each track's own real type, the same information a real media player already relies on, rather than continuing to guess from the extension alone (extension-based guessing still exists as this app's own fallback default, favoring audio to match this app's own in-browser recording feature, for the rare case where a file's own structure can't be read at all). ~.mp4~ stays video unconditionally, with no need for the same content check: a recorded audio/mp4 file is always named ~.m4a~ specifically, precisely to avoid this exact ambiguity, so a literal ~.mp4~ attachment is essentially always a real video file. With no attachments at all, a clear message says so rather than opening an empty picker; with exactly one, it acts directly, no extra tap needed; with more than one, a prompt asks which file first, matching real org-attach's own actual documented behavior for this exact case.
- *💾 Save* — downloads the heading's own current attachment to the device, unconditionally, regardless of file type (the same "which file, if more than one" picker Open above uses). This is what Open itself used to do before it was changed to try viewing first — Open trying to view isn't a replacement for being able to actually save a copy, so both exist as clearly separate, intentional actions now.
- *🗑️ Delete* (real org's own ~org-attach-delete-one~) — the same "prompt if more than one" selection Open/Save above use, then a confirmation, then removes *both* halves at once: the actual file on GitHub/WebDAV, and the ~[[attachment:...]]~ link referencing it in the heading's own body. The backend delete happens first — if that fails, the in-document link is left alone too, rather than the app believing something's gone that's actually still sitting on the server.

Tapping an ~attachment:~ link directly in a heading's own body (rather than going through the Attach menu at all) does the same thing Open does — tries to view it, falling back to download only when there's no viewer.

*An attached image displays inline, the same as any other image in this app* (see [[#links-and-images][Links and images]]) — a bare ~[[attachment:photo.jpg]]~ with no description, matching real org's own actual "no description = inline image" convention exactly (adding a description turns any image link into a plain, named, non-displayed link instead — org's own behavior, not specific to attachments). Recognized image extensions include ~.heic~ / ~.heif~, the default photo format on modern iPhones, alongside the usual ~.png~ / ~.jpg~ / ~.gif~ / ~.svg~ / ~.webp~ / ~.bmp~ — though actual HEIC *rendering* support still depends on the browser viewing it (Safari/iOS renders it natively; desktop Chrome/Firefox generally don't), a browser capability gap rather than something this app's own link handling controls.

*An attached audio file gets its own inline playback UI*, rather than either the image treatment above or a plain download link — a compact "▶️ filename" button that, once tapped, fetches the actual bytes (lazily — only once actually tapped, unlike an image's own eager inline fetch, since an audio recording is often considerably larger and there's no reason to pull it down before someone's actually asked to hear it) and expands into a real, native browser ~<audio>~ player: play/pause, and a scrubber for moving forward and backward through the recording, both genuinely native, not a hand-built equivalent. Recognized audio extensions cover both what this app's own recording feature actually produces (~.webm~, ~.m4a~) and common existing audio files someone might attach directly (~.mp3~, ~.wav~, ~.ogg~, and a few others).

A non-image, non-audio attachment (a PDF, a document, anything else) keeps the filename as its own visible description — ~[[attachment:notes.pdf][notes.pdf]]~ — and tapping it opens a new tab with the browser's own native viewer for anything Open (above) would recognize as viewable (a PDF, for instance), or downloads it when there's no such viewer.

An ~attachment:~ link resolves against whichever heading's own ~:ID:~ actually owns the attachment directory — the heading it's written in first, or (matching real org-attach's own actual inheritance) the nearest ancestor's ~:ID:~ if the heading itself doesn't have one of its own. A hand-written ~attachment:~ link under a heading with no ~:ID:~ anywhere in its own ancestor chain has nothing to resolve against, and shows as a broken/unresolved link rather than guessing.

*Only works with GitHub or WebDAV connected* — the same reasoning [[#agenda][Agenda Files]] and cross-file [[#archiving][Archive]]/[[#refile][Refile]] already established: writing a brand-new file, reading one back, or deleting one all need a backend that can do that without a fresh picker gesture first, and a local (File System Access) or iOS-import file has no equivalent capability. Tapping Attach without one of those two connected shows a clear explanation rather than attempting something that can't succeed — the action itself is always visible (not hidden depending on the current backend), so its own error message is what explains the limitation rather than the option quietly not being there at all.

Two backend-specific reliability details: *(GitHub)* a file larger than 1MB — an ordinary camera photo easily exceeds this — is read back correctly via GitHub's own Blobs API (a much higher 100MB ceiling), since GitHub's own Contents API only inlines a file's content directly for anything under that size. *(WebDAV)* every intermediate folder in an attachment's own path is created automatically before the write, since a real WebDAV server requires each one to already exist first — unlike GitHub's git-based storage, where a "folder" is just a path prefix with nothing to separately create.

Attaching a file doesn't re-download the exact bytes it just finished uploading — the newly-attached image (if inline images are on) uses the already-uploaded bytes directly, rather than being fetched a second time purely to display what's already sitting in memory.

A picked filename is lightly sanitized first — path separators and a few other characters that would be meaningful (or simply illegal) within a storage path get replaced with an underscore — but is otherwise used as-is, including spaces; a name that ends up entirely empty after sanitizing falls back to the literal name "attachment" rather than an empty path segment.

*A filename that collides with something already attached to the same heading is automatically disambiguated* — "-1" inserted before the extension, then "-2", and so on, until landing on a name that's actually free. This matters more than it might sound: many camera apps, on both iOS and Android, hand back the exact same generic filename (commonly "image.jpg") for every single photo or video captured — not a rare edge case, the everyday default. Since an attachment's own storage path is derived purely from the heading's own ~:ID:~ plus the filename, attaching a second capture with an identical name would otherwise silently overwrite the first one's actual file content at that same path — both links in the document ending up pointing at whatever was uploaded last, with no error or warning at all. Two separate captures named "image.jpg" now become ~[[attachment:image.jpg]]~ and ~[[attachment:image-1.jpg]]~, each with its own genuinely distinct storage path.

*Not built*: ~org-attach-dired~-equivalent bulk operations (drag-select several attachments at once) — Delete above handles one at a time; and any *browsing* view independent of a specific heading's own action menu — there's no single "every attachment across the whole file" list, only what Open/Delete's own picker shows for whichever heading you're currently acting on.

** Clocking
:PROPERTIES:
:CUSTOM_ID: clocking
:END:

A heading's own action menu has a clock toggle — ▶️ *Clock in* / ⏹️ *Clock out* — in the slot "Add table" used to occupy (moved to the general editor instead — see [[#editing-your-outline][Editing your outline]]). Only one heading can have a running clock at a time within this app's own UI, though a hand-edited file with more than one running ~CLOCK:~ line round-trips fine; the toggle itself just reflects whichever heading it's currently showing for.

*org-clock-in* inserts a bare ~CLOCK: [timestamp]~ line marking the start of a clocking session. Tapping it again while already running on the *same* heading is a no-op — real org itself doesn't let you double-start the same clock either, it just continues the existing session. Tapping it on a *different* heading while another one's clock is running auto-clocks-out that previous one first, at the exact same moment the new one starts (no gap between them), matching real org's own actual behavior — only one clock can ever meaningfully be "the current task" at a time.

*org-clock-out* / *org-clock-cancel*: tapping *Clock out* again while a clock is running no longer stops it directly — it shows a prompt with three choices. *Stop* is the normal completion (~org-clock-out~): replaces the bare ~CLOCK: [timestamp]~ line with ~CLOCK: [start]--[end] =>  H:MM~, computing the duration from the two actual timestamps. *Cancel* is ~org-clock-cancel~: discards the running session entirely — the ~CLOCK:~ line is removed outright, as if it had never been started, no duration ever recorded. Used for a clock started by mistake, or switching to something completely different without wanting the elapsed time logged. *OK* just closes the prompt and leaves the clock running, untouched. Tapping Clock out with nothing running at all is still a no-op, same as before.

*One deliberate simplification, stated plainly*: real org keeps a heading's very first ~CLOCK:~ line bare, directly under the heading, only wrapping it (and every subsequent one) into a ~:LOGBOOK:~ drawer once a *second* clocking happens. This app's own LOGBOOK handling was already unified into always using the drawer from the start (see [[#progress-logging][Progress logging]]) — clocking follows that same established convention rather than reintroducing the bare-line special case just for this one thing.

*org-clock-display*: a *Clock* checkbox on *View → TODO* (the same style and placement as Agenda's own *Log* checkbox — see [[#agenda][Agenda]]) shows each item's total clocked time next to its title — real org's own "all time ever clocked in for this task and its children," including every descendant's own sessions, and a currently-running clock's own elapsed-so-far time counted too, not just completed sessions. Off by default, matching real org's own actual behavior (an on-demand command, ~M-x org-clock-display~, not something always shown) rather than a persisted setting — this is a plain in-session UI toggle, not a Global/Local Variable.

*org-clock-report* — a real ~#+BEGIN: clocktable ... #+END:~ dynamic block, computed for a date range and shown read-only in *View → TODO*'s own *Clock report* section. See [[#the-todo-view][The TODO view]] for the full behavior.

*What's not built*: a persistent mode-line/status-bar display of the currently-running clock; clock-continue (resuming the most recently-clocked task); and effort estimates / clock-in reminders tied to them. See [[#differences-from-emacs-org-mode][Differences from Emacs org-mode]].

** The plain-text editor
:PROPERTIES:
:CUSTOM_ID: the-plain-text-editor
:END:

Tap *View → Text* to switch the entire outline view for one full-width textarea containing the whole document as raw org text — everything, including ~#+STARTUP:~, ~#+TODO:~, a [[#local-variables][Local Variables]] block, and any syntax the structured view still doesn't have dedicated UI for (editing block content, changing the ~#+TODO:~ sequence itself). Tap *View → Org* to switch back; the text is reparsed from scratch at that point, so any changes — including to ~#+STARTUP~ / ~#+TODO~ /Local Variables — take effect immediately, correctly mark the document as modified, and persist the same way every other edit does — a genuine text change here is exactly as durable as tapping a heading's own title to edit it.

*Switching in lands near wherever you last navigated to*, not always the top of the file — tap a search result or an internal link, then switch to Text, and the cursor and scroll position land at that same heading's line rather than losing the context you just found. This only tracks explicit "jump to X" navigation (search, internal links, agenda items), not manual scrolling within the outline; scroll around on your own and switch to Text, and it opens at the top as before. The scroll position itself is an approximation (proportional to the target line's position in the file), not a pixel-exact one — a wrapped line's real rendered height varies with content, so "near the same line" is the actual guarantee here, not perfect alignment.

*Select All* and *Copy All* buttons sit above the textarea — selecting or copying an entire long document via the native mobile drag-handle gesture (long-press somewhere, then drag two handles across potentially thousands of lines) is painful enough that a one-tap alternative is worth having, rather than requiring a selection to already be underway before the device's own "Select All" bubble becomes reachable at all. *Select All* selects the full text in place — the device's own native Copy still works normally from there. *Copy All* goes one step further, writing the full text directly to the clipboard without needing a manual selection step at all; if the browser's clipboard API is unavailable or denied (a non-secure context, or permission refused), it falls back to selecting the text instead, so there's always a way forward rather than a silent failure. Keyboard ~Ctrl-A~/~Cmd-A~ already works natively inside the textarea regardless — these buttons are specifically for reaching the same thing without a physical keyboard.

This is the escape hatch for everything the tap-driven UI doesn't cover yet.

** Agenda
:PROPERTIES:
:CUSTOM_ID: agenda
:END:

Tap *View → Agenda* for a list of everything with a date attached, grouped into Day, Week, or Month views. A single toggle button cycles between the three on tap — fixed-width, so it never shifts size as the label changes — rather than three separate buttons competing for space. *‹*/*›* step the view backward or forward by whatever unit is currently active — a day, a week, or a month — and *Today* jumps back to the current date. Tapping an item switches back to the Org view and scrolls straight to it.

*The `g` button toggles `org-agenda-show-all-dates` on the fly*, matching real org's own `g` keybinding exactly — an ephemeral, in-session toggle, not a permanent change to anything in a file. By default every day shows, even ones with nothing scheduled on them (a full 7-day week, every day of the month). Press `g` to hide empty days entirely instead — a light month can shrink from 30-odd days down to just the handful that actually have something on them; a Week view might end up showing only "Monday" and "Thursday"; a Day view landing on a completely free day shows nothing at all rather than an empty header. `g` bolds itself while active (hiding empty days) as a reminder the view is in its non-default state. The file's own persistent starting value for this (what `g` starts from each time Agenda is freshly opened) is configurable via [[#local-variables][Local Variables]] or the *Show empty days in Agenda* Quick Settings field — real org's own default is to show every day, matching what this app already does unless that's explicitly turned off.

*Week view always aligns to an actual calendar week* — Monday through Sunday by default (configurable, see below), regardless of which day of that week you happened to open the agenda on. It resolves to the same 7-day window whether you're looking at it from Monday or Friday, not "whatever day is currently open, plus the next six." Every day of the week shows by default, even a fully free one with nothing scheduled on it — a week view is a fixed 7-day skeleton, not a list that shrinks to just the days something happens to land on, unless `org-agenda-show-all-dates` has been turned off (see the `g` button above). Each day's own header shows its ISO 8601 week number wherever that day is the start of its own week — the first day for Week view (always Monday, or whichever weekday is configured), every such day within the month for Month view, and always for Day view (only one day is ever shown, so there's no repetition to worry about). The overall range label above the day list also shows the week number(s) the current view spans — a single ~(W36)~ for Day/Week, or the full range (e.g. ~(W31-W36)~) for Month — matching real org-agenda's own buffer title line exactly.

*Every item shows a category prefix* — real org-mode's own ~#+CATEGORY:~ file keyword if a file sets one, otherwise that file's own name (no directory path, no ~.org~ extension) as the implicit default, matching real org's actual behavior exactly. ~#+CATEGORY:~ goes at the top of a file, before any headings:

#+BEGIN_SRC org
  ,#+CATEGORY: Projects
  * TODO Review weekly goals
    SCHEDULED: <2026-09-07 Mon>
#+END_SRC

*Timed entries can carry a time range*, real org syntax on any SCHEDULED/DEADLINE/plain timestamp: ~SCHEDULED: <2026-08-31 Mon 08:00-09:00>~. Week and Month views show a range as ~08:00-09:00~; a single time with no range shows as ~08:00 ……~ (trailing dots, not a bare number, so a quick glance can tell "this has a specific start but no stated duration" from "this is a range" at the format level, not just by reading closely). An untimed SCHEDULED/DEADLINE item shows its own ~Scheduled:~ / ~Deadline:~ label instead of any time at all.

*Day view additionally shows an hour-by-hour time grid*, matching real org's own ~org-agenda-time-grid~ default exactly — dashed marker lines every two hours from 8am to 8pm. Untimed items (SCHEDULED/DEADLINE with no time component) list first, above the grid entirely; timed items — real org's own actual convention here too — are interleaved with the grid lines in chronological order, appearing right where their own time falls between two markers, so the whole day's shape (what's free, what's packed) is visible at a glance rather than only wherever something happens to be scheduled. Week and Month views intentionally do NOT show this grid — real org's own agenda reserves the hourly timeline for Day view specifically, with Week/Month staying a flat per-day list.

*** Dated entry sources
:PROPERTIES:
:CUSTOM_ID: agenda-dated-entries
:END:

Five kinds of dated entry show up, and *they behave differently from each other in an important way* — this is real org-mode semantics, not an app-specific choice:

- ~SCHEDULED:~ — when you intend to do something. Shows on its date, and if the heading isn't marked done, *keeps reappearing on every day after that* (as overdue) right up through today, until you mark it done. This is what makes "I meant to do this last week and never did" actually visible instead of quietly vanishing off the agenda the day after its original date. The overdue count shows directly on the item ("3 days overdue"). It also supports a *delay* suffix (real org syntax: ~SCHEDULED: <2026-01-10 Sat -2d>~) — the *opposite direction* from DEADLINE's own delay suffix below: it doesn't show at all until the delay has actually elapsed, not even on its own literal date, let alone before it.
- ~DEADLINE:~ — same carry-forward behavior as SCHEDULED once the date passes with the heading still not done. It also supports a *delay/warning-period* suffix (real org syntax: ~DEADLINE: <2026-01-10 Sat -3d>~), which makes it start appearing /before/ its date too — 3 days early in that example, showing "due in 3 days," counting down each day until it either gets marked done or becomes overdue (at which point it switches to counting up instead). *Without an explicit suffix, a DEADLINE still starts appearing ~org-deadline-warning-days~ before its date* — real org's own actual default is *14*, not "only on its date." Configurable via [[#local-variables][Local Variables]]; an explicit per-deadline suffix always overrides this file-wide default for that specific heading.
- *A plain, active timestamp written directly in a heading's title* — the standard org convention for tracking something like a recurring birthday right on its own heading line (~**** Jane Doe <2000-01-01 Sat +1y>~), a genuinely separate source from SCHEDULED/DEADLINE, not a fallback for it. This one does *not* carry forward, ever, regardless of done status — matching real org's own distinction ("if you didn't go to your doctor's appointment yesterday, that doesn't mean you still have one today"). Only counted when the heading has no SCHEDULED/DEADLINE of its own (to avoid a confusing double entry), and only /active/ ~<...>~ timestamps count — an inactive ~[...]~ one is excluded, same reasoning: a dated record, not a reminder. This only looks at the title, not body text, to avoid pulling in unrelated dates mentioned in ordinary prose elsewhere in a journal-heavy file.
- *A general ~<%%(sexp)>~ timestamp*, in that exact same title position — real org's own general sexp-timestamp mechanism, evaluated fresh per day rather than one literal date, and (like the plain timestamp above) never carrying forward and only counted when the heading has no SCHEDULED/DEADLINE of its own. See [[#agenda-sexp-timestamps][General <%%(sexp)> timestamps]] below for the full syntax, the small expression evaluator behind it, and worked examples.
- ~org-contacts-anniversaries~ — real org-contacts' own mechanism for recurring yearly events (birthdays, anniversaries), read directly from a heading's own property rather than a separate, duplicated line of text — one source of truth for a date you might also want recorded as a property for other reasons (vCard export, contact lookup). A contact heading gets a property (default key ~BIRTHDAY~, matching real org-contacts' own default exactly — configurable via [[#local-variables][Local Variables]]) formatted ~YYYY-MM-DD Description~:

#+BEGIN_SRC org
  * John Doe
  :PROPERTIES:
  :BIRTHDAY: 2000-01-01 Birthday
  :END:

  * Mary & John Doe
  :PROPERTIES:
  :BIRTHDAY: 2000-06-15 Wedding Anniversary
  :END:
#+END_SRC

  Placing the trigger line ~%%(org-contacts-anniversaries)~ anywhere in the file activates the scan — its own position doesn't matter beyond "present somewhere"; it's a switch, not itself an event, so it's usually placed under its own heading (~* Anniversaries & Birthdays~) purely for organization. Every heading anywhere in the file carrying the configured property gets checked, producing a line like ~John Doe: Birthday (26)~ — the age is computed fresh for whichever year's occurrence is being shown, so the same entry correctly shows a different number across a multi-year Month or Week view, not one age frozen in. ~YYYY~ can be the literal word ~nil~ when the actual year isn't known — the age then can't be computed, and ~(??)~ is shown instead of a number, exactly as asked for rather than a bare dash or omitting the parentheses. Shown with a 🎂 icon in the agenda to tell it apart from the other three kinds at a glance. A heading with the property in an unparseable format, or no description text after the date, is silently skipped rather than erroring — an empty scan result and a broken one are treated the same way here, since there's no per-item feedback channel in an agenda list to report a parse failure through.

  Does *not* require an ~:EMAIL:~ property to count as a valid contact, unlike real org-contacts' own default — requiring it here would silently exclude anyone whose birthday is tracked without an email on file.

*** Diary-sexp forms
:PROPERTIES:
:CUSTOM_ID: agenda-diary-sexp
:END:

  *Ten more diary-sexp forms* are supported too, each a self-contained, per-line entry (unlike ~org-contacts-anniversaries~' own trigger-line-plus-property mechanism above — no separate switch line needed; each of these appears exactly where it's meant to trigger, anywhere in a heading's body, shown with a 🔁 icon except the solar ones' own ☀️):

  - ~%%(org-anniversary YEAR MONTH DAY) description text~ — real org's own diary-anniversary-based mechanism, e.g. ~%%(org-anniversary 1956 5 14) Arthur Dent is %d years old~. The file author writes the description text directly, with ~%d~ substituted for the elapsed years and an optional ~%s~ substituted for that same number's own ordinal suffix ("st"/"nd"/"rd"/"th") — ~%%(org-anniversary 2001 6 12) %d%s wedding anniversary~ shows "25th wedding anniversary" in year 2026. February 29 is treated as March 1 in a non-leap year, matching real diary-anniversary's own special case.
  - ~%%(org-cyclic N YEAR MONTH DAY) description text~ — flags the agenda every ~N~ days starting from the given baseline date (never before it). ~%%(org-cyclic 14 2026 1 1) Water the succulent~ shows up every two weeks starting January 1, 2026.
  - ~%%(diary-float MONTH DAYNAME N [DAY] [YEAR]) description text~ — the /n/-th occurrence of a weekday within a month: ~MONTH~ is 1-12, a parenthesized list of them (~(1 4 7 10)~ for quarterly), or the literal ~t~ for every month; ~DAYNAME~ is 0 (Sunday) through 6 (Saturday); ~N~ counts forward from the start of the month when positive, backward from its end when negative (~-1~ is the last occurrence, ~-2~ the second-to-last). ~%%(diary-float 11 4 4) Thanksgiving~ is the U.S. holiday's own actual real-world definition (the 4th Thursday in November) and correctly lands on November 26 in 2026. An optional ~DAY~ resets the search window's own starting point instead of the month's default first/last day — ~%%(diary-float 11 2 1 2) US Election Day~ finds the 1st Tuesday in November but starts scanning from the 2nd, correctly skipping a Tuesday that happens to land on the 1st; an optional trailing ~YEAR~ restricts the whole entry to that one specific year, blank in every other.
  - ~%%(org-block YEAR1 MONTH1 DAY1 YEAR2 MONTH2 DAY2) description text~ — flags every day in an inclusive range between two dates, written in either order. ~%%(org-block 2026 6 1 2026 6 5) Beach vacation~ shows up on the agenda for all five days.
  - ~%%(diary-sunrise)~, ~%%(diary-sunset)~, ~%%(diary-civil-dawn)~, ~%%(diary-civil-dusk)~, ~%%(diary-nautical-dawn)~, ~%%(diary-nautical-dusk)~, ~%%(diary-astronomical-dawn)~, ~%%(diary-astronomical-dusk)~ — this app's own extension, computed from ~calendar-latitude~ / ~calendar-longitude~ (default the coordinates for *Durham, NC*, configurable via [[#local-variables][Local Variables]] or the device-location button in Quick Settings) using the standard NOAA solar-position formulas. Each is a self-contained line showing "06:30 Sunrise", "20:15 Sunset", "06:02 Dawn", "20:43 Dusk" by default — 24-hour, zero-filled time. The three dawn/dusk pairs are the sun crossing progressively deeper below the horizon: *civil* at 6°, *nautical* at 12°, *astronomical* at 18° — each pair's own "Dawn"/"Dusk" label is identical regardless of which one, since the twilight KIND is what the function name itself already says. ~n/a~ shows in place of the time for whichever one doesn't occur that day (a "white night" at high latitude, where the sun dips low enough to set but never all the way to that particular angle below the horizon — more likely for nautical/astronomical than civil, since they're deeper angles). Two of this app's own extension variables adjust the output, configurable via [[#local-variables][Local Variables]] or Quick Settings (see [[#settings][Settings]]): ~solar-ampm~ (default ~nil~ — 24-hour) switches to 12-hour am/pm when non-nil ("6:30am Sunrise"); ~solar-hide-label~ (default ~nil~ — label shown) omits the trailing label entirely when non-nil, leaving just the bare time ("06:30"). Both combine freely.
  - ~%%(diary-day-length)~ — this app's own extension, total daylight duration (sunset minus sunrise, for the same day and location) as "13:32 daylight" — 24-hour, zero-filled ~HH:MM~, since this is a *duration*, not a time-of-day. ~solar-ampm~ has no effect on this one — there's no am/pm distinction for a duration — but ~solar-hide-label~ still applies, leaving a bare "13:32". At a latitude experiencing true polar day or polar night, this correctly shows "24:00 daylight" or "00:00 daylight" rather than ~n/a~ — a day-length total is always well-defined even when there's no sunrise or sunset to report.
  - ~%%(org-weather)~ — this app's own extension: live current-conditions-plus-today's-forecast data from the [[https://open-meteo.com/][Open-Meteo]] API (free, no API key required). Uses the same ~calendar-latitude~ / ~calendar-longitude~ the solar forms above read. Shows the *last-fetched* snapshot — refreshing (manual or automatic, see below) is a separate action from viewing it. Only generates a single agenda entry, on today's own actual date, however wide the queried view. No entry at all until the first successful refresh.

    ~org-weather-format~ controls the displayed text — default ~"Weather: %desc, %tcur(%tmin-%tmax)%tu, %p%pu, %h%hu, %s%su, %a%au"~, e.g. "Weather: Overcast, 86.3(75.5-91.8)°F, 1002.8hPa, 49%, 5.1mph, 12m" — with these placeholders: ~%desc~ / ~%icon~ (a text description / emoji from the current WMO weather code; an unrecognized code shows "Unknown weather"/❓), ~%tcur~ / ~%tmin~ / ~%tmax~ (current temperature, today's own low/high), ~%tamin~ / ~%tamax~ (today's own "feels like" low/high), ~%tu~ (the configured temperature unit, ~org-weather-temperature-unit~, default ~°F~), ~%h~ / ~%hu~ (humidity and its own unit, ~%~), ~%p~ / ~%pu~ (surface pressure and its own unit, ~hPa~), ~%s~ / ~%su~ (wind speed, and the configured speed unit ~org-weather-speed-unit~ — ~mph~ default, or ~km/h~ / ~m/s~ / ~Knots~), ~%a~ / ~%au~ (age of the snapshot itself — computed from the data's own reported reading time, not whenever the line happens to render or however stale the last successful fetch actually was — and its own unit letter: ~m~ for 0-59 minutes, ~h~ for 1-23 hours, ~d~ for 1 day or more, switching at the natural boundary rather than ever showing e.g. "65m" once a full hour has actually passed). An unrecognized ~%~-sequence is left untouched. All three variables are also editable directly in Quick Settings, with a reset-to-default option.

    *Refreshing*: Settings has a "Weather" section showing the last-refreshed time, a "Refresh weather now" button, and a note distinguishing whether ~%%(org-weather)~ is used in the current document, used only via an ~org-agenda-files~ entry, or not used anywhere yet — weather integration isn't necessarily tied to whatever document happens to be open; it's just as commonly the Agenda view itself showing it, from a file that isn't the one currently open. Next to that button, on the same line, ~org-weather-refresh-interval~ (this app's own extension, matching the rest of the ~org-weather-*~ family's own naming) sets how often it also refreshes on its own — ~never~ (the default — manual refresh is already one tap away, so nothing happens in the background unless deliberately opted into), or every ~1~ / ~2~ / ~4~ / ~6~ / ~12~ / ~24~ hours. When set, it's checked once when the app opens (the most important check in practice, given a phone-installed PWA is typically opened fresh rather than kept running for hours at a stretch) and every 30 seconds after that — riding the modeline's own existing clock timer rather than a separate one of its own, since the check itself is nearly free (a timestamp comparison, doing nothing further unless a refresh is actually due) and keeps running at that same cadence regardless of whether the modeline's own date/time display (~display-time-mode~) is switched on — refreshing whenever the configured interval has actually elapsed since the last fetch. Only runs at all when ~%%(org-weather)~ is actually in use somewhere relevant (the current document or an agenda file) — never unprompted network activity otherwise. A failed refresh (offline, the API unreachable, a malformed response) leaves whatever was already cached in place. The fetched snapshot persists across restarts.

*** General ~<%%(sexp)>~ timestamps
:PROPERTIES:
:CUSTOM_ID: agenda-sexp-timestamps
:END:

Real org's own general sexp-timestamp form — ~<%%(expression)>~, written directly where a plain ~<timestamp>~ would go (a heading's own title line, right alongside the fixed, whole-line ~%%(...)~ forms above, which this is a different mechanism from). The expression is evaluated once for every day currently being considered, and each day it evaluates to something non-nil, that's an occurrence — a *dynamic matcher*, not a stateful task repeater: marking a heading with a sexp timestamp as DONE has no effect on it, and a sexp timestamp can't be combined with a real repeater suffix in the same brackets, matching real org's own restriction.

#+BEGIN_SRC
* Weekly Sunrise <%%(when (org-cyclic 7 2026 8 9) (diary-sunrise))>
* TODO Team Sync <%%(diary-float t 6 1)>
* Water the plants <%%(org-cyclic 3 2026 1 1)>
* Company Anniversary <%%(org-anniversary 2018 5 14)>
#+END_SRC

A small, non-general expression evaluator — not a real elisp interpreter, just enough to combine the pieces useful here:

- ~(when CONDITION EXPR)~ — evaluates ~CONDITION~; if it's non-nil, evaluates and returns ~EXPR~'s own result; otherwise the whole thing is nil (no match that day). The one control-flow form supported.
- ~(today-p)~ — this app's own extension, *not* a real elisp/org function — shorthand for real org's own idiom ~(equal date (calendar-current-date))~. ~<%%(when (today-p) (diary-sunrise))>~ shows sunrise only on today's own agenda entry, nowhere else.
- ~(org-cyclic N YEAR MONTH DAY)~, ~(org-anniversary YEAR MONTH DAY)~, and ~(diary-float MONTH DAYNAME N [DAY] [YEAR])~ — the same three functions and argument shapes documented above, usable as a genuine sub-expression now (inside a ~when~, as this heading's own entire timestamp on its own, or both). ~(diary-sunrise)~, ~(diary-sunset)~, ~(diary-civil-dawn)~, ~(diary-civil-dusk)~, ~(diary-nautical-dawn)~, ~(diary-nautical-dusk)~, ~(diary-astronomical-dawn)~, ~(diary-astronomical-dusk)~, ~(diary-day-length)~, and ~(org-weather)~ too, with one difference: unlike the other three (which return a plain match/no-match), each of these always returns its own *formatted string* — and whenever an expression's own final result is a string rather than a plain match, that string becomes part of what's displayed (~"Weekly Sunrise: 06:30 Sunrise"~ for the first example above, ~"Civil Dawn Today: 06:02 Dawn"~ for ~<%%(when (today-p) (diary-civil-dawn))>~). ~org-block~ and ~org-contacts-anniversaries~ aren't recognized inside a sexp timestamp — both are tied to their own separate mechanisms (a property scan, an explicit date range).
- ~(format FORMAT-STRING ARG...)~ — real elisp's own function, combining any of the string-returning functions above into one custom line: ~<%%(when (today-p) (format "Rise %s (%s)" (diary-sunrise) (diary-civil-dawn)))>~ shows "Rise 06:30 Sunrise (06:02 Dawn)". Set ~solar-hide-label~ (see [[#agenda-diary-sexp][General diary-sexp forms]]) to get the bare times only — "Rise 06:30 (06:02)". Only ~%s~ is recognized, plus ~%%~ for a literal percent sign. Each ~%s~ recursively evaluates its own corresponding sub-expression — including another ~format~ call, nested arbitrarily deep. An extra, unused argument beyond what the format string's own ~%s~ count needs is ignored; too *few* arguments evaluates to "no match" rather than erroring. A heading whose own title is entirely the ~<%%(...)>~ timestamp itself, with no other text — ~* <%%(when (today-p) (format ...))>~ — shows the result string exactly as ~format~ built it, with no leading title/colon prefix (a plain, non-string match on a title-less heading still shows "(untitled)", but a string result never gets that fallback prepended).
- Anything else — an unrecognized function name, a malformed expression, a bare value not wrapped in a function call — evaluates to "no match" rather than erroring the whole agenda out.

*How this differs from the five fixed forms above*: those five are self-contained, whole-line triggers anywhere in a heading's own *body* (~%%(org-anniversary ...) description text~, no angle brackets, no combining) — this is a real *timestamp*, written in a heading's own *title* (the exact same position a plain ~<2026-01-01>~ title-timestamp already occupies, and mutually exclusive with it the same way SCHEDULED/DEADLINE already exclude the plain-timestamp scan — a heading with SCHEDULED/DEADLINE set doesn't also get scanned for a sexp timestamp in its own title). Skipped over by SCHEDULED/DEADLINE's own carry-forward logic too — like the plain title-timestamp case, a sexp-timestamp match only ever shows on the specific day(s) it actually evaluates true for, never carrying forward as overdue the way an incomplete SCHEDULED does.

*** Other agenda behavior
:PROPERTIES:
:CUSTOM_ID: agenda-behavior
:END:

Other behavior:

- *Completed items are excluded* — using the file's own ~#+TODO:~ sequence (whatever keywords you've actually defined as "done"), not a hardcoded check for the literal word ~DONE~.
- *Repeating timestamps expand properly*, for SCHEDULED/DEADLINE/title-timestamp (the first three sources above — ~org-contacts-anniversaries~ recurs by its own inherent yearly mechanism instead, described above, not this repeater syntax). ~<2000-01-01 Sat +1y>~ shows up every year on the anniversary within whatever range is currently displayed, not just its one literal stored date — switch to Month view and it correctly shows up in whichever month it falls in. Carry-forward, delay, and repetition don't combine — a /repeating/ SCHEDULED/DEADLINE shows on its own repeat dates only, with no additional carry-forward or early-warning between them.

- *Marking a repeating task done shifts it instead of finishing it* — real org's own actual behavior, and a genuinely different mechanism from the agenda-display expansion just above: completing a heading whose SCHEDULED and/or DEADLINE carries a repeater doesn't leave it done. Its date shifts forward by the repeater's own interval, ~LAST_REPEAT~ is stamped with the moment this happened, and the heading's TODO state bounces immediately back to the first keyword in the sequence — the task stays alive and recurring rather than actually completing. The three repeater marks genuinely behave differently here, not just cosmetically different syntax: ~+N~ (cumulate) adds one interval to the *previous* date, even if the result is still in the past — miss several occurrences in a row and marking it done that many times in a row is what catches it up; ~++N~ (catch-up) adds the interval repeatedly *from the previous date* until the result lands in the future, landing on the same day-of-week/time-of-day the timestamp always had; ~.+N~ (restart) bases the new date on *today* — whenever the task was actually completed — plus one interval, ignoring the old date's own position entirely. The original DONE transition is still logged normally (a ~CLOCK~-note, a ~CLOSED~ timestamp per whatever's configured); the automatic bounce-back itself isn't logged as a second, separate transition, matching real org's own actual behavior, though any ~CLOSED~ timestamp that was just inserted is removed again, since the heading isn't actually staying done.
- Archived headings are excluded, same as everywhere else in the app.
- *Commented headings are excluded too* — a heading whose title starts with ~#~ followed by a space (or is just ~#~ alone), real org's own comment-line convention applied to a heading title (e.g. ~** # draft, not ready yet~). Both this and archived-heading exclusion are configurable via [[#local-variables][Local Variables]] (~org-agenda-skip-comment-trees~ / ~org-agenda-skip-archived-trees~), matching real org's own two separate settings for this.
- *Week view's start day is configurable* via ~org-agenda-start-on-weekday~ in a [[#local-variables][Local Variables]] block — Monday by default, matching real org.

One thing worth knowing if a title timestamp isn't showing the way you expect: *a trailing tag needs a space before it to actually parse as a tag* (~<2000-01-01 Sat +1y> :BDAY:~, not ~+1y>:BDAY:~) — this matches real Emacs org-mode's own heading-parsing rules, not a gap specific to this app. Without the space, the tag stays as literal title text instead of becoming a real, filterable tag — but the /timestamp itself/ is still found and still shows up in the agenda either way, since that scan doesn't care about tag formatting.

*** Agenda Files
:PROPERTIES:
:CUSTOM_ID: agenda-files
:END:

*Agenda Files* (real org's ~org-agenda-files~ idea): configure additional files in *Settings → Quick Settings → Agenda files* for an app-wide default, or a specific document's own *~# Local Variables:~* block (see [[#local-variables][Local Variables]]) to override it just for that file — semicolon-separated ~scheme:path~ entries (e.g. ~github:journal.org;webdav:notes/todo.org~), the same syntax and treatment as ~org-refile-targets~ (see [[#refile][Refile]]) — and the Agenda and TODO views scan across all of them, not just the currently open file. A file-local ~org-agenda-files~ line takes precedence over the Settings value whenever that specific document is the one currently open, matching real org's own actual behavior (confirmed directly against real Emacs org-mode: a file-local override is honored when the agenda command runs from within that specific buffer, the closest real-org analogy to this app's own always-current-document Agenda view). A malformed entry (not ~scheme:path~, or an unrecognized scheme) is silently skipped rather than blocking the rest of the list. *Only ~github~ and ~webdav~ are supported* — the same reasoning as archiving, capture-to-file, and image loading: those two backends can read an arbitrary path directly, while a local (File System Access) or iOS-import file needs a fresh picker gesture per file that can't happen silently in the background. If the currently open file is also in the configured list, its live in-memory version (including anything not yet saved) is used instead of a separately fetched, possibly-stale copy of the same file — no double-fetching, no double-counting.

Configured files are fetched once per session and cached, not refetched on every single agenda interaction (switching Day/Week/Month, stepping the date) — a *↻* button appears in the agenda controls once any files are configured, for pulling fresh copies on demand. The agenda renders immediately with whatever's already loaded and updates again as each configured file's fetch completes, rather than blocking on all of them together; a file that fails to load (network error, wrong path, missing permissions) shows a clear message above the agenda list rather than silently vanishing.

** The TODO view
:PROPERTIES:
:CUSTOM_ID: the-todo-view
:END:

Tap *View → TODO* for every active TODO-state heading in the file, *completely independent of any date* — matching real org-mode's own global TODO list (~C-c a t~, distinct from ~C-c a a~, the calendar-style agenda). A TODO with no SCHEDULED, DEADLINE, or timestamp attached never shows up in Agenda at all — by design, not by omission — so this is where it lives instead.

It's a flat list, in document order, each item showing its TODO keyword and title, tap to jump straight to it in the outline. Same exclusions as Agenda: completed items (via the file's own ~#+TODO:~ sequence), archived headings, and commented headings, using the same [[#local-variables][Local Variables]] overrides where relevant.

*Clock report* — a checkbox on the same row as *Clock* (an ~hr~ above separates this whole clock-controls area from the task list above it) — real org-mode's own ~org-clock-report~ / ~#+BEGIN: clocktable ... #+END:~ dynamic block, rendered here as a read-only, selectable report rather than written into the document (this view, like Agenda, is a computed display over the file — it never edits it). Checking it shows a start/end date picker (defaulting to the last 7 days including today the first time you check it, remembering whatever you actually pick after that) with a ~maxlevel~ selector (1–10, default 2, matching real org's own default) alongside it, and the report itself below: a table listing every heading with clocked time in that range, up to whichever ~maxlevel~ is currently selected — with each row's own total genuinely including every one of its descendants, not just what was clocked directly on that heading. A heading deeper than ~maxlevel~ still contributes its own time upward to whichever ancestor is shown, it just doesn't get a row of its own; a heading with no relevant clocked time anywhere in its own subtree is omitted entirely, same as real org. A currently-running (not yet clocked out) session is deliberately excluded, since an in-progress duration would keep changing every time the report is viewed. A *Copy* button, on the same row as the *Clock* / *Clock report* checkboxes, copies the exact rendered text to the clipboard — real, valid org dynamic-block syntax, ready to paste into a file if you want a permanent, literal record of a specific report rather than a live, recomputed one.

** Capture Templates
:PROPERTIES:
:CUSTOM_ID: capture-templates
:END:

Tap *More → Capture* (the ⋮ button next to the filename) for real org-mode's own ~org-capture-templates~ system, for quickly filing a note, task, or table row into a specific spot in the outline without navigating there by hand. Templates show two per row (their description only — the ~key~ is just an internal identifier, not shown); tap one, and if it has any ~%^{Prompt}~ or ~%?~ fields, an in-app form appears asking for each — filled in and submitted together, not one native dialog after another — with a *live preview* above the fields showing the actual expanded result as you type, so a template like ~%<%H:%M> - %?~ visibly reads "22:07 - " with your cursor right after it, not a bare, context-free text box. The first field is focused immediately, keyboard already up and ready for typing, rather than needing an extra tap on the field itself before anything can be typed. *The form closes after a successful capture, returning to the template list — and the capture panel itself stays open there*, rather than closing outright: tap straight into the next template (the same one again, for repeated entries like journal lines or tracking rows, or a different one entirely) without navigating back through More → Capture each time. If a capture fails partway — a network error, a sync conflict on the target file — the form stays exactly as you left it instead, everything you'd typed still there rather than being silently discarded; fix whatever went wrong (or copy the text out to save some other way) and tap Capture again from that same form.

*A capture into a different file than the one currently open will refuse if that file has its own unsaved local changes waiting from an earlier session.* Writing directly to another file's backing store while it also has an unsynced local edit sitting untouched would create a real trap: reopening that file later would still offer to "resume" the stale edit with no indication the file had changed via capture in the meantime, and resuming-then-saving would silently overwrite the capture. Open that file directly first, resolve its pending changes one way or the other, then retry the capture.

Four example templates are the default, so this works immediately with no setup: ~b~ (Bullet List), ~c~ (Check List), ~m~ (Meeting), and ~t~ (Table Row). Edit or replace them any time in *Settings → Capture Templates* — configured as JSON (an array of template objects), not a visual builder, matching how this app already handles GitHub/WebDAV config.

*Template shape:*

#+BEGIN_SRC json
{
  "key": "b",
  "description": "Bullet List",
  "type": "item",
  "olp": ["heading 1", "heading n"],
  "template": "%? [The captured text or note]",
  "file": "journal.org",
  "prepend": true,
  "prependHeading": true
}
#+END_SRC

- ~key~ — must be unique; shown next to the description in the picker.
- ~type~ — one of ~item~ (plain bullet), ~checkitem~ (checkbox item), ~plain~ (raw text, parsed as its own org fragment and merged in — the only type that can itself contain heading syntax, properties drawers, TODO keywords, etc.), or ~table-line~ (one row, appended to the nearest existing table under the target or creating a new one).
- ~olp~ — the outline path to insert into, found or created heading by heading. A segment wrapped in ~%<FORMAT>~ (e.g. ~"%<%Y-%m>"~) expands dynamically — real org's own ~,(format-time-string ...)~ idea, translated into this app's %-escape syntax so a monthly table can target "2026-07" without you creating that heading by hand every month. Any other segment is used completely literally, with no escape processing at all.
- ~file~ /(optional)/ — capture into a DIFFERENT file than the one currently open, real org's own ~(file+olp "target-file.org" ...)~ idea. Optionally prefixed with a scheme (~"github:foo.org"~ / ~"webdav:foo.org"~, case-insensitive — the same ~"scheme:path"~ convention Agenda Files already uses, see [[#local-variables][Local Variables]]) *if the file you mean is actually the currently open one, or you want to be explicit about which backend it's on* — without a scheme, a bare filename (~"journal.org"~) lands as a sibling of whatever file is currently open (same convention as archiving's ~%s_archive~), and a path containing ~/~ is used as-is. *Critical: an explicit scheme that doesn't match whatever backend the currently open document actually uses is refused outright* with a clear error, rather than silently attempted — capture can't switch backends mid-session, it always reads/writes via the same backend the current document already came from. If ~file~ happens to resolve to the exact file already open, the capture correctly lands in that live, in-memory document (visible immediately, saved the normal way) rather than being treated as a separate file. If ~file~ genuinely does target a different file, *that other file is never switched to or displayed* — this reads it via whichever backend the current document uses, inserts, and writes it back directly (nothing is changed if the write fails, the same safety pattern archiving uses). Omit ~file~ entirely to capture into the currently open file, exactly as before this existed. Same local-file picker-permission limitation as archiving: a target file on GitHub/WebDAV works automatically; a local (File System Access) or iOS-import target needs that file opened/saved once first, or you'll get a clear message explaining why instead of a silent failure.
- ~template~ — the text actually inserted (after ~%~-expansion, see below). A literal ~\n~ within the string inserts a newline the normal JSON way — there's no separate ~emptyLines~-style property for spacing; a blank line after the captured content is just ~"...%?\n"~ in the template text itself, the same as any other line break within it.
- ~prepend~ /(optional, default ~false~)/ — real org's own ~:prepend t~ property: puts the new entry at the *top* of the target instead of the bottom. A new list item lands before the first existing item; a new table row lands right after any header row + rule line (so it becomes the first *data* row, not literally above the header) — a brand-new table has nothing to prepend relative to yet, so this makes no difference there. For ~item~ / ~checkitem~ / ~plain~ specifically, ~prepend~ *also* controls where any heading ~olp~ has to auto-create along the way lands among its own siblings (first vs. last child of its own parent) — for those three types, "where does the container heading go" and "where does the content go" are really the same decision applied at two tree levels, not two independent ones, so one setting covers both.
- ~prependHeading~ /(optional, default ~false~, ~table-line~ *only*)/ — for ~table-line~ specifically, heading placement and row placement genuinely are two separate decisions (a common, sensible case: newest month's heading always on top, but that month's own rows still flow in chronological order underneath it) — so ~table-line~ gets its own dedicated field for the heading side, completely independent of ~prepend~. ~prepend: false, prependHeading: true~ is exactly that combination: a newly-created ~olp~ heading becomes the *first* child of its own parent, while every row captured into its table — including the very first one — still appends in increasing order. Applies independently at *every* level of ~olp~ that actually needs auto-creating (a multi-segment path where more than one segment is missing gets each newly-created heading placed first among its own siblings, not just the deepest one); an already-existing segment is matched and reused exactly as before, never reordered. Has no effect at all for the other three types — set ~prepend~ instead, which already covers both concerns for those.

*Template text — the %-escape language, local time throughout:*

- ~%<FORMAT>~ — a practical ~format-time-string~ subset. Every specifier below, shown against the same example moment (Wednesday, March 5, 2025, 14:30:07) so the values are directly comparable:

| Specifier | Meaning | Example output |
|---+---+---|
| ~%a~ | Abbreviated weekday name | ~Wed~ |
| ~%A~ | Full weekday name | ~Wednesday~ |
| ~%b~ | Abbreviated month name | ~Mar~ |
| ~%B~ | Full month name | ~March~ |
| ~%d~ | Day of month, zero-padded (01–31) | ~05~ |
| ~%e~ | Day of month, space-padded ( 1–31) | ~␣5~ |
| ~%F~ | ISO date (~%Y-%m-%d~ combined) | ~2025-03-05~ |
| ~%H~ | Hour, 24-hour, zero-padded (00–23) | ~14~ |
| ~%I~ | Hour, 12-hour, zero-padded (01–12) | ~02~ |
| ~%j~ | Day of year, zero-padded to 3 digits (001–366) | ~064~ |
| ~%m~ | Month, zero-padded (01–12) | ~03~ |
| ~%M~ | Minute, zero-padded (00–59) | ~30~ |
| ~%p~ | ~AM~ or ~PM~ | ~PM~ |
| ~%R~ | Hour:minute (~%H:%M~ combined) | ~14:30~ |
| ~%S~ | Second, zero-padded (00–59) | ~07~ |
| ~%T~ | Hour:minute:second (~%H:%M:%S~ combined) | ~14:30:07~ |
| ~%y~ | 2-digit year | ~25~ |
| ~%Y~ | 4-digit year | ~2025~ |
| ~%%~ | A literal percent sign | ~%~ |

  An unrecognized specifier is left visible (e.g. ~%Z~ stays as ~%Z~) rather than silently dropped.

- ~%t~ / ~%T~ — an active timestamp, date-only / date-and-time.
- ~%u~ / ~%U~ — the same, but inactive (~[...]~ instead of ~<...>~).
- ~%^{Prompt}~ — asks a question via this app's own in-app form (not the browser's native ~window.prompt~, which has real reliability and layout problems in a PWA running standalone on mobile — see below). ~%^{Prompt|default}~ pre-fills an answer; ~%^{Prompt|default|choice1|choice2}~ also lists the choices as a hint under the field (there's no dropdown here — real org's completion-table equivalent is just shown as text to pick from). Multiple prompts in one template all appear as separate fields on the same form, not one dialog after another — filled in together, submitted together; cancelling discards the whole capture, nothing partial gets inserted.
- ~@#~ — real org's own table-formula row-number constant, for ~table-line~ captures only (empty otherwise). Also supports a simple offset, ~@# + n~ or ~@# - n~ (whitespace around the operator optional either way, ~n~ any non-negative integer) — e.g. ~@# + 3~ evaluates to the row number plus three.
- ~%?~ — real org's own "cursor goes here" marker, treated here as just another prompt: it shows up in the same in-app form as any ~%^{Prompt}~, labeled "Text," gathered before insertion rather than left empty with a cursor position to find and focus afterward. If it's the first (or only) field in the template, its own input is focused with the keyboard already up — the closest equivalent this design has to real org's own immediate "cursor lands here, start typing" behavior. This works identically for every capture type and every target file.

** Extras menu
:PROPERTIES:
:CUSTOM_ID: extras-menu
:END:

A floating (☰) button, bottom-right, opens a configurable popup of quick actions — a vertical list of menu items, adjacent to the button and extending to its left rather than covering it. Not a real org-mode feature; this app's own extension, configured through ~org-xx-extra-menu~ (Global or Local Variables — see [[#local-variables][Local Variables]]). The button is hidden entirely whenever ~org-xx-extra-menu~ is unset or resolves to nothing selectable, rather than showing an always-present button that opens onto an empty menu. A separate, sibling variable, ~org-xx-menu-aliases~ — relabeling or hiding buttons in this app's own *existing* File/More/Export/View menus, rather than adding new ones the way this one does — is documented in [[#menu-customization][Menu customization]].

*Syntax*: a sequence of double-quoted entries, each ~"SPEC;LABEL"~, spread across several physical lines with a trailing ~\~ for readability (see [[#configuration][Configuration]] for the general Global/Local Variables line-continuation mechanism this relies on):

#+BEGIN_SRC
org-xx-extra-menu: "t;⭐ Tracking" \
                "["Journal", "%<%Y-%m>"];👁 Current" \
                "-----" \
                "j;📔 Journal" \
                "c;✅ Checklist" \
                "m;👥 Meeting" \
                "'org-clock-out;⏹ clock-out" \
                "'org-xx-calendar;📅 Calendar"
#+END_SRC

*LABEL* is the display text for that menu item, shown exactly as written (icon prefix and all). *SPEC* is one of three shapes:

- A bare *capture-template key* (~t~, ~j~, ~c~, ~m~ above) — selecting the item runs that template, exactly as if it had been picked from the regular Capture menu itself (see [[#capture-templates][Capture Templates]]). A key with no matching template shows a status message rather than doing nothing silently.
- A bracketed *OLP path* (real capture-template ~olp:~ syntax — an array of double-quoted heading titles, each segment itself expanded for ~%<FORMAT>~, e.g. ~["Journal", "%<%Y-%m>"]~ resolving to the current year-month at the moment the item is actually tapped, not when the menu was configured) — selecting the item navigates straight to that heading. Unlike a capture template's own ~olp:~ target, this *never creates a missing heading* — browsing a quick-access menu shouldn't silently write new headings into the file. If the path doesn't fully exist yet, nothing is created and a status message says so; capture templates are completely unaffected by this and still create missing headings along an ~olp:~ path exactly as before, since capturing something is an explicit, deliberate act of adding content in a way that browsing a menu isn't.
- A *quoted function reference* (~'org-clock-out~ above) — selecting the item runs that specific built-in function directly. Every function currently supported:
  - ~'org-clock-out~ — stops whatever clock is currently running, wherever it is in the document (searches the whole document, not just a specific already-selected heading). Records the elapsed time normally. A status message shows if nothing is running. See [[#clocking][Clocking]].
  - ~'org-clock-cancel~ — same search, but discards the running session entirely instead of recording it — no duration ever gets logged, as if the clock had never been started. See [[#clocking][Clocking]].
  - ~'org-cut-subtree~ — the same ~C-c C-x C-w~ god-mode command, run against whichever heading is currently selected. "Currently selected" prefers whichever heading's own per-row action menu is open (tapping a heading's title, the touch-native way to designate a specific heading without a keyboard at all — and this survives the extras menu opening on top of it, since that doesn't close an already-open action menu), falling back to whichever heading is keyboard-focused if no action menu is open. A status message says so if neither is set, rather than doing nothing silently. No confirmation prompt, matching the god-mode command and real org-mode itself — cut copies to the clipboard first, so it's recoverable via paste (or the OS clipboard) even before considering this app's own undo history. See [[#outline-editing][Outline editing]].
  - ~'org-paste-subtree~ — the same ~C-c C-x C-y~ god-mode command and target-heading resolution as ~'org-cut-subtree~ above — pastes the clipboard's own subtree as a sibling right after the selected heading, at that heading's own level. See [[#outline-editing][Outline editing]].
  - ~'org-xx-calendar~ — this app's own extension too, not a real org-mode function: opens a single-month calendar overview (year/month navigation, a Today jump). Today's own date is bold with a two-color "halo" ring around it — a black outer ring and a white inner ring, each a genuine ~border~ on a real, nested element (not ~box-shadow~, which had a reported rendering failure on Android specifically despite working correctly on iOS; ~border~ is the single most universally, unambiguously supported CSS property there is) — guaranteed visible against any background it might land on, the plain panel in either light or dark theme or any of the three event colors below, since at least one of white/black always contrasts strongly against whatever's underneath; no single fixed color (even chosen per-theme) can promise that for every combination. Each day is color-coded by what's on it that day, computed from the exact same agenda pipeline the Agenda view itself uses (so a day's own color here always matches what Agenda would actually show for it) — green for a contact's birthday (~org-contacts-anniversaries~, see [[#agenda][Agenda]]), blue for any other kind of event (a SCHEDULED/DEADLINE/plain timestamp or diary-sexp entry), burnt orange when a day has both together. Ambient, every-day diary-sexp entries (sunrise/sunset/weather and similar) and logbook entries don't count toward this — they'd color almost every day, making the distinction meaningless. *Tapping any real date closes the calendar and jumps straight to Agenda's own Day view, anchored on that specific date* — always available regardless of what's currently open or which backend is connected (unlike Attachments or cross-file Archive/Refile, jumping to an arbitrary date in Agenda needs no special backend capability at all, so there's no "can't do this right now" case to design around here). The displayed month/year is remembered for the rest of the session once you first open the calendar — closing and reopening it picks up wherever you left off, rather than always resetting back to today.
  - ~'org-table-recalculate-buffer-tables~ — real org's own actual, distinct command (recalculating just the CURRENT table is ~C-c C-c~ / ~C-u C-c C-c~ instead, a completely separate command — not this one escalated by a further prefix argument). This app has no "point"/cursor concept for "the current table" the way Emacs does, so there's a *🔢 Calc* button on every table that has a formula instead, for that single-table case — see [[#table-formulas][Table formulas]]. This menu entry is for the other one: every ~#+TBLFM:~ formula in every table in the whole document gets recalculated together, reported and committed as one single undo step.

  Selecting any of these runs it directly, no additional confirmation prompt — unlike the action menu's own Clock out button, which now asks first (Cancel/Stop/OK); a deliberate menu selection is already the confirming step. More functions may be added over time as they become useful for a quick-access menu specifically — an unrecognized function name is skipped rather than erroring (see below), so this list can grow without breaking anything already configured against an older version.

Five hyphens (~"-----"~) on their own is a visual separator, not a selectable item — group related actions without needing a heading structure of their own.

A malformed entry (bad JSON in an OLP array, an unrecognized function name, a spec matching none of the three shapes, a missing label) is silently skipped rather than breaking the whole menu — one bad line doesn't take out every other one.

** Menu customization
:PROPERTIES:
:CUSTOM_ID: menu-customization
:END:

One Global/Local Variable, ~org-xx-menu-aliases~, lets you relabel or hide individual buttons across this app's own File, More, Export, and View menus at once. Not a real org-mode variable (the ~xx~ marks it as this app's own extension, the same convention other app-specific variables here are gradually moving toward); it uses the same Global/Local Variables mechanism every other setting on this page does. A related ~org-xx-*~ variable, ~org-xx-extra-menu~, is documented separately in [[#extras-menu][Extras menu]] — it *adds* an entirely new, freely-configurable quick-access menu of its own, rather than relabeling one of these four existing ones.

*Syntax*: a sequence of double-quoted ~"menu:Label;alias"~ entries, space-separated (spread across multiple physical lines with a trailing ~\~ for readability, same line-continuation mechanism every other multi-entry variable here already uses). ~menu~ is one of ~file~, ~more~, ~export~, ~view~ — which of the four menus that specific entry applies to:

#+BEGIN_SRC
org-xx-menu-aliases: "file:New;➕" "file:Open;📂" "file:Save;💾" "file:Save As;💾➕" "file:Export;↗️" \
                      "export:Markdown;" \
                      "more:Search;🔍" "more:Capture;📸" "more:History;🔄" "more:Add Header;➕" "more:Help;❓"
#+END_SRC

~Label~ is one of that menu's own real, built-in button labels — see the table below for exactly which labels each of the four menus actually has. A label that doesn't match any real button in that menu simply has no effect (never looked up by anything), the same tolerant-of-the-unexpected handling every other "recognized subset" parser in this app already uses, rather than a hard error — the same tolerance applies to ~menu~ itself: an entry naming anything other than ~file~ / ~more~ / ~export~ / ~view~ is silently skipped too.

~alias~, after the semicolon, has two meanings depending on whether it's present:
- *Non-empty* — the button's default label text is replaced with the alias wherever it's shown (the button still does exactly the same thing; only what's written on it changes). The original label becomes that button's accessible name (screen readers, hover tooltips) instead, so it still says what the button actually is even once the visible text is just an icon.
- *Empty* (~"menu:Label;"~ with nothing after the semicolon) — the button is *omitted entirely*, not shown at all, not even disabled. ~"export:Markdown;"~ above is exactly this: hides the Markdown button from the Export menu, with no other route left to it (unlike some other buttons, this app's own ~org-xx-extra-menu~ doesn't have a Markdown-export shortcut of its own). *~more:Settings~ is the one exception* — it's a required capability (GitHub/WebDAV setup, Global Variables, and everything else reachable only from there), so it can never actually be hidden this way; an empty alias for it specifically means "keep the real label, ~Settings~" rather than "omit the button", the only label anywhere in this variable where empty doesn't mean hidden.

A label never mentioned in the variable at all keeps its default, unchanged text — this is an opt-in override list, not a full redefinition of any menu. ~view~ isn't mentioned anywhere in the example above at all, meaning no overrides for the View menu specifically — every one of its buttons keeps its default label.

*The order buttons appear in can be changed too* — but only once *every single one* of a menu's own real labels is listed for it (see the table below for the complete set each menu needs), even ones kept at their own default label and visibility; a partial listing leaves that menu's own default order completely untouched, so setting an alias for just one or two buttons never has the side effect of silently reordering the rest. Once every label is present, the buttons render in whichever order they're listed in — top to bottom, matching the order the ~"menu:Label;alias"~ entries themselves appear in the variable's own value. An entry with an empty alias still counts as "listed" for this purpose (that's how a button can occupy a specific position in the order without changing its label at all — ~"more:Settings;"~ places ~more:Settings~ exactly where listed while still showing the plain word "Settings", per the required-visibility exception above). For example, to show the More menu as Settings, Capture, Search, in that order, with History/Add Header/Help at their own defaults:

#+BEGIN_SRC
org-xx-menu-aliases: "more:Settings;" "more:Capture;" "more:Search;" "more:History;" "more:Add Header;" "more:Help;"
#+END_SRC

*Each menu is a genuine floating popup* — File, View, More, and Extras all open as a small, bordered, drop-shadowed panel positioned directly next to their own trigger button (below it if there's room, above it otherwise — Extras' own button sits near the bottom of the screen, so its popup opens upward), sized to fit its own widest row with no wasted width, rather than an inline panel taking up the page's own width. All four are built through the exact same positioning code, not merely four separate implementations that happen to look similar — one full-width row per button, top to bottom, a short label like "New" and a longer one like "Save As" both simply filling the row's own width the same way; on a mouse (not a touch device), moving the pointer over a row highlights it before you click, exactly like a native OS/browser menu. Tapping anywhere outside a menu closes it ("light dismiss," the same convention a native browser or OS popup menu uses), and selecting an action closes the menu immediately — its own result (a save completing, a file opening) is then reported separately via the status line, not by leaving the menu open. Every popup menu in the app — File, View, More, Export, the Open/Save-As backend picker, and Extras — is built and styled the identical way, and shares one size setting (Settings → Appearance → *Menu Size*, Regular/Small) rather than each having its own separate look.

The four menus' own real labels, exactly as they'd appear in ~"menu:Label;alias"~ — the complete set needed to reorder that specific menu:
| ~menu~ | Labels |
|----------+--------|
| ~file~ | ~Export~, ~New~, ~Open~, ~Save~, ~Save As~ |
| ~more~ | ~Add Header~, ~Capture~, ~Help~, ~History~, ~Search~, ~Settings~ |
| ~export~ | ~ASCII~, ~Calendar (.ics)~, ~HTML~, ~Markdown~, ~ODT~ |
| ~view~ | ~Agenda~, ~Org~, ~Text~, ~TODO~ |

** File management
:PROPERTIES:
:CUSTOM_ID: file-management
:END:

*File menu*: New, Open, Save, Save As.

- *New creates a document entirely in memory* — no file picker, no naming prompt, no backend choice up front. It's editable immediately, and every edit is cached locally exactly the same way any other open document's edits already are — including surviving a crash or an accidentally-closed tab, since reopening the app resumes it from that same cache, the same "resume unsaved local version" prompt any other file's unsynced edits already trigger. Nothing is written to a real backend (disk/GitHub/WebDAV) until you explicitly choose to keep it, though — the header shows *Untitled (unsaved)*, styled the same attention-grabbing red as an ordinary file with unsaved edits, since "this needs a destination" is the same kind of thing "this has unsaved changes" already is. *Save* stays disabled the whole time (there's nowhere to save TO yet); *Save As* is what actually picks a destination and turns it into a real, persisted file — at which point it behaves exactly like any other open document from then on. Useful as a scratch pad — trying out a capture template, testing a table formula, drafting something before deciding it's worth keeping — without the friction of naming and placing a file for something that might get thrown away in a minute. Creating another new document while the current one is itself still unsaved asks for confirmation first, since replacing it discards whatever's cached under that same slot with nothing else to fall back on — the one genuine exception to every other document-switch in this app already being safe to do without asking.
- *Open* asks which backend to use (Local/Import, GitHub, or WebDAV).
- *Opening from GitHub or WebDAV browses a real folder/file listing* — no more needing to already know the exact path from some other source. Folders (📁) are tappable to navigate into; among files, ~.org~ files (📄) and ~_archive~ files (🗄️, real org's own archive-file naming convention — see [[#archiving][Archiving]]) are shown, other files in the same folder are filtered out rather than cluttering the list. An *↑ Up* button appears once you're below the root. GitHub uses its Contents API (the same one reads/writes already used); WebDAV uses the standard ~PROPFIND~ method, which most servers (Nextcloud, ownCloud, Apache ~mod_dav~) support out of the box. If listing ever fails — a server that doesn't support ~PROPFIND~ well, a token without list permission on a specific folder — *"Type a path instead…"* is always available as a fallback, the same manual entry this replaced as the default path.
- *Save* always writes back to whichever backend the current file came from — you don't get asked again.
- *Save As* lets you pick a new destination, possibly on a different backend than the one you opened from (or, for a brand-new unsaved document, the very first destination it's ever had).
- If a file has local edits that were never saved when you try to open it again, you're asked whether to *resume* those edits or *discard* them and load the current version — either choice actually opens the file; there's no dead-end confirmation. The prompt shows exactly when the pending edit happened, not just "an earlier session," and discarding genuinely clears it. *Settings → Pending Local Changes* also lists every file with something unsynced directly, with its own Discard button per file (and Discard all when there's more than one) — a way to check "does anything actually have unsaved changes?" without needing to open each file individually to find out.
- *Conflict handling*: if the on-disk/remote version changed since this app last synced it, Save asks you to keep your version or the other one, via a plain confirm dialog — there's no diff or merge view.
- *Recently opened*, below a double separator, lists files you've actually opened or saved-as before — not every file that's ever existed, just ones this app has itself touched. Persists across sessions (stored the same way as every other setting), sorted alphabetically for display, capped at the last handful, and never includes whichever file is currently open — there's nothing useful about a menu item for "open the file you're already looking at." A long-press on the *Recently opened* label itself asks whether to clear the whole list (Clear/Cancel) — there's no per-item removal, just the list as a whole. Tapping an entry opens it directly, the same as tapping a file while browsing GitHub/WebDAV/local — no re-prompting for a path or a picker, except for a file that was originally brought in via *Import* (the read-once fallback for browsers without File System Access, e.g. iOS Safari): that one genuinely can't be reopened without you re-selecting it, since there's no live handle back to the original to reuse.

** Export
:PROPERTIES:
:CUSTOM_ID: export
:END:

*More → Export…* gets a document out of org-pwa as ASCII, Markdown, HTML, ODT, or a calendar file, for the whole file or (ASCII/Markdown/HTML/ODT) just one heading's subtree. All five walk the same parsed structure the app already renders from, not a text-level reparse. Every file keyword this app recognizes anywhere — ~#+TITLE~ / ~#+AUTHOR~ / ~#+DATE~ / ~#+OPTIONS:~ / ~#+INCLUDE:~ here, and ~#+STARTUP:~ / ~#+TODO:~ / ~#+TBLFM:~ / ~#+BEGIN_...~ / ~#+ARCHIVE:~ elsewhere in this document — matches case-insensitively, the same as real org itself: ~#+title:~ works exactly the same as ~#+TITLE:~.

*Scope*: *This file* exports everything; *Choose a heading…* shows every heading in the document — regardless of current fold state, so something folded away is still pickable — and exports just that heading and its descendants. The selected heading becomes the new top level (plain text / ~#~ / ~<h1>~ / ODF outline level 1, depending on format) in the output, not its original depth, so a level-3 heading exported on its own doesn't produce a dangling, orphaned sub-level with nothing above it. Calendar export shares this same scope choice too (see below) — including its own *Choose a heading…* option, exporting just that heading's dated items and its descendants'.

*ASCII* is a plain, readable text rendering — real org's own ~ox-ascii~ backend, for the core cases. A level-1 heading is underlined with a row of ~=~ matching its own width; deeper headings are indented. Paragraphs are word-wrapped to ~org-ascii-text-width~ characters (see [[#local-variables][Local Variables]] — the real org-mode variable this is named after, default ~72~, matching real org's own default exactly), breaking only at whitespace — a single word longer than the width is kept whole on its own line rather than split mid-word. Lists and blocks render as plain, readable text; a ~[[target][description]]~ link becomes ~description (target)~, since the raw bracket syntax reads far less like natural prose than everything else here.

*Tables get properly typeset, fixed-width columns* — every column is padded to the width of its own longest cell, so every row in the table lines up exactly. Alignment is auto-detected per column too, matching real org exactly: a column that's mostly numbers is right-aligned, everything else is left-aligned. Cell content is parsed for inline markup the same as everywhere else in this export (~*bold*~ stripped, ~~code~~ → the ~`text'~ backtick-quote convention, etc.) — see the *Inline markup is parsed* paragraph below for the full reasoning.

*Explicit column widths* — real org's own ~<N>~ width-cookie syntax (a row where every cell is exactly ~<N>~, e.g. ~| <30> | <10> | <24> |~, typically placed just above the header row) forces that column to exactly ~N~ characters wide in ASCII export instead of the auto-computed one. Content wider than its column's width word-wraps across multiple output lines within the same logical table row, breaking at a hyphen when a single long word (a long, hyphenated variable name, for instance) doesn't fit on its own — this preserves every character rather than silently dropping any.

*The cookie row itself is recognized and excluded from every export format* (ASCII, HTML, Markdown, ODT) — a directive, not table data, so it never shows up as a literal ~<10>~ cell anywhere. This matters beyond just tidiness for HTML and Markdown specifically: both always treat a table's first data row as its header, so an unrecognized cookie row wouldn't just appear as odd-looking content — it would actively hijack the header position, demoting the table's real header row into the body underneath it. Only ASCII export actually uses the specified widths, though — HTML, Markdown, and ODT recognize and skip the cookie row the same way, but otherwise size columns exactly as they already did (the browser/renderer's own layout for HTML, GFM's own table rendering for Markdown, ODF's own table-column defaults for ODT).

*Inline markup is parsed, not left as raw source text*: ~*bold*~, ~/italic/~, ~_underline_~, and ~+strikethrough+~ all have their markers stripped entirely — ASCII has no way to represent any of them visually, and org's own export framework already separates the markup from its content before a backend's own transcoder ever sees it, so there's genuinely nothing for an ASCII backend to re-add. ~code~ and =verbatim= become real org's own backtick-quote convention (=`text'=, ~org-ascii-verbatim-format~'s actual default) — not the literal ~~~ / ~=~ source markers, which read as stray, meaningless punctuation once nothing renders them as a visual distinction. A footnote reference becomes a bracketed label (~[1]~), with its definition collected into a "Footnotes" section at the end.

*Section numbering and a generated Table of Contents* are both included by default — real org's own default too. A heading is numbered ~1~, ~1.1~, ~2~, ... and — for any document with more than one heading, since a single heading has nothing worth a table of contents for — a "Table of Contents" listing appears at the very top, each entry showing its own number and dot-leader indentation matching depth, mirroring real org's own ~org-ascii--build-toc~ output.

Doesn't implement ~ox-ascii~'s fuller feature set (Latin-1/UTF-8-specific character substitutions, ~:width~-configurable horizontal rules, left/right/center justification blocks) — see [[#differences-from-emacs-org-mode][Differences from Emacs org-mode]].

*~#+TITLE~ / ~#+AUTHOR~ / ~#+DATE~ / ~#+OPTIONS:~* work the same way across all four document formats (ASCII/Markdown/HTML/ODT), whole-document export only — exporting just a subtree shows that heading itself as the natural starting point instead, the same reasoning real org's own subtree export uses. ~#+TITLE~ becomes a real, visible title (an underlined ASCII header, ~<h1 class="title">~, a "Title"-styled ODT paragraph); ~#+AUTHOR~ / ~#+DATE~ appear right beneath it, and also populate each format's own real metadata (ODT's own ~dc:creator~ / ~dc:date~) where the format has one. ~#+OPTIONS:~ supports six keys, chainable on one line or split across several (a later value for a repeated key always wins): ~toc:~ (an integer depth limit, or ~nil~ to disable the Table of Contents entirely — independent of ~num:~: a depth-limited ToC listing still coexists with full section numbering throughout the body, not one combined toggle); ~num:~ (heading numbers on/off — for ASCII/HTML/ODT this numbers headings themselves; real org's own Markdown backend never number-prefixes a heading in the body at all, so here ~num:~ instead switches the ToC's own list between ordered and unordered); ~^:~ (sub/superscript strictness — the same three states as ~org-use-sub-superscripts~, see [[#local-variables][Local Variables]]; an explicit ~#+OPTIONS: ^:~ value on the file overrides that variable for this export, matching real org's own actual file-over-global precedence); ~author:~ / ~date:~ (whether those fields appear at all, independent of each other); ~creator:~ (a "Generated by org-pwa" notice, default off — matching real org's own actual default too). Markdown specifically has no ~#+TITLE~ / ~#+AUTHOR~ / ~#+DATE~ / ~creator:~ support at all, matching real org's own ~ox-md~ backend, which doesn't implement any of the four either — only ~toc:~ / ~num:~ apply there.

*~#+INCLUDE: "path" [block-type] [language] [:lines "N-M"] [:minlevel N]~* splices another document's own content into this one at export time, across the same four formats — either before the first heading (the same place ~#+TITLE~ / ~#+OPTIONS:~ already live) or inside a heading's own body text; the latter nests the included content as *children of that heading* rather than as document-level siblings, matching real org's own actual behavior. With no explicit ~:minlevel~, a mid-heading include defaults to one level deeper than its own containing heading — genuinely different from a document-level include, which keeps the sub-document's own original levels unchanged. Body text before/after the ~#+INCLUDE:~ line, within the same heading, stays exactly where it was; real org has a further quirk of merging trailing text into whatever the last included element happened to be, which this app doesn't reproduce (a well-defined, predictable placement instead of an incidental artifact of real org's own internal merging). ~path~ resolves against this app's own storage: an explicit ~github:~ / ~webdav:~ prefix (the same convention [[#agenda][Agenda Files]] / [[#refile][Refile Targets]] already use) reads from that adapter regardless of what's currently open; a bare path resolves against whichever file is currently open instead. With no ~block-type~, the included file is parsed as a real org document and its own headings splice in — but never its own ~#+TITLE~ / ~#+AUTHOR~ / etc., a deliberate simplification (real org's own actual behavior here is a surprising edge case: a plain default-format include literally concatenates the two files' own ~#+TITLE~ values together in its own ASCII output). ~:minlevel N~ shifts the included content's own top level to ~N~, preserving whatever depth it already has internally. With a ~block-type~ (~src~ / ~example~ / ~quote~ / ~export~ — a ~src~ block can also take a ~language~, either a source language alongside ~src~ or a backend name alongside ~export~, e.g. ~#+INCLUDE: "path" export html~), the file's own raw text is wrapped in the matching ~#+BEGIN_.../#+END_...~ block and placed in whichever body it was included from (the document's own preamble, or that specific heading's own body, both rendered by every export format) rather than becoming a heading, matching real org's own actual placement. ~:lines "N-M"~ / ~"-M"~ / ~"N-"~ filters the raw text before anything else happens to it — ~"N-M"~ is inclusive of its own start but *exclusive* of its own end (the Org manual's own wording, "lines 5-10," reads as inclusive on both ends, but real org's own actual behavior isn't). A ~#+INCLUDE:~ pointing at a file that can't be found or reached is skipped silently — the rest of the export still proceeds, rather than one broken reference failing the whole thing.

*~#+HTML_HEAD:~* inserts raw HTML/CSS verbatim into the exported document's own ~<head>~, right before ~</head>~ — no escaping, since the whole point is literal passthrough (a ~<style>~ block, a ~<link>~ tag, whatever's needed). Multiple ~#+HTML_HEAD:~ lines concatenate, joined by newlines in source order, rather than only the last one winning — the natural way to write a multi-line ~<style>~ block one directive line at a time. HTML export only; every other format silently ignores it, matching real org's own confirmed behavior. Still applies during a subtree-only export, not just a whole-document one.

*Page numbers*, one concrete, worked use of the above: CSS's own ~@page~ rule is inherently print-only — it takes effect only once the browser actually paginates the document (printing, or *Print → Save as PDF*, this app's own documented PDF path — see *HTML* below), so it's invisible during normal on-screen viewing, which is correct: a page number genuinely means nothing until there are pages.

#+BEGIN_SRC
#+HTML_HEAD: <style>@page { @bottom-center { content: counter(page); } }</style>
#+END_SRC

Bottom-right instead of centered, with a bit more page margin to make room for it:

#+BEGIN_SRC
#+HTML_HEAD: <style>@page { @bottom-right { content: counter(page); } margin: 2cm; }</style>
#+END_SRC

"Page 3 of 12" style, via CSS's own ~counter(pages)~ (the *total* page count, not just the current one):

#+BEGIN_SRC
#+HTML_HEAD: <style>@page { @bottom-center { content: counter(page) " of " counter(pages); } }</style>
#+END_SRC

~counter(pages)~ specifically has weaker browser support than ~counter(page)~ alone — it works in Chrome, less reliably elsewhere, so the plain page-number version above is the more broadly reliable one if the destination browser is unknown. Combine with a ~#+BEGIN_EXPORT html~ block (see below) for a running header/footer alongside the page number, not just the number on its own.

*~#+BEGIN_EXPORT <backend> ... #+END_EXPORT~* passes its own raw content straight through, completely unescaped, but *only* when ~<backend>~ matches whichever format is currently being exported to (~html~, ~ascii~, or ~md~ — real org's own confirmed name, though ~markdown~ also works, matching real org's own acceptance of both) — for any other backend, the whole block is omitted entirely, not shown as generic text. This is how the two together build a fixed print header/footer: an ~#+HTML_HEAD:~ ~<style>~ block with ~@media print~ rules pinning ~header~ / ~footer~ to the page edges, paired with a ~#+BEGIN_EXPORT html~ block (before the first heading, or inside whichever heading it belongs to) containing the actual ~<header>~ / ~<footer>~ markup.

*ODT's own equivalent*, ~#+BEGIN_EXPORT odt~, works the same way but the raw content is expected to already be valid ODF XML markup (~<text:p text:style-name="...">...</text:p>~ and similar) — confirmed directly against real org's own ~ox-odt.el~ source, which inserts an ODT export block's own raw value completely unescaped into the document XML too, the author's own responsibility to get right, not something this app validates.

*Markdown* is GFM-flavored: checkboxes become real task-list syntax (~- [ ]~ / ~- [x]~), tables become pipe tables, fenced code blocks keep their language hint, footnotes become GFM's own ~[^label]~ / ~[^label]: text~ syntax. TODO keyword, priority, and tags stay as plain text on the heading line (~# TODO [#A] Buy milk~) since Markdown has no native syntax for any of the three — matching org's own source convention rather than inventing one. Underline and sub/superscript fall back to raw ~<u>~ / ~<sub>~ / ~<sup>~ HTML passthrough, since Markdown has no native syntax for those either (both CommonMark and GFM allow embedded HTML, so this renders correctly wherever the output is actually viewed). *Internal links resolve to real GFM anchors*: a ~[[#custom-id]]~ / ~[[*Heading]]~ / bare fuzzy-title link resolves (via the same ~resolveLinkTarget~ [[#export][HTML export]] uses) to the target heading, then generates a ~#slug~ using GitHub's own heading-slug algorithm exactly — lowercased, punctuation stripped rather than hyphenated, spaces to hyphens, a duplicate title disambiguated with GitHub's own ~-1~ / ~-2~ / ... suffixes — the specific convention GitHub itself, and most other GFM-compliant renderers, actually use to generate a heading's own clickable anchor. A link to a heading outside the exported scope, or one that doesn't resolve to anything at all, falls back to the literal target text, same as before.

*ODT* produces a real, standalone OpenDocument Text file (~.odt~) — opens directly in LibreOffice, OpenOffice, Word (with the ODF filter), or Google Docs (import), no conversion step needed. Headings become real, navigable outline levels; bold/italic/underline/strikethrough/code map to named character styles; checkboxes render as real checkbox glyphs (☐/☑ — ODF has no native checkbox-list construct to match org's own, the same reasoning Markdown's own real task-list syntax doesn't need); footnotes become genuine, editable ODF footnotes (~<text:note>~) that a word processor can renumber and reflow on its own, not a hand-numbered list the way Markdown/HTML export approximate them. *Internal links resolve to real, working cross-references* — a ~[[#custom-id]]~ or ~[[*Heading]]~ link becomes an ODF bookmark reference pointing at the actual target heading, the same ~resolveLinkTarget~-based resolution [[#export][HTML export]] uses (see below) — not the raw org target text left as an unresolved, non-functional link the way Markdown export still does. Images are referenced by their target path as plain text, not embedded (embedding would mean packaging each image's own binary into the archive, out of scope here) — matching how ASCII/Markdown export already treat images as a reference rather than embedded data.

*HTML* is a complete, standalone document — open it directly, no other files needed. TODO keywords and priority get small styled badges (a done-state keyword like ~DONE~ or a custom one like ~KILL~, correctly read from the file's own ~#+TODO:~ line, renders in green rather than red). Checkboxes are real disabled ~<input type="checkbox">~ elements. Footnotes become jump-linked superscripts with a back-linked Footnotes section at the end. *Internal links resolve to real, working anchors*: every exported heading gets an ~id~ (its own ~:CUSTOM_ID:~ if set, otherwise a slug generated from its title, disambiguated if two headings would otherwise collide), and a ~[[#custom-id]]~ / ~[[*Heading]]~ / bare fuzzy-title link resolves against it using the same ~resolveLinkTarget~ the live app itself uses for on-screen navigation — not the raw org target text dumped in as the ~href~ unresolved. A link to a heading outside the exported scope (e.g. exporting just a subtree) falls back to the literal target text, since there's genuinely nowhere within that specific export for it to point to. *This is also the path to PDF*: the exported HTML includes print-aware CSS (headings and tables don't split awkwardly across a page break), so opening it and using the browser's own Print → Save as PDF produces a properly paginated PDF with no separate export path needed — a browser's print engine handles pagination far better than a hand-rolled PDF generator would, and needs no new dependency to get there.

*Calendar (.ics)* exports every dated item — SCHEDULED, DEADLINE, a plain active timestamp in a heading's title, and [[#agenda][org-contacts-anniversaries]] — as a standard iCalendar file, importable into any real calendar app. *Scope*: *This file* exports just the currently open document; *This file + Agenda Files* (shown only when [[#agenda][Agenda Files]] are actually configured) additionally pulls in every configured file, the same aggregation the live Agenda view itself already uses — including fetching any not yet loaded this session, so this always reflects everything the Agenda view would show, not just whatever happened to already be cached. A repeater (~+1w~, ~++3d~, ~.+1m~) becomes a real ~RRULE~, letting the destination calendar app expand the recurrence itself, rather than exporting a separate event for every individual occurrence. A DEADLINE's own delay/warning-period suffix (~-3d~) becomes a calendar alarm reminder. Matches the Agenda view's own default exclusions (archived headings, commented headings, completed items) for consistency. Re-exporting the same file later produces the same event IDs for the same items, so a calendar app recognizes an update rather than creating duplicates on every re-import.

*What's dropped on export, deliberately*: property drawers (an implementation detail, not reader-facing content) and the ~ARCHIVE_*~ properties specifically, even if present — their meaning is entirely internal to this app's own archiving feature (see [[#archiving][Archiving]]). SCHEDULED/DEADLINE render as a small italicized line under the heading instead (Markdown/HTML/ODT only — Calendar export is built entirely from these). Internal links (~[[*Some Heading]]~, ~[[#custom-id]]~) resolve to real, working cross-references across all three formats — see each format's own paragraph above for exactly how (HTML and ODT both generate their own id/bookmark, so this app fully controls the anchor; Markdown specifically matches GitHub's own heading-slug algorithm, since that's the closest thing to a de facto standard other GFM-compliant renderers converge on too).

** Settings
:PROPERTIES:
:CUSTOM_ID: settings
:END:

Reached via *More (⋮) → Settings*, which replaces the outline with the settings screen — same as switching to Text or Agenda view, not a popup over the outline. Tap Settings again from the More menu, or any of File/More/View, to leave settings and return to whatever was showing before (there's no separate "Done" button; those are already the way out).

- *Quick Settings* — a proper, labeled control for every Global/Local Variable this app supports (grouped by area: Progress logging, Agenda, Contacts & Calendar, Weather, Search & tags, Editing, Export, plus an *Advanced* group for the handful with more complex, multi-entry syntax of their own — refile targets, agenda files, the ~org-xx-*-menu~ family) rather than a "name: value" line you have to already know to type into the text box below. A toggle, a number field, a select, or (for anything long enough to be awkward in a single line — refile targets, agenda files, the menu-customization fields, ~org-weather-format~) a small, read-only preview that opens a large, scrollable popup on focus for the actual editing — Cancel discards, OK commits, and Reset (shown only once a field has actually been changed from its own default) reverts it. The background page is locked from scrolling while any of these popups is open — a fully-covering overlay alone doesn't stop a touch-drag from scrolling whatever's behind it on mobile, a separate thing from painting order. Every one of these writes into the *exact same* app-wide Global Variables baseline as the Global Variables text box further down — changing a toggle here updates that text, and vice versa, so neither is a separate, out-of-sync source of truth. A file's own ~#+STARTUP:~ or "# Local Variables:" block still overrides anything set here, same precedence as always — this only changes the app-wide default, not any per-file override. Applies immediately, no reload needed. A small *?* next to almost every field jumps straight to the relevant part of the help doc.
- *Global Variables* and, directly beneath it, *Capture Templates* — the same small-preview-opens-a-popup pattern as the longer Quick Settings fields above, editing the app-wide variable baseline as raw "name: value" lines and the capture template list as raw JSON respectively. The popup's own OK validates and saves; Reset (Global Variables) or "reset to defaults" (Capture Templates) is offered the same way, only once something's actually been changed.
- *GitHub* and *WebDAV* — each a single popup form (personal access token/owner/repo/branch for GitHub; server URL/username/password for WebDAV), opened by focusing any of the small preview fields shown inline. Cancel discards; Save commits every field in the form together. Use a fine-grained GitHub token scoped to just that repo with Contents read/write only, not a broad classic token. For WebDAV, use an app-specific password if your server supports one; most WebDAV servers don't send CORS headers by default, and a network error on Open/Save is very likely that, not a bug in this app.
- *Appearance* — theme (System/Light/Dark), font (System/Serif/Monospace), two independently adjustable font sizes on the same row: the main size (headings, paragraphs, and lists/checkboxes all share this one) and *Tables* (tables have their own size rather than inheriting the main one — a table at the same size as prose text tends to feel cramped or oversized depending on column count), and *Menu Size* (Regular/Small) — the size of every popup menu's own items (File, View, More, Export, and Extras all at once, never configurable per-menu, so they stay visually consistent with each other regardless of which is chosen). Regular (the default) is the larger, roomier sizing with a full 44px touch target; Small is the more compact sizing Extras originally shipped with on its own, before every popup menu in this app was unified onto the same shared look. Each has its own color swatch plus an opacity slider (several of these colors are semi-transparent by default — a border or a badge background, for instance — which a plain color picker alone can't represent), and its own *Reset* back to the built-in default; *Reset all* clears an entire theme's customizations at once. Nothing here changes any default — every color is exactly what it's always been until you actually pick something different. When *System* theme is active, whichever theme (Light or Dark) actually matches the OS's live preference is the one whose customizations apply, updating immediately if the OS preference itself changes while the app is open.
- *Backup* — *Export Settings* bundles everything registered on this page — appearance (including any custom theme colors), capture templates, GitHub, WebDAV (including credentials), and the Global Variables baseline (whatever Quick Settings and/or the raw text box currently hold) — into one downloadable JSON file, for moving settings to another device. A confirmation is shown first if the export would include a token or password, since the file contains them in plain text. *Import Settings…* picks a previously-exported file and merges its contents into what's already configured here — a setting the file doesn't mention is left completely untouched, so importing an older or partial export can never silently wipe out something it simply doesn't know about. Anything with an immediate visual effect (theme, fonts, custom colors) applies right away, no reload needed.
- *Updates* — appears at the very top of Settings by default, ahead of even Appearance, since for many people it's the single most-used entry on the whole page. ~org-xx-updates-at-top~ (a global variable, this app's own extension — not a real org-mode variable, same "org-xx-" convention as ~org-xx-extra-menu~ / ~org-xx-calendar~) controls this: explicitly set to ~nil~, Updates moves back to its own original position at the bottom of the page instead; anything else (including simply never setting it at all) keeps it at the top. The version currently running (e.g. "org-pwa-shell-v225") is always shown right here, not only after tapping *Check for updates* — asked from the active service worker itself the moment Settings first needs it, so what's displayed is genuinely what's controlling the page, not just whatever's newest in the cache (which can briefly differ if an update has downloaded but hasn't been applied yet). A new version is checked for at app startup, and whenever you tap *Check for updates* here — no periodic background polling and no automatic recheck on returning to the tab, deliberately: those add complexity and can behave unpredictably across platforms (iOS/Safari in particular is known to throttle or skip background service-worker checks more aggressively than other browsers, which is exactly the situation this button exists for) without actually being more reliable than a check you can trigger yourself whenever you want to know. The button reports what it found — you're on the latest version, an update was found (with a Reload banner appearing at the top to apply it), or the check itself failed (e.g. offline). Finding an update through either path shows the same Reload banner; tapping Reload there applies it immediately. Wherever you're currently scrolled to on this page stays put while the check runs and while its result is shown — finding whichever element is genuinely scrolling at the moment (Settings renders into a container that only actually scrolls on a wide/desktop screen; on a phone, its parent does the scrolling instead), rather than assuming a specific one.

** Offline behavior and sync
:PROPERTIES:
:CUSTOM_ID: offline-behavior-and-sync
:END:

Every edit applies to an in-memory copy and is cached to IndexedDB in the background immediately — the UI never waits on a write to feel responsive, and nothing is lost by closing the tab before hitting Save. Writing back to disk/GitHub/WebDAV only happens on an explicit Save. Local File System Access reads are unaffected by network connectivity (it's not a network call); GitHub and WebDAV obviously do need a connection.

*Conflict detection*: Save compares the file's current disk state against what this app last knew about it — if someone or something else changed the file since then, you're asked whether to keep your version or the other one, rather than one silently overwriting the other with no warning. This tracking stays accurate no matter WHICH feature actually wrote to a file — capturing, archiving, refiling, or restoring to a different file than the one currently open all update it too, not just an explicit Save of the currently-open document. Every one of those goes through the same shared, centralized write path internally, specifically so a future feature needing the same "write to another file" shape can't independently forget this bookkeeping the way separate, hand-written copies of it once did. That same shared path also refuses outright to write into a file that already has unsaved local changes of its own sitting unsynced from an earlier session, rather than silently risking that they'd never be seen.

*Proactive external-change detection*: rather than only finding out about a conflict whenever Save eventually happens, this app also checks in the moment it's actually likely to matter — right after opening a file (comparing against what it reads fresh from disk), and again whenever the tab regains focus (catching a change made elsewhere while this tab sat in the background). If the file has changed since either checkpoint, a dismissable banner says so immediately, with the option to reload the current version or keep working and rely on Save's own conflict check as the final safety net regardless. A dismissal only applies to the specific change that was seen — a genuinely newer change after that still gets its own notice, rather than being silently swallowed by an earlier dismissal.

*Every GitHub and WebDAV read explicitly bypasses the browser's own HTTP cache* (~cache: 'no-store'~ on the request). Without it, updating the same file twice in quick succession — the exact shape of repeated capture, especially the "multiple entries" loop-back in [[#capture-templates][Capture Templates]] — could read back a browser-cached, already-stale version of the file on the second attempt, sending a write with an out-of-date GitHub ~sha~, which GitHub then correctly refuses as a conflict even though nothing had actually changed except this app's own previous write moments earlier.

** Platform support
:PROPERTIES:
:CUSTOM_ID: platform-support
:END:

Local file access (the "Local" option, with a live, writable handle) requires the File System Access API — Chrome and Edge, desktop or Android. *No browser on iOS supports this*, because Apple requires every iOS browser to use WebKit, which has never implemented it — that's not fixable by switching browsers on that platform.

*Android specifically*: the file picker filters by MIME type through the OS's own Storage Access Framework, and ~.org~ has no MIME type registered on Android (unlike ~.txt~, which maps cleanly to ~text/plain~), so ~.org~ files could be invisible in the open picker even though they're right there. Filtering on the ~.org~ extension directly via ~accept: {'*/*': ['.org']}~ instead of a specific MIME type does *not* resolve this — ~.org~ files still stay invisible while ~.txt~ keeps working. The open picker has no ~types~ filter at all, showing every file rather than guessing at an ~accept~ shape that satisfies Android's filtering — if file visibility ever regresses here, that's the first thing to check, and re-adding any MIME-based filter to the open picker specifically should be treated with suspicion given this history.

On unsupported platforms, *Import* replaces "Local": pick a file once via the native file picker, edit it, and Save triggers a download of the new version, which you then move into place yourself (e.g. overwriting the original in the Files app). GitHub and WebDAV work the same everywhere, including iOS, since they're plain HTTPS requests rather than filesystem access.

*Screen size*: this was built mobile-first — 44px touch targets, swipe-to-cycle-visibility, tap-to-reveal action menus instead of hover/right-click — and stays that way below 900px wide, byte-for-byte the same layout it's always had. Above 900px (a laptop or desktop browser window), two things change: opening Settings or Docs shows them in a *side panel* next to the outline instead of replacing it outright — there's room to see both at once, so replacing the whole screen for something like settings stopped making sense — and the app itself uses the full width of the window, at any width, rather than capping at some fixed value and leaving empty space on either side; the outline's own reading width follows suit by default too, deliberately — see *Reading width* below for why, and how to opt into a narrower column if you'd rather have one. Every other interaction — swipe, tap-to-reveal, the action menus — works identically at any width; this is a layout change, not a second UI. Resizing a browser window across the breakpoint while Settings/Docs is open switches between the two modes correctly rather than getting stuck in whichever one it started in.

*The side panel is resizable*, by dragging the thin divider between it and the outline (visible on hover, ~6px wide, cursor changes to signal it) — shrink it down for more outline room, or widen it to give Settings/Docs most of the screen if that's what you're actually working in at the moment. Neither side can be dragged below its own 280px floor, so one can't fully swallow the other. The chosen width is remembered across restarts (the same ~settings:sidePanelWidth~ persistence every other appearance preference already uses), but the panel itself is never a permanent fixture — it only exists at all, resizable or not, while Settings/Docs is actually open, exactly the same show/hide-on-toggle behavior as before this existed.

*Reading width* is unlimited by default — the outline uses the full available width, same as everything else in the app, rather than capping line length as an invisible default nobody asked for. If you'd still like a narrower, more traditional reading column, Settings → Appearance → *Reading Width* has an opt-in toggle and a ~ch~-based stepper (80ch to start, adjustable by 5 at a time). ~ch~ is a character-count-based CSS unit, not a pixel value — it's the width of the current font's own "0" character, so the same chosen line length holds steady as font size changes, rather than a fixed pixel cap silently getting cramped (or loose) as the two are adjusted independently of each other.

*No auto-capitalization, anywhere in this app.* Mobile Chrome and Safari both default to capitalizing the first letter of each sentence in a text field — every text input and textarea this app creates has that turned off, application-wide, in one place rather than field by field, since this app's own conventions (tags, properties, list markers, and most everyday capture text) are almost always lowercase and the automatic capital just gets in the way. A manual capital is still one tap away on the keyboard's own shift key, same as it always was — this only removes the automatic, unrequested kind.

*Tapping to edit a heading title or body opens the on-screen keyboard immediately on iOS, in one tap.* The mechanism: focusing the field is deferred via ~queueMicrotask~ to make sure the field exists in the DOM first, while still running before the browser considers the originating tap gesture over — WebKit specifically only allows a programmatic ~.focus()~ call to open the keyboard when it happens within that same synchronous gesture window; a ~requestAnimationFrame~ deferral falls just outside it, focusing the field without ever opening the keyboard.

*The top bar, and the modeline+minibuffer bar at the very bottom, both stay visually pinned to the actually-visible screen while the on-screen keyboard is open* (editing any body text, not just a heading title, opens one), on both iOS and Android (Android Chrome adopted the same behavior as iOS Safari as of Chrome 108) — a fixed-position element like either of them pins to the *layout* viewport, not the smaller *visual* viewport a keyboard actually leaves visible, and the browser auto-scrolling the page to bring a focused field into view would otherwise leave a fixed bar behind (the top bar) or beneath the keyboard, invisible (the bottom one). The ~visualViewport~ API (well-supported on both platforms since ~2019~) is the core mechanism — nudging the top bar down by exactly however much the visible area has shifted, and the bottom bar up by exactly how much of the layout viewport's own bottom edge the keyboard is currently covering. A single fix built purely on that API's own resize/scroll events isn't enough on its own: iOS 26 has a known, actively-tracked WebKit bug (filed with Apple; unpatched as of the sources checked, though a later point release may have addressed it since) where ~visualViewport.offsetTop~ can fail to reset back to 0 after the keyboard is dismissed on some devices, leaving either bar misaligned again on the way back down. Rather than depend on any one event source being perfectly reliable on every platform/browser combination, the same repositioning (both bars, from one shared set of triggers) runs from three independent triggers: the visualViewport events themselves, a plain window-level scroll/resize (catching whatever the browser's own default "scroll the focused field into view" behavior does at the layout-viewport level, independent of visualViewport's own timing), and a delegated check whenever any field gains or loses focus anywhere in the app, with a short delay either way to let the keyboard's own open/dismiss animation actually finish first — this last one specifically double-checks and re-corrects the iOS 26 stuck-offset case, rather than trusting the first attempt got it right.

** Keybindings
:PROPERTIES:
:CUSTOM_ID: keybindings
:END:

A practical subset for a keyboard/mouse device — genuinely inert on a phone or tablet (nothing to press these on), except a Bluetooth keyboard paired to a tablet, which they work correctly for too, same code path either way.

*Not a faithful reproduction of real org's own bindings*, deliberately: org leans heavily on the ~C-c~ prefix (~C-c C-t~, ~C-c C-s~, ~C-c C-d~, ...), and ~C-c~ / ~C-v~ / ~C-a~ / ~C-f~ and friends are universally reserved by every browser for copy/paste/select-all/find — they can't be reliably intercepted from a web page, and building shortcuts on that prefix would mean silently breaking copy-paste rather than a reasonable tradeoff. Real org's ~M-←~ / ~M-→~ (promote/demote) collide with the browser's own back/forward navigation the same way. Where the real org key is actually safe to use, it's used as-is; everywhere else this substitutes a different, safe key rather than pretending the conflict doesn't exist.

| Key | Action | Matches real org? |
|---+---+---|
| ~↓~ / ~↑~ | Move keyboard focus to the next/previous visible LINE -- any row (heading, paragraph, table, list item, block), not just headings. Moving down into a heading whose own body is currently folded reveals it first, landing directly on its own first body row rather than skipping past it. At the very first/last line, a status message says so rather than silently doing nothing | No direct equivalent |
| ~S-↓~ / ~S-↑~ / ~S-←~ / ~S-→~ | *Only when keyboard focus is on a table*: move to the next/previous row/column within it, cell by cell (the header row counts as a real, navigable row; a horizontal rule between rows doesn't). At the table's own edge, a status message says so rather than silently doing nothing. Outside a table, these aren't intercepted at all. Tapping a cell (not just arriving via ~↓~/Shift+arrow) also focuses it, so editing a cell directly by tap, then pressing ~Enter~ (commits) or ~Escape~ (cancels) to exit, leaves that same cell highlighted and ready for further Shift+arrow navigation either way — deliberately, not an oversight: Shift+arrow only ever receives a keypress once the cell's own textarea has lost focus (a browser can't deliver it to both at once), so clearing this the moment editing ends would leave Shift+arrow with nothing to navigate from at exactly the point it's normally used. A click landing on anything that isn't a table cell at all — another heading, a menu, empty background — clears it cleanly instead, with nothing left highlighted anywhere, the direct way to deselect a table once you're actually done with it | No direct equivalent |
| ~i~ | Enter edit mode for whatever the line-cursor is currently on (a heading's own title, a paragraph, a table cell, a list item), cursor positioned at the start of the line by default | Loosely inspired by vim's own ~i~, not a real org/Emacs binding |
| ~j~ | Move keyboard focus to the next visible heading specifically -- a faster heading-to-heading jump than ~↓~. A status message reports the boundary at the very first/last heading, same as ~↓~ / ~↑~ | No direct equivalent — the web/vim-style analog |
| ~k~ | Move keyboard focus to the previous visible heading specifically | Same |
| ~Tab~ | Cycle the focused heading's fold state | *Yes* — ~org-cycle~, exactly |
| ~Enter~ | Open/close the focused heading's action row | No equivalent (org has no "action menu" concept) |
| ~/~ | Focus the search box | Common web convention, not org-specific |
| ~Escape~ | Cancel an in-progress god-mode sequence, then exit god-mode, then clear keyboard focus, then enter god-mode (first applicable, in that order) | Not an org concept — a web convention, extended for god-mode below |

Keyboard focus is a separate concept from tapping a heading open — a thin highlight around the focused row, moved with ~↓~ / ~↑~ / ~j~ / ~k~, that the rest of the table's shortcuts act on. It starts unset; the first arrow / ~j~ / ~k~ press picks the first (or last) visible heading, and every shortcut after that requiring "the focused heading" simply does nothing until one exists. ~Tab~ here follows the same archived-heading rule as the swipe gesture (see [[#local-variables][Local Variables]]), not the chevron's force-open behavior — there's no keyboard equivalent to tapping the chevron specifically. None of this ever fires while actually typing in a text field — every shortcut above is disabled the moment any input or textarea has focus, and Ctrl/Cmd-held combinations are never treated as one of these shortcuts either, so the browser's own copy/paste/find/new-tab bindings are never at risk of a silent double-action.

*Cycling TODO state, moving a heading among its siblings, and promoting/demoting are all still fully available* — via god-mode ([[#god-mode][below]]: ~c t~, ~g↑~ / ~g↓~, ~g←~ / ~g→~ respectively) or a tap (the action menu). *Inserting a new heading* is available the same two ways too, though not as an exact substitute for the old ~n~ specifically: god-mode's own ~gRET~ inserts at the same level as whichever heading is currently focused (matching real org's own ~M-RET~ exactly), while the ⊕ button always inserts a genuinely new top-level one, same as ~n~ used to. Keeping both a plain shortcut and a god-mode sequence for the exact same action risked genuine confusion over which one was "the" way to do it — god-mode's own sequence is the one kept, since it's the only one that also generalizes to org's fuller keybinding set.

*** god-mode
:PROPERTIES:
:CUSTOM_ID: god-mode
:END:

An alternate input mode reaching real org's own fuller keybinding set (~C-c C-t~, ~M-RET~, and the rest) without the browser ever seeing an actual Ctrl/Alt combination held down — sidestepping the exact copy-paste/back-navigation collision the table above works around by substituting different keys instead. ~Escape~ toggles it on when nothing else needs it (see the table above for the full priority order). While active, every key is read as part of a sequence rather than triggering the plain shortcuts above; the minibuffer (see [[#modeline][Modeline and minibuffer]]) shows it's on and echoes the sequence typed so far. *Entering god-mode auto-focuses a heading if none is already focused* — the first visible one in the document, outlined so it's clear which heading every action below actually operates on — since god-mode's own actions all need a specific heading to act on, the same as the plain shortcuts above.

*Opening any overlay panel* (the extras menu, Settings, Docs, Capture, Search, the File/View/"More" menus, the undo History panel, or the single-month Calendar) *automatically exits god-mode* — none of these are separate "views," so without this, god-mode would otherwise keep silently intercepting every keystroke meant for that panel instead. The same awareness applies to the plain shortcuts above too: none of them act while one of these panels is open, and ~Escape~ closes whichever one is open first, rather than toggling god-mode underneath it.

Translation rules — this is a direct implementation of real god-mode.el's own actual, documented mechanism (github.com/emacsorphanage/god-mode), not an approximation invented for this app:
- A plain key defaults to Control — typing ~t~ alone means ~C-t~. This is the only default; every rule below is either an exception to it or a way to override it for one keystroke.
- ~g~ prefixes the next key with Meta — ~g↑~ means ~M-↑~. As in real god-mode, this means there's no way to type a bare ~C-g~ — ~g~ always means "the next key gets Meta."
- ~G~ (Shift+g) prefixes the next key with Control+Meta — ~Gn~ means ~C-M-n~.
- ~SPC~ (Space) is the literal key — it *toggles* literal mode, sticky: once on, every following key is typed with no modifier at all, until ~SPC~ is pressed again to toggle it back off. ~c SPC g~, for instance, means ~C-c~ followed by a literal ~g~ (~C-c g~), not ~C-c C-g~.
- A named key (arrow, Tab, Return) typed bare, with no ~g~ / ~G~ prefix and literal mode off, is never auto-controlled — ordinary cursor movement stays usable while god-mode is active.
- ~c~ (typed as the first key of a sequence, with none of the above overrides active) generates ~C-c~ and marks the rest of that sequence as an org-style chain: every further *letter* also auto-controls, matching how nearly every real org C-c binding is itself multi-key (~C-c C-t~, ~C-c C-c~) — but *punctuation* inside that same chain stays literal instead (~C-c .~, ~C-c |~), matching org's own bindings that mix the two. This one rule is this app's own necessary stand-in for what real Emacs gets for free from its own keymaps (~C-c~ is always a prefix key here, never a complete command by itself) — everything else above is real god-mode's own actual mechanism, unmodified. *Only one ~c~ is needed for any ~C-c C-<letter>~ command* — ~c t~, not ~c c t~, reaches ~C-c C-t~; the second ~c~ in ~c c~ is simply another letter auto-controlled by this same rule, which is why ~c c~ alone reaches ~C-c C-c~ specifically (a real, standalone org command in its own right) rather than being some special 2-key case.

| god-mode sequence | Emacs chord | Action |
|---+---+---|
| ~↓~ / ~↑~ | ~<down>~ / ~<up>~ | Move focus to the next/previous visible LINE -- any row, not just headings (matches the plain, non-god-mode shortcut exactly, including auto-revealing a folded heading's own body when moving down into it, and reporting the boundary via a status message at the very first/last line) |
| ~S-↓~ / ~S-↑~ / ~S-←~ / ~S-→~ | ~S-<down>~ / ~S-<up>~ / ~S-<left>~ / ~S-<right>~ | Table cell navigation -- see the plain-shortcut table above, same behavior |
| ~i~ | (not a real chord) | Enter edit mode for the current line, cursor at the start by default -- see below for ~a~ / ~e~ |
| ~a~ | ~C-a~ | Before pressing ~i~: the eventual cursor lands at the START of the line instead of the default |
| ~e~ | ~C-e~ | Before pressing ~i~: the eventual cursor lands at the END of the line instead of the default |
| ~Tab~ | ~Tab~ | Cycle the focused heading's fold state |
| ~S-Tab~ | ~S-Tab~ | Cycle the whole document's fold state (two-state: overview / fully shown) |
| ~g↑~ / ~g↓~ | ~M-↑~ / ~M-↓~ | Move the focused heading up/down among its siblings |
| ~g←~ / ~g→~ | ~M-←~ / ~M-→~ | Promote/demote the focused heading (and its subtree — this app doesn't distinguish single-heading from whole-subtree) |
| ~gS-←~ / ~gS-→~ | ~M-S-←~ / ~M-S-→~ | Same as above — no separate "whole subtree" action exists to map to |
| ~c f~ / ~c b~ | ~C-c C-f~ / ~C-c C-b~ | Move focus to the next/previous heading at the same level -- reports via a status message when there is none |
| ~c u~ | ~C-c C-u~ | Move focus to the parent heading -- reports via a status message when already at the top level |
| ~c n~ / ~c p~ | ~C-c C-n~ / ~C-c C-p~ | Move focus to the next/previous visible heading, at any level |
| ~c x w~ | ~C-c C-x C-w~ | Cut the focused heading and its entire subtree to the clipboard, then delete it (~org-cut-subtree~) |
| ~c x y~ | ~C-c C-x C-y~ | Paste a subtree from the clipboard as a sibling right after the focused heading, at the focused heading's own level -- every level within the pasted content shifts by whatever amount makes that true, preserving its own internal structure (~org-paste-subtree~) |
| ~gRET~ | ~M-RET~ | Insert a new heading after the focused one, at the same level |
| ~gS-RET~ | ~M-S-RET~ | Same, with a TODO keyword set |
| ~c t~ | ~C-c C-t~ | Cycle the focused heading's TODO state — or, with no current state and more than one ~#+TODO:~ workflow, open a state picker instead (see below) |
| ~c ,~ | ~C-c ,~ | Cycle the focused heading's priority (None → A → B → C → None) |
| ~c v~ | ~C-c C-v~ | Switch to the TODO view (closest match to a sparse TODO tree) |
| ~c .~ / ~c !~ / ~c d~ / ~c s~ | ~C-c .~ / ~C-c !~ / ~C-c C-d~ / ~C-c C-s~ | Open the focused heading's details editor (where SCHEDULED/DEADLINE/timestamps live) |
| ~c SPC a~ | ~C-c a~ | Open the Agenda view |
| ~c SPC c~ | ~C-c c~ | Open Capture (see below — exits god-mode and offers hotkey template selection) |
| ~h SPC i~ | ~C-h i~ | Open Help/Docs — see below, doesn't exit god-mode (real Emacs's own actual Info binding) |

Sequences that are valid god-mode input but have no equivalent in this app yet report that plainly rather than silently doing nothing or approximating something misleading: ~c c~ (checkbox toggling / code-block execution — both need a finer keyboard focus than a heading), ~c |~ and the table row/column-insert sequences (use the always-visible +row/+col controls below any table instead), ~c SPC l~ / ~c l~ / ~c o~ (no link-insertion or cursor-based link-opening command exists), and ~c e~ (use More → Export instead).

*~c SPC c~ (Capture) and ~c t~ on a heading with no current TODO state and more than one workflow both exit god-mode and hand off to a hotkey-driven picker*, rather than staying in god-mode's own chord system — real org's own actual ~C-c c~ works the same way: the keybinding itself never reads a template letter, the command it invokes does that as its own separate, subsequent prompt once already running. Both pickers here work the same way: opening one shows every option (capture template, or TODO state) as normal, tappable buttons, and — since this came from god-mode, a keyboard-driven context — also labels each one with its own single-character hotkey, typeable immediately without needing to reach for a tap at all. *A hotkey only appears, and is only ever accepted, when it doesn't collide with another option's own key* — if two capture templates (or two TODO states, even across different ~#+TODO:~ workflows shown in the same picker) happen to share a key, neither gets a hotkey at all; that specific choice becomes tap-only rather than guessing which one a keypress meant. Opening either picker any other way (a plain tap, the ⋮ Capture button, tapping a TODO-less heading's own badge directly) never shows hotkeys — they're a god-mode-specific convenience, not a general feature of these pickers. ~Escape~ still cancels either picker, same as any other panel.

*~h SPC i~ opens Help/Docs* — real Emacs's own actual ~C-h i~ binding (Info, "Enter Info, the documentation browser"), and, unlike Capture/TODO above, *doesn't exit god-mode*: reading a help page shouldn't cost you an active sequence you were in the middle of building. While it's the only thing open, god-mode keeps working completely normally underneath it — further sequences keep reaching god-mode's own dispatch exactly as if Help weren't showing, and ~Escape~ follows god-mode's own usual priority (cancel a sequence, then exit god-mode) rather than closing Help specifically. Opening any other panel, or exiting god-mode, returns to the ordinary rule (keystrokes and ~Escape~ act on whatever's open, Help included) — the exception applies only for as long as Help is the sole thing on screen and god-mode is still active.

*~i~ / ~a~ / ~e~ bypass god-mode's own chord system entirely* — they're not translated into any Control/Meta chord at all (unlike everything else on this page), loosely inspired by vim's own modal-editing keys rather than any real Emacs binding. This only applies at the very START of a fresh sequence, with nothing else pending — typed as the second (or later) key of a deliberate sequence, they behave completely normally instead: ~g i~ still reaches ~M-i~, ~c i~ still reaches ~C-c C-i~ within the chain. ~a~ / ~e~ on their own do nothing visible — they just set where the cursor will land the next time ~i~ is actually pressed, exactly as ~C-a~ / ~C-e~ would in real Emacs before typing. Once ~i~ has actually entered edit mode, left/right (and every other key) work exactly as normal browser text-field editing — nothing in this app intercepts them there at all, in either mode; ordinary typing always takes priority over any keyboard shortcut the moment an actual text field has focus.

** Differences from Emacs org-mode
:PROPERTIES:
:CUSTOM_ID: differences-from-emacs-org-mode
:END:

This is the section to read if you know org-mode well and want to know exactly where org-pwa is a subset, a simplification, or just plain different.

*Interaction model.* Touch-first, primarily: tap-to-reveal actions and gestures (swipe-left to cycle fold) are the primary interaction model, not a keyboard-driven one. A practical subset of plain keyboard shortcuts exists for non-touch devices, plus god-mode — a toggled, modal key-sequence layer reaching real org's own fuller keybinding set (~C-c C-t~, ~M-RET~, and more) without the browser ever seeing an actual Ctrl/Alt combination held down (see [[#god-mode][god-mode]]). Still no command equivalent to ~M-x~, and god-mode's own action table covers headings, TODO/priority, and navigation specifically — not table cells, per-list-item checkboxes, or link insertion, each reported plainly as unsupported rather than silently doing nothing.

*Folding.* org-pwa's fold model is three flags per heading (~collapsed~, ~bodyHidden~, and ~drawersHidden~), not Emacs's richer subtree-visibility state machine. It's enough to implement ~overview~ / ~content~ / ~showall~ / ~showeverything~ correctly — including the real distinction between ~showall~ (drawers/blocks still folded) and ~showeverything~ (everything open) — but doesn't have a direct equivalent to cycling through every intermediate visibility Emacs supports.

*Priority.* Priority cookies (~[#A]~) have dedicated UI in the general editor (A/B/C/None buttons — see [[#editing-your-outline][Editing your outline]]), not just parsed-and-preserved on round-trip. Editing a heading's title directly through the outline UI still treats the whole string as literal title text rather than re-parsing it for a priority cookie — set priority through the dedicated buttons, not by typing ~[#A]~ into the title field.

*Tags.* Tags have dedicated UI in the general editor — removable chips plus an add button, not a full-replace prompt where you'd retype the whole space-separated list. Not org-mode-style completion against tags used elsewhere in the file, though. One related quirk, still true: if you type something that /happens/ to look like a tag — ending in ~:word:~ — into the /title/ field specifically, it'll be re-interpreted as a tag on next parse, since org-pwa can't tell "literal colons in a title" from "a tag" once it's back in the file as text. Editing tags through the dedicated chips doesn't have this problem.

*Properties.* Property drawers have dedicated UI too — individual key/value rows in the general editor, each with its own add/remove, not a full-replace text block. Not real org-mode-style value completion, and no special handling or validation for the properties org itself treats specially (~CUSTOM_ID~ still has its own separate, simpler action; things like ~ARCHIVE_*~ properties round-trip fine and are surfaced with real meaning for archiving/restoring — see [[#archiving][Archiving]] — but nothing else treats them specially).

*Inheritance.* Tags and properties both support ancestor inheritance for search/filter purposes, matching real org's own actual defaults exactly: tag inheritance is *on* by default (~org-use-tag-inheritance~) — a ~tag:~ search filter matches a heading whose tag comes from an ancestor, not just its own, the same as real org's "if a heading has a certain tag, all subheadings inherit the tag as well". Property inheritance is *off* by default (~org-use-property-inheritance~) — a ~key:value~ filter only looks at a heading's own properties unless turned on, since real org itself doesn't enable this by default either ("it can slow down property searches and is often not needed"). Both are simple ~t~ / ~nil~ booleans here rather than real org's fuller list-of-tags/regexp value space for either variable — a stated simplification covering the common on/off case. Inheritance is a search-time concept only, matching real org's own UX — it doesn't change what's /displayed/ on a heading (no inherited tag badges shown inline), only what a filter search matches against. See [[#local-variables][Local Variables]].

*Archiving.* The ~org-archive-subtree~ move, confirmation dialog, and full restore/unarchive are all built now — see [[#archiving][Archiving]] for the complete behavior, including ~org-archive-location~'s own headline-part target at an arbitrary single level (not just level 1) via its own asterisk count, matching real org's own actual documented behavior exactly. Refile ([[#refile][see above]]) now covers the general "move a subtree to an arbitrary destination" case, including moving something back out of an archive file by hand.

*Checkbox progress cookies.* ~[2/5]~ or ~[40%]~ now auto-recalculates on toggle/add/delete, matching real org-mode's default hierarchical counting. A heading's own ~:COOKIE_DATA:~ property is now read and acted on too — ~checkbox~ / ~todo~ mode selection and ~recursive~ TODO-counting scope, matching real org's own actual documented behavior (see [[#lists-tables-and-body-text][Lists, tables, and body text]] for the full behavior).

*Tables.* ~#+TBLFM:~ formulas are now evaluated — see [[#table-formulas][Table formulas]] for the full behavior, including exactly what's in scope (arithmetic plus a handful of aggregate functions) and out (Emacs Calc compatibility beyond that, a deliberate, documented scope cut, not an oversight).

*Footnotes.* Both reference forms (~[fn:label]~ and inline ~[fn:label:definition]~ / ~[fn::anonymous]~) and the separate-definition-line convention work, with tap-to-jump navigation between a reference and wherever its definition actually lives. What's different from real Emacs: no ~org-footnote-new~ / ~org-footnote-normalize~-style commands (auto-inserting a new footnote at point, renumbering/sorting existing ones, converting between the inline and separate-line forms) — editing a footnote means editing its raw text directly, the same as any other inline markup here. No integration with ~org-ref~ / ~org-cite~-style citation footnotes either.

*Progress logging.* ~org-log-done~ and the general per-keyword ~!~ / ~@~ / ~@/!~ / ~/!~ logging spec are both built, writing into a shared ~:LOGBOOK:~ drawer, including the conditional leaving-log semantics (a state's own leaving-timestamp only fires when the target state doesn't already log its own entry) — see [[#progress-logging][Progress logging]] for the full behavior. Fast-access keys (~TODO(t)~) work as keyboard shortcuts within the multi-workflow picker described above, when a file has more than one ~#+TODO:~ sequence; tap-to-cycle remains how a single-workflow file's state actually changes, same as always.

*Clocking* (see [[#clocking][Clocking]] for the full behavior) covers the core ~org-clock-in~ / ~org-clock-out~ / ~org-clock-cancel~ / ~org-clock-display~ / ~org-clock-report~ commands. What's different from real Emacs: no persistent mode-line display of the running clock, no clock-continue, and no effort estimates.

*Agenda.* Day/Week/Month views, repeating-timestamp expansion, completed-item exclusion, SCHEDULED/DEADLINE carry-forward with a visible overdue count, the delay/warning-period suffix making a deadline show up early (SCHEDULED's own delay suffix instead pushes its appearance /later/ — the opposite direction, real org's own actual behavior), multi-file aggregation via ~org-agenda-files~, marking a repeating task done shifting its date by the repeater's own interval rather than actually completing it (with the three repeater marks genuinely distinguished for this specific case), fifteen fixed diary-sexp forms (~org-contacts-anniversaries~, ~org-anniversary~, ~org-cyclic~, ~diary-float~, ~org-block~, ~diary-sunrise~, ~diary-sunset~, ~diary-civil-dawn~, ~diary-civil-dusk~, ~diary-nautical-dawn~, ~diary-nautical-dusk~, ~diary-astronomical-dawn~, ~diary-astronomical-dusk~, ~diary-day-length~, ~org-weather~), and real org's own general ~<%%(sexp)>~ timestamp mechanism — combining ~when~, this app's own ~today-p~ convenience predicate, real elisp's own ~format~, and the string-returning subset of those same functions as genuine sub-expressions (see [[#agenda-sexp-timestamps][General <%%(sexp)> timestamps]]) — are all built now (see [[#agenda][Agenda]]). What's still different from real org: the three repeater marks (~+~, ~++~, ~.+~) still all expand identically for the agenda's own DISPLAY of a still-incomplete task's future occurrences (distinct from the completion-time shift above), since that's a read-only display with no notion of "when was this marked done" driving a catch-up/restart calculation there; the sexp-timestamp evaluator supports only the functions/forms documented above, not a real elisp interpreter; and ~org-agenda-files~ only supports GitHub/WebDAV entries, not a local file, for the same picker-permission reason stated throughout this document (see [[#agenda][Agenda]] for the details).

*No babel, no command palette.* These were scoped early on as possible future work and never built.

*Undo/redo* covers every edit now (see [[#undoredo-and-history][Undo/redo and History]]) — snapshot-based (one step per completed edit action, not per keystroke), not persisted across a reopen, by explicit design choice. What's different from real Emacs: no per-buffer undo tied to Emacs's own undo-tree machinery, and no attempt to preserve fold state across an undo/redo jump (it reapplies the file's own ~#+STARTUP~ visibility fresh each time instead, same as reopening the file does). Headings /can/ be reordered now (see above) — but only via the dedicated Move/Promote/Demote actions, not by dragging.

*Search* looks at the whole document (see [[#searching][Searching]]), with an optional regex mode, but no search-and-replace and no filtering the outline view down to just the matches (it's a separate results list, not a live-filtered tree).

*Export* (see [[#export][Export]] for the full behavior) covers ASCII, Markdown, HTML, ODT, and Calendar (.ics) — the whole file or (ASCII/Markdown/HTML/ODT) a single heading's subtree — with PDF available via the browser's own print dialog on the exported HTML rather than a separate hand-rolled PDF path. What's different from real org's own export backends: no LaTeX or other document formats beyond what's built (ODT covers the "open in a word processor" case real org would use ~ox-odt~ for); and ASCII export doesn't implement ~ox-ascii~'s fuller feature set (Latin-1/UTF-8-specific character substitutions, ~:width~-configurable horizontal rules, left/right/center justification blocks) — a plain, readable, width-wrapped rendering of the outline, not full fidelity with real org's own backend.

*Refile* (see [[#refile][Refile]] for the full behavior) covers the core ~org-refile~ case — moving a subtree to become the last child of a chosen target, anywhere in the current file or another configured one. What's different from real org: only ~:level~ / ~:maxlevel~ target matching (no ~:tag~ / ~:todo~ / ~:regexp~), no most-recent-targets history, and no creating a brand-new destination heading by typing a name that doesn't exist yet — picking from the existing outline is the only way in.

*Attachments* (see [[#attachments][Attachments]] for the full behavior) — this app's own extension, not a faithful ~org-attach~ port: no attachment browsing/listing/deletion UI, no ~org-attach-dired~-equivalent bulk operations, and only works with GitHub or WebDAV connected (the same platform limitation Agenda Files, cross-file Archive, and cross-file Refile all already have) rather than real org-attach's own filesystem-agnostic approach.

*Single document at a time.* Opening a different document — via a ~file:~ / ~github:~ / ~webdav:~ link, tapping an Agenda item or a search result that belongs to a different file, or File → Open — always replaces what's currently showing; there's no true simultaneous multi-document editing (several documents open/dirty/rendered at once, tab-bar style). Reading/aggregating across ~org-agenda-files~ (see [[#agenda][Agenda]]) for display, and capture-to-file (see [[#capture-templates][Capture Templates]]), both work across multiple files without needing any of them to become the active document just to be read from or written to — only actually navigating to a specific result inside one switches to it.

*Conflict resolution* is a plain confirm dialog (keep mine / keep the other version), not a diff or three-way merge view.

** Known limitations / not built yet
:PROPERTIES:
:CUSTOM_ID: known-limitations--not-built-yet
:END:

Restated in one place for scanning:

- No LaTeX or other document export formats beyond ASCII, Markdown, HTML, and ODT (PDF is covered via the browser's own print dialog on the exported HTML, see [[#export][Export]]) — this is about exporting a whole document *to* LaTeX as a target format, a different thing entirely from LaTeX math fragments rendering *within* a document, which is built (see [[#latex-fragments][LaTeX math fragments]]); ASCII export doesn't implement real org's ~ox-ascii~ fuller feature set (Latin-1/UTF-8-specific character substitutions, ~:width~-configurable horizontal rules, left/right/center justification blocks)
- Refile only matches ~:level~ / ~:maxlevel~ targets (no ~:tag~ / ~:todo~ / ~:regexp~), no most-recent-targets history, and no creating a new destination heading by typing a name — see [[#refile][Refile]]
- Search regex mode is JavaScript RegExp, not Emacs regex syntax — no search-and-replace, no filtered tree view
- No footnote commands (~org-footnote-new~ /normalize/sort/renumber) — editing a footnote means editing its raw text directly
- No persistent mode-line clock display, clock-continue, or effort estimates — see [[#clocking][Clocking]] for what IS built (~org-clock-in~ / ~org-clock-out~ / ~org-clock-cancel~ / ~org-clock-display~ / ~org-clock-report~)
- ~org-xx-extra-menu~'s function-reference entries only recognize ~'org-clock-out~, ~'org-clock-cancel~, ~'org-xx-calendar~ (this app's own single-month calendar overview, not a real org-mode function), ~'org-table-recalculate-buffer-tables~ (real org's own actual, distinct command — see [[#table-formulas][Table formulas]]), ~'org-cut-subtree~, and ~'org-paste-subtree~ today — an unrecognized function name is silently skipped rather than an error, so more can be added over time without breaking anything already configured — see [[#extras-menu][Extras menu]]
- No drag-to-reorder (button-based Move/Promote/Demote actions exist instead — see [[#editing-your-outline][Editing your outline]])
- No dedicated "browse your recently-opened documents" switcher UI — switching between documents happens by tapping a ~file:~ / ~github:~ / ~webdav:~ link or File → Open, not a tab bar or history list; and no true simultaneous multi-document editing (see [[#differences-from-emacs-org-mode][Differences from Emacs org-mode]] for the full explanation)
- Agenda's own display-time expansion of a still-incomplete, repeating task's future occurrences doesn't distinguish the three repeater marks (~+~ / ~++~ / ~.+~) — they're only genuinely distinguished when a task actually gets marked done, see [[#agenda][Agenda]]; fifteen fixed diary-sexp forms are supported (~org-contacts-anniversaries~, ~org-anniversary~, ~org-cyclic~, ~diary-float~, ~org-block~, ~diary-sunrise~, ~diary-sunset~, ~diary-civil-dawn~, ~diary-civil-dusk~, ~diary-nautical-dawn~, ~diary-nautical-dusk~, ~diary-astronomical-dawn~, ~diary-astronomical-dusk~, ~diary-day-length~, ~org-weather~), plus a general ~<%%(sexp)>~ timestamp mechanism combining ~when~ / ~today-p~ / ~format~ / the string-returning subset of those same functions (see [[#agenda-sexp-timestamps][General <%%(sexp)> timestamps]]) — not a full elisp interpreter, only what's documented there
- Local/relative images resolve and render on GitHub/WebDAV; on local files (File System Access) and iOS import, still a placeholder (same picker-permission limitation as archiving/capture-to-file)
- Conflict resolution has no diff/merge view
- No File System Access support on iOS (by platform limitation, not a bug — see [[#platform-support][Platform support]])
- god-mode's own action table covers headings, TODO/priority, navigation, and a handful of other actions — not table cells, per-list-item checkboxes, code-block execution, or link insertion, each reported plainly rather than silently doing nothing (see [[#god-mode][god-mode]])
