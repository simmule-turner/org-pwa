#+TITLE: Changelog
#+STARTUP: overview

Highlights only — the "why", not every line changed. Newest first. Each
entry is tagged with the service worker cache version it shipped in
(=sw.js='s own =CACHE_NAME=), so "which build has this" is always a
direct lookup rather than a guess.

* v332 — Revert: speech-to-text (v330, v331)
Removed entirely. Every text field already gets dictation for free
from the OS keyboard itself on iOS and Android — the mic key on the
iOS keyboard, Gboard voice typing — including fields the custom
version didn't even reach (table cells, property values). The custom
Web Speech API integration was redundant surface: four separate UI
touchpoints, real browser-support gaps to track (none at all in
Firefox), and a permission-denied error path, duplicating a platform
capability with already-broader reach.

* v331 — Speech-to-text: the log-note prompt
Extends last release's speech-to-text button to the note prompt shown
when marking a TODO done (or any other transition whose own logging
spec asks for a note). Table cells, property values, and the GitHub/
WebDAV credential fields were reconsidered too, and deliberately left
without it — none are a fit for dictation.

* v330 — Speech-to-text dictation
A 🎤 toggle button now dictates directly into heading title/text
editing, the plain-text editor (View > Text), and each capture
template prompt field, wherever the browser supports speech
recognition (absent entirely on Firefox, otherwise present). Runs
continuously with live interim text, cleanly replaced as each phrase
is confirmed rather than duplicated.

* v329 — Fix: inf showed as "Infinity" with a format spec
Last release's own inf fix only covered formulas with no explicit
format spec — a formula like `if($1==90, inf, tan($1));f4` still
showed JS's own "Infinity" instead of "inf". Fixed everywhere a result
gets formatted, including duration and fraction display, not just the
one spot that was reported.

* v328 — inf constant, and #ERROR for undefined math
#+TBLFM: formulas now support inf, matching pi's own built-in
treatment. Also: division by zero, sqrt of a negative number, ln/log10
of a non-positive number, and out-of-range arcsin/arccos now produce
#ERROR in that cell instead of silently returning 0 — confirmed
against the real Calc manual that these are genuine errors under
Calc's own default settings, which is what real org table formulas
actually use.

* v327 — Table formulas: pi and named constants
#+TBLFM: formulas can now use pi directly, and $name to reference a
named constant defined on a #+CONSTANTS: line (e.g. #+CONSTANTS:
c=299792458, then $1*($c^2) in a formula) — matching real org's own
documented syntax for both.

* v325 — Table formulas: trig, logs, and D/R angle mode
#+TBLFM: formulas now support sin/cos/tan, arcsin/arccos/arctan, ln,
log10, log(x, base), exp, and exp10 — matching real Calc's own exact
names (arcsin, not asin) and default semantics (degrees by default,
matching real org's own documented default) wherever feasible, so
nothing here reads as a "new" or surprising name to anyone who knows
real org-mode. New ;D/;R mode flags switch angle mode explicitly.

* v324 — Fix: stale file when exporting Contacts (.vcf)
A file listed in both org-agenda-files and org-contacts-files could
export with outdated content, since the two lists cached that same
file completely independently, with no awareness that an update
reflected in one had happened at all. Both Contacts (.vcf) and
Calendar (.ics) export now always fetch every configured file fresh
at export time, rather than trusting whatever happened to already be
cached.

* v323 — Contacts (.vcf) export: one screen instead of two
The name filter added last release was its own separate step before
the scope choice — clunky and awkward. Both now live on the same
screen: type a filter (or leave it blank) and tap a scope option
directly, no extra "Continue" step in between.

* v322 — Contacts (.vcf) export: filter by name
Contacts (.vcf) export now has an optional name filter, matched
against each contact's own heading title, with a toggle between a
plain "contains" match and full regex — matching real org-contacts'
own NAME argument, confirmed directly against its actual source.
Leave it empty to export everyone, same as before.

* v321 — Fix: narrow + edit + Save + widen lost the rest of the buffer
Narrow a heading, switch to Text view, edit it, Save, then switch back
to Org view — Widen would disappear and the whole document collapsed
down to just the narrowed heading's own content. Saving while narrowed
correctly commits the edit, but a second, internal commit step
triggered by switching views right after was incorrectly treating the
same edit as a fresh whole-document replacement. Fixed at the source;
also verified correct across multiple edits and saves in a row while
staying narrowed.

* v320 — Contacts (.vcf) export
New "More > Export > Contacts (.vcf)", matching real org-contacts.el's
own org-contacts-export-as-vcard: any heading with a non-empty EMAIL
property (and not marked :IGNORE: t) becomes a vCard, with PHONE/CELL,
WORK_PHONE, ADDRESS, NICKNAME, NOTE, and BIRTHDAY all mapped to their
matching vCard fields. New org-contacts-files setting, for pulling
contacts from additional files beyond the one currently open — same
syntax and behavior as the existing Agenda Files setting, kept as its
own independent list since the two commonly differ.

* v319 — Dark-mode popup contrast: bigger shift
The lighter popup background shipped in v318 wasn't different enough
from the page behind it to actually notice. Now a bigger step up
(#36383c vs the page's own #16181c), picked directly from a side-by-
side comparison of a few shift sizes.

* v318 — Fix: low popup/dark-mode contrast
Every modal and dropdown menu's own background was the exact same
color as the page behind it in dark mode, leaving nothing but a faint
border for separation. Popups now use a distinctly lighter background
than the page in dark mode, so it's clearly visible as its own
surface rather than blending into the backdrop. Light mode unchanged.

* v317 — Fix: Archive > Refile (and other modals) completely unusable
The previous release's own modal conversion (v316) broke Refile, the
TODO workflow picker, the audio-recording panel, the calendar picker,
and Capture entirely — buttons were visible but not actually
clickable, with no way to interact with or exit the popup at all.
Root cause: these modals were nested inside the top bar, which is
harmless for a small inline panel but clips a full-screen overlay's
own hit-testing once it's converted to one. Moved all three out to be
direct children of the page instead. Also added a Close/Cancel button
to two states (the capture-template list, and refile's own "loading
targets" step) that never had one at all, even before last release —
harmless as a small inline panel, but a real dead end once it became
a full-screen overlay.

* v316 — Refile and other panels are proper modals now
Refile, the TODO workflow picker, the multi-attachment file picker,
the audio-recording panel, the calendar date picker, the capture-
template form, and the mark-as-DONE note prompt all used to be thin,
edge-to-edge inline panels — hard to distinguish from the background,
especially in dark mode. All seven are now bordered, centered modal
popups with a dark backdrop, matching the general editor's own
established look exactly, so it's immediately clear there's something
to act on.

* v315 — Fix: tab-switch data loss, and banners hidden while scrolled
Two fixes. First, a severe, confirmed data-loss bug: switching tabs
could show the wrong tab's own content in Text view (whichever tab's
textarea happened to render most recently), and saving in that state
overwrote the active tab's document with the other tab's content
entirely. Not specific to narrowing — narrowing just made the
consequences dramatic and immediately visible rather than subtle.
Switching tabs now correctly commits any pending edit and rebuilds
fresh from the newly-active tab's own state, rather than silently
reusing whatever was left over from before. Second, the "file changed
elsewhere" and "new version available" banners no longer scroll out
of view along with the document — they're now pinned directly under
the tabs regardless of scroll position, matching every other
always-visible part of the top bar.

* v314 — Settings > Extras menu / Menu labels: multi-line by default, and genuinely stable
Both fields now show and edit as one double-quoted entry per line with
a trailing backslash — matching this app's own documented file-based
syntax for them — instead of one long run-on line. This also fixes
the actual bug behind that old single-line display: saving now
re-tokenizes and rebuilds a canonical value rather than storing
whatever raw text was in the box, so the value stays exactly as
entered across a reload instead of silently collapsing back to one
line the way it used to.

* v313 — Fix: the previous "unsaved changes" fix still missed tags
The previous fix for the general editor silently discarding unsaved
changes (v312) had its own bug: the pending-changes check stored a
live, mutable reference instead of a frozen copy, so adding a tag
never actually registered as a change — the exact scenario reported.
Fixed at the root: the check now captures an immutable string
snapshot the instant the editor opens, rather than an object that
could still be mutated later out from under it. Verified this time
against all nine ways the editor's fields can change, across all
three action buttons (Add table, Delete table, Attach).

* v312 — Fix: general editor silently discarded unsaved changes
Tapping Add table, Delete table, or Attach inside the general editor
used to silently discard any unsaved field edits (priority, tags,
scheduled/deadline, properties) — none of the three ever checked for
or committed pending changes before proceeding. Now, if anything's
actually changed, a prompt offers a real choice: commit those changes
and continue, discard them and continue, or go back and keep editing.
With nothing changed, all three proceed exactly as before, no
interruption. Also removed the icons from these three buttons, for
consistency with the plain-text Cancel/Reset/OK row in the same modal.

* v311 — Attach moves into the general editor; Narrow/Widen moves to the action menu
📎 Attach is now a button inside the general editor (📋 Edit details)
instead of its own separate action-menu item — its own behavior is
completely unchanged, just relocated. Narrow/Widen moves the other
way: out of the More menu and into the per-heading action menu,
replacing Attach's own vacated slot there. Shows 🔽 Narrow on any
heading that isn't currently narrowed to, or 🔼 Widen specifically on
the one heading that is.

* v310 — Modal popups: general editor, Archive, Attach
The general editor (📋 Edit details — SCHEDULED/DEADLINE/plain
timestamp, tags, priority, properties) is now a modal popup instead of
an inline row-expansion panel, with a Cancel/Reset/OK button row
replacing the old Save/Cancel pair. Reset genuinely restores every
field back to its on-entry value without closing the editor.
Archive's own confirmation prompt and Attach's own first-level choice
are both modal popups now too, replacing their previous small,
in-flow panel — their own buttons and behavior are otherwise
unchanged.

* v309 — Toolbar reorganization: Search, Help, and History move
Search (=🔍=) and Help (=❓=) are now direct top-bar buttons instead
of items buried in the More/View menus — Search sits next to the View
menu button, Help right before it. History moved from the View menu
into the More menu instead. The top bar itself is restructured to
match: File and Save stay left-aligned, and everything else (=+=,
=❓=, =🔍=, the View menu button, the More menu button) is now
right-aligned as one group, replacing the old layout that centered
the =+= button between two spacers.

* v308 — Narrowing (org-narrow-to-subtree / widen)
More → Narrow restricts the outline to one heading and its own
subtree — every sibling, ancestor, and unrelated heading disappears
from view entirely. A persistent =Narrowed to: TITLE — Widen= banner
stays visible the whole time; the same god-mode chords real org uses
(=C-x n s= / =C-x n w=, typed as =x SPC n s= / =x SPC n w=) work too.
This is a display restriction only — =state.doc= itself is never
touched, so Save/Export/Agenda/Search all keep operating on the whole
document regardless of what's narrowed. The narrowed heading is
tracked live, so it follows a promote/demote/move rather than
becoming stale, and auto-widens if it's deleted outright. Narrowing
genuinely persists — across tab switches, and across actually closing
and reopening the app. =View → Text=, while narrowed, shows and edits
just the narrowed subtree's own raw text instead of the whole file,
splicing the result back into its own exact original position on
commit.

* v307 — Discard symbol, full-screen History, %Z/%z
Three changes. The table-cell discard button now shows =⎌= (the
universal undo symbol) instead of =×=. History is now a full-screen
view matching Settings exactly — on a narrow layout it replaces the
outline entirely instead of sitting as a small panel with content
scrolling behind it; on a wide layout it renders into the side panel
alongside the outline, same as Settings and Docs already do. Added
=%Z= (alphabetic timezone abbreviation, e.g. =EDT=) and =%z= (numeric
UTC offset, e.g. =-0400=) to both =%<FORMAT>= and
=format-time-string()= — under =format-time-string()='s own UTC flag,
both correctly resolve to =UTC=/=+0000= rather than the device's own
real local timezone.

* v306 — Editing: one consistent, explicit-confirm interface everywhere
Every text-editing surface in the app now uses one of two deliberate
patterns instead of a mix of implicit blur-commits and three
different button sets. Heading titles, list items, and paragraphs all
use the same popup Edit heading text and Settings' own Menu labels
editor already used — Cancel / Reset / OK, same size, same behavior.
WebDAV/GitHub and the Capture prompt form were brought in line with
this same button convention too. Table cells stay inline — a real
"tap the next cell to commit and move on" workflow would have broken
under a modal — but gained a small *×* button right next to the field
while editing: the one genuinely mobile-friendly way to back out of a
cell edit, since neither iOS's nor Android's on-screen keyboard
exposes an Escape key at all. Also fixed two regressions caught before
shipping: a runtime error from an invented element ID, and table
cells silently losing real keyboard focus after being reverted from
modal back to inline.

* v305 — Edit heading text: now matches Settings' own Menu labels editor
The heading action menu's own *Edit text* — editing a heading's
combined body text as one block — is now a popup matching Settings'
own Menu labels editor exactly, instead of an inline textarea with no
buttons that committed on blur or cancelled on Escape. Same size, same
three explicit buttons: *Cancel* discards and closes, keeping the
prior text; *Reset* reloads the original text and keeps the popup
open for continued editing; *OK* saves and closes.

* v303 — THE BUG THIS FIXES: date-to-time() on a timestamp with a time-of-day
=date-to-time($ref)= on a cell holding this app's own native org
timestamp (=<...>=/=[...]=) produced =#ERROR= whenever the timestamp
had a time-of-day component — =$2=now()= followed by
=date-to-time($2)= being the exact real-world case that surfaced it.
Root cause: this function was relying on JS's own =Date.parse()= for
org's bracketed format too, which turns out to tolerate stray =<=/=>=
characters around a single, unambiguous date purely by an
undocumented accident, and breaks outright the moment a time is also
present. Fixed by trying the same dedicated org-timestamp parser
=date()= already uses first, falling back to =Date.parse()= only for
the genuinely different formats (ISO 8601, email headers, US dates)
it's actually meant for.

* v302 — date-to-time / format-time-string: restored to their real names
Reverted the previous release's own =date_to_time=/=format_time_string=
back to =date-to-time=/=format-time-string= — real Emacs Lisp's own
literal, hyphenated names. A working solution for this exact naming
had already been built earlier (a small, isolated tokenizer exception,
since this app's own formula language always treats =-= as the
subtraction operator), but got reverted by mistake while picking the
feature back up mid-session. No functional change beyond the spelling
— everything from v301 works identically, just reachable under its
real name again.

* v301 — Table formulas: date_to_time, format_time_string, fraction mode
Three new table-formula capabilities. =date_to_time(ref)= is real
Emacs's own =date-to-time=, parsing a much wider variety of date/time
strings than =date()= does — ISO 8601, RFC 822/2822 email-header
dates, and common US formats. =format_time_string(fmt, time, utc)= is
real Emacs's own =format-time-string=, using the exact same
=%<FORMAT>= codes capture templates already support, with an optional
UTC flag. Both are spelled with underscores rather than real Emacs's
own literal hyphens — this app's own formula language treats =-= as
the subtraction operator, so a hyphenated function name isn't
reachable as a single token at all. =;F= (Fraction Mode) and =;FS=
(mixed numbers) are new mode flags: =$1/$2;F= on 3 and 6 shows =1/2=
rather than =0.5=; =;FS= on an improper fraction shows a mixed number
instead, e.g. =3 + 1/2=.

* v300 — Capture: same treatment as Export/Clocking
More → Capture's own template picker is now a step within the same
More menu, matching Export and Clocking exactly — one plain row per
configured template, using its own description as the label, rather
than a separate popup with a two-column grid. Picking a template with
prompts to fill in still hands off to the existing prompt form
unchanged; a template with none captures immediately. Not aliasable
via =org-xx-menu-aliases= the way Export/Clocking's own items are —
templates already have their own real name (each one's own
description), so a second naming layer would be redundant. God-mode's
own capture shortcut and the Extras menu's own direct-to-template
entries are both untouched, reaching the exact same underlying system
they always did.

* v299 — Menu aliases: a fifth "clocking" namespace
Setting an icon for a Clocking sub-item (Clock-in, Clock-out, and so
on) via =org-xx-menu-aliases= had no effect, however it was written.
Root cause was two-fold: the parser only ever recognized four
namespaces, and the Clocking items themselves were never wired to
consult any alias map at all. Fixed the same way Export's own
sub-items already work — they get their own dedicated =export:=
namespace rather than being nested under =more:=, since a sub-flow's
own items aren't part of the parent menu's own top-level labels.
Clocking now works the identical way: =clocking:Clock-in;▶️= and
similar now apply correctly. Also confirmed directly: the nested
=more:clocking:Clock-in= form doesn't error, it silently lands in the
wrong namespace as an inert, never-consulted entry — worth knowing if
you tried that form and it also seemed to do nothing.

* v297 — Menu restructuring: Add heading, History, Help, Clocks, TODO
Several related moves. The ➕ Add heading button is a real, visible,
centered toolbar button again — it had been deliberately hidden all
along, only reachable through the More menu's own proxy click, a past
decision now reversed. History and Help moved from the More menu to
the View menu. The heading action menu's own Clock button is gone,
replaced by a "Clocks" entry in the More menu — one popup with every
clock action as plain text (Clock-cancel, Clock-continue, Clock-in,
Clock-out), reached from a menu rather than any specific heading.
TODO took over the action menu's newly-freed slot, restoring its
pre-general-editor behavior exactly — a simple toggle for the common
case, a full state picker only for a file with more than one parallel
workflow — and was removed from the general editor entirely. All of
it already configurable via the existing =org-xx-menu-aliases=
system, unchanged.

* v296 — All clock actions in one place
Replaced the heading action menu's own clock-in/clock-out toggle (and
its separate three-choice stop prompt) with a single ⏱️ Clock button
opening one popup listing all four actions together — ▶️ clock-in,
⏹ clock-out, ❌ clock-cancel, ⏭️ clock-continue — so clock-cancel and
clock-continue, previously buried or Extras-menu-only, are just as
discoverable as clock-in already was. Clock-out and clock-cancel
operate on whichever clock is actually running anywhere, not
necessarily the specific heading whose popup was open to reach them —
matching real org's own actual clock semantics.

* v295 — Fixed: opening a second document could silently blank Agenda's own file list
Reported precisely: a file with =org-agenda-files= set via Local
Variables correctly showed birthdays, holidays, and weather in
Agenda — until a *second*, unrelated document (one with no
=org-agenda-files= of its own) was also opened, after which Agenda
showed nothing at all, even switching back to the first file. The
underlying config value was a single, shared variable that never got
recomputed on switching tabs, so it stayed stuck on whichever
document was opened last. Also explains a separately-reported
symptom: the "Refresh agenda files" button, which only shows when
there's something configured to refresh, was silently disappearing
for the same reason — not removed, just correctly hidden by a value
that had gone wrong.

* v294 — Two tab-lifecycle safety improvements
Switching into a tab backed by a real file now also checks whether it
changed elsewhere since last seen — the same proactive check that
already ran on open and on the browser tab regaining focus, now also
catching the moment you're about to start looking at or editing it.
Separately: closing a tab with unsaved changes now confirms first,
matching real Emacs's own ~kill-buffer~ behavior — saying no leaves it
open exactly as it was, so it can be saved properly instead. A clean
tab still closes immediately, no confirmation needed.

* v293 — org-clock-continue, and a documentation correction
Added ~org-clock-continue~ as a new Extras-menu action: resumes
clocking on whichever heading was most recently clocked, anywhere in
the document, without navigating back to find it first — a status
message covers both "a clock's already running" and "nothing's ever
been clocked" instead of doing nothing silently. Separately: corrected
the README, which incorrectly claimed there's no persistent modeline
clock display — there already was one, confirmed by directly running
it (a running clock shows its own elapsed time and heading title in
the modeline, refreshed every 30 seconds); the code was already right,
only the documentation was stale.

* v292 — New documents are named "*scratch*", matching real Emacs
A fresh, unsaved document with no heading yet now shows *scratch* in
both the tab bar and modeline, instead of the generic "Untitled" —
real Emacs's own name for a fresh buffer. The moment the first heading
gets a title, that takes over as the label, same as before. Sharing
one label function between the modeline and tab bar also surfaced and
fixed a separate bug: the modeline was previously showing a new
document's own raw internal ID directly, never meant to be seen.

* Undated (shipped before v290, entry added retroactively) — Capture: table-line captures no longer render bold
A ~table-line~ capture creating a brand-new table (no existing table
under the target heading yet) reused a helper meant for "insert a new
table with a header row" — meaning the captured row ended up shaped
exactly like a header with zero data rows underneath it, which is why
it rendered bold. Fixed by giving that helper an explicit opt-out for
capture's own case, where the row is plain data (a log/tracking
entry), never a header. This entry exists because the fix itself
predates this changelog file catching up to it — the code and its own
tests have already been in every shipped build since it was made; only
the changelog documentation was missing.

* v291 — Fixed: typed text silently lost when tapping a different heading mid-edit
Reproduced live, following a precise reported repro: type a new
sub-heading's title, tap a *different* heading before the first one
committed, and the typed text vanished — replaced by an empty
"Heading title" field, no error, nothing recoverable. Confirmed this
happens on desktop too, not just mobile. Root cause: tapping a
heading's title uses ~mousedown~, which browsers fire before ~blur~ —
and opening the tapped heading's own action menu re-renders
immediately, which destroys the still-being-typed-into field before
its own blur ever gets a chance to save what was in it. Fixed by
committing any other in-progress edit first, whenever a heading title
or table cell is tapped. Also fixed a second, related crash this
exposed (committing a field this way can trigger its own blur a
second time) and removed leftover debug logging found while auditing
for the same issue elsewhere.

* v290 — Table formulas: bare-reference date subtraction now works
Reported against real org-mode's own documented spreadsheet behavior:
Calc auto-recognizes org timestamps during ordinary cell evaluation,
so subtracting two timestamp cells directly (~$3=$1-$2~) should just
work, no wrapper function required. It didn't — a bare cell reference
fell straight through to plain numeric parsing, which can only ever
be NaN for something like "<2026-12-25 Fri>", and this app's own
~date()~ function (invented here, not something real org-mode
requires) was the only way to get correct results. Fixed at the
single shared function behind every cell reference, so it applies
consistently to plain references and to aggregate functions across a
range alike. ~date()~ itself still has real, distinct value — an
explicit error for a cell that isn't timestamp-shaped at all, and its
three-argument form for building a date from separate Y/M/D cells —
and is unchanged.

* v289 — Corrected the previous release's own menu-width fix
The v287 fix for menu-item text wrapping used a minimum width, which
meant every popup menu was always at least 75% of the screen wide,
even a short two-item menu that never needed that much room. Replaced
with genuine content-based sizing: a menu now grows to fit its own
widest row, capped at that same 75%-of-screen limit only for content
that actually needs it. Also found a second, separate width cap
hiding in the code that positions menus near their trigger button,
quietly overriding the CSS one with its own, different, hardcoded
value — now unified to compute the same limit.

* v288 — Three small UI corrections
The tab bar now always shows, even with just one document open,
instead of only appearing once a second tab exists — so the UI's own
shape stays consistent regardless of how many tabs happen to be open.
Closing the only remaining tab now creates a fresh, empty buffer
immediately rather than dropping to a "nothing open" state. Also fixed
a real regression from the previous release: removing the old
filename display took its implicit spacer role with it, collapsing
the top toolbar's own File/Save/View/More buttons onto the left edge
instead of keeping File/Save left and View/More right.

* v287 — Toolbar cleanup and menu-width fix
Removed the top-line filename display — redundant once the tab bar and
modeline already show the same thing, genuinely overkill across three
places. Fully removed, not just hidden, including the now-dead
~org-xx-hide-filename-in-menu~ setting it existed to control. Added a
💾 Save button next to the File menu for a one-tap shortcut to the
single most common action. Fixed Export (and every other dropdown
menu — File, View, More) wrapping menu-item text like "Choose a
heading" instead of growing to fit it: the shared menu class had no
explicit width at all, so it shrink-wrapped to content by default.
Now sized to at least 75% of a narrow screen's own width, capped at a
reasonable size on desktop.

* v286 — Fixed: switching tabs lost your scroll position and cursor
Reported as "switching tabs is like opening a file newly." Three
separate, compounding bugs. Scroll restoration ran before the
re-render that immediately wiped it out, and was targeting the wrong
element on mobile in the first place (the actual scroll container
below the desktop breakpoint is ~#contentArea~, not the outline
itself). Separately, a click listener from an earlier session's fix
was firing on every click anywhere in the app — including the File
menu and tab bar — which meant switching documents cleared keyboard
focus before the tab being left even got a chance to save it. Fold
state needed no fix; it lives directly on each heading and was already
being preserved correctly. Also: the active tab now scrolls into view
whenever the tab bar renders, so it's never hidden off-screen.

* v285 — Standardized touch-target sizing across every list row
Prompted by Export and Refile's own heading pickers being reported too
small on mobile — a full audit turned up two separate problems.
Refile's own heading list and Export's "Choose a heading" list were
both using a CSS class meant for horizontal button groups as a bare
clickable row, with zero padding and no minimum height at all — a
genuine bug. History, Agenda, the TODO view, and the file browser each
had their own small, inconsistent padding with no shared floor, unlike
the Extras menu and Search, which already guaranteed a real 44px
minimum. Every one of these now shares that same consistent sizing.
Also restructured Export's ASCII/Markdown/HTML/ODT picker (previously
three small buttons crammed into a wrapping row) to match Calendar
export's own better, full-width stacked layout.

* v284 — Fixed: delete confirmations visually recommended the wrong button
The keyboard-focus mechanism from the earlier "Cancel is the default"
fix (Cancel focused, Enter cancels) was correct, but provided zero
benefit on this app's primary interface — a touch device has no
visible focus indicator at all. Visually, both buttons looked like the
same weight of plain button except the destructive one was colored
red, which draws the eye and reads as "the one to tap." Cancel is now
the filled, high-contrast button — the one that visually reads as the
recommended choice on sight — while the destructive option is plain
and unfilled, red text only: still clearly marked as dangerous, never
visually competing with Cancel for attention.

* v283 — Multiple documents, tab-bar style
The largest architectural change this app has taken on. Rather than
threading a "which document" parameter through the thousands of
read/write sites already spread across this 13,500+ line file, used a
session-swapping model instead — closer to how Emacs itself handles
buffer-local state internally. Every existing global (~state~,
~editingCell~, ~history~, and ~20 others) keeps its exact name, and
every existing call site throughout the file stays completely
untouched; only tab-switching itself needed to learn about sessions
at all. New tab bar, hidden until a second tab is actually open.
Opening a document — New, Open, a ~file:~/~github:~/~webdav:~ link,
an Agenda or Search result — now opens into its own tab, or switches
to it if it's already open, uniformly, since they all share the same
underlying open-a-document logic. Each tab keeps its own content,
editing state, cursor, scroll position, and undo history, completely
independently. The full set of open tabs — not just the single most
recent document — now persists and restores across closing and
reopening the app entirely. Found and fixed two real bugs during
testing: leftover "confirm discard" logic from the old single-document
model was silently blocking every second new tab behind an unanswered
dialog, and every unsaved draft sharing one fixed internal id broke
persistence itself — multiple unsaved tabs collided in the same cache
entry, so only the last-saved one actually survived a reload.

* v282 — Table-highlight bug, fully resolved
The other half of v281's fix: dismissing the highlight by tapping
something that isn't a table cell — most commonly, a different
heading — now also takes effect on the first tap. A new document-level
mousedown handler commits a pending cell edit before whatever was
actually tapped gets its own chance to react, closing the same DOM-
replaced-mid-gesture race the cell-to-cell fix closed. That alone
wasn't quite enough, though — the heading title's own action (opening
its action menu) still used ~click~, which can't reliably resolve its
own target once a capture-phase handler has already rebuilt the DOM
out from under it. Converting the heading title to ~mousedown~ too,
the same approach already used for table cells, was what actually
closed the gap. Verified live with real taps: tapping a different
heading mid-edit now correctly commits the cell, opens that heading's
own action menu, and moves the highlight there in one tap.

* v281 — The actual root cause of "table cell switching needs two taps"
Found after several earlier attempts across sessions misdiagnosed this
as a DOM-replacement timing race. The real cause: committing a table
cell's edit fully re-parses the heading's whole body, producing a
brand-new table object each time — so a cell-switching handler that
committed the OLD cell then reused the already-captured table
reference for the NEW cell was working with something already stale
the instant both cells shared a heading. The render pass afterward
could never match it against the freshly-reparsed table, which is why
the cell never actually showed as editing despite its row/column
being tracked correctly the whole time. Fixed by re-finding the table
fresh by its own line position after any commit — the same pattern
already used elsewhere for exactly this kind of reference. Verified
live with real taps across multiple consecutive cell switches, each
correctly focusing and preserving data on the first tap. Dismissing
the highlight by tapping something other than a table cell — a
heading, say — still needs a second tap; extending this fix there too
is a separate, larger piece of work.

* v280 — Undo/redo history persists across reopening a file
New =src/history-store.js= module, same per-document key pattern
=outbox.js= already uses (its own docstring anticipated exactly this).
Capped at 200 steps once persisted — a full-text snapshot per step
makes unbounded storage a real, ongoing cost for a file kept in
long-term regular use, unlike the old in-memory-only history, which a
session's own natural end (closing the tab) already bounded. Restored
history requires its own latest snapshot to exactly match what's
actually on screen on reopen; if the file changed elsewhere since
(another device, GitHub's own web UI, WebDAV directly), the old
history no longer corresponds to reality and is discarded rather than
offering undo into disconnected content. Also investigated (per
direct request) whether per-keystroke undo granularity would be worth
building instead of the current one-step-per-completed-edit — recommending
against it: the browser's own native field-level undo already covers
the in-field case for free, before a field is even blurred, and real
Emacs's own undo batches consecutive typing the same way this app's
current granularity already does.

* v279 — Delete confirmations default to Cancel, not OK
Every delete/discard confirmation (heading, table, note, list item,
row/column, attachment, recent files, discarding an unsaved document,
reloading over local changes, exporting credentials in plain text) now
uses a custom dialog instead of the browser's own native ~confirm()~,
specifically so *Cancel* — not the destructive option — is the default:
focused when the dialog opens, activated by a stray Enter press,
Escape, or tapping the dark backdrop instead of a button. Native
~confirm()~'s own default button was never something JS could control
at all, which is why this needed a real replacement rather than a
setting. Two dialogs (resolving a stale local edit, resolving a sync
conflict) are deliberately still native for now — both offer a genuine
choice between two valid outcomes rather than "destroy vs. do
nothing," and need their own careful design rather than a mechanical
swap.

* v278 — CRITICAL: the ACTUAL Android/ChromeOS data-loss regression
v277 fixed a real but, it turned out, unreachable code path (the
top-toolbar *+*, permanently hidden and never actually used). The
person's own correction — the button in question was the header
action-menu's own *Add sub-heading* (+) — led to the real cause: a
document-level click listener from an earlier session's "table
highlight" fix fires on every click, including action-menu button
taps. Opening a heading's action menu already sets its own keyboard-
focus state; tapping *Add sub-heading* right after — which itself
already starts a new edit session and renders once, correctly — would
then ALSO trigger this listener's own render() on that same click,
tearing down the just-created title field right as the platform's own
virtual keyboard/IME was establishing focus on it. Confirmed
definitively by reverting only this one guard and reproducing the
exact reported symptoms: field present but not actually focused, typed
text landing nowhere, the new heading silently discarded on Enter.

* v277 — CRITICAL: data loss on Android/ChromeOS adding a new heading
The top-toolbar *+* (New Heading) button called ~render()~ twice in
quick succession — the second call, already happening on its own
inside ~startEditingTitle()~ right after, made the first one purely
redundant, but its real effect was tearing down and rebuilding the
brand-new title field right as the platform's own virtual
keyboard/IME was establishing focus and composition on it. On
Android/ChromeOS specifically this meant the new field never actually
received focus, and text typed after manually tapping into it anyway
could be lost entirely on Enter. No other "add heading" path had this
extra call — isolated and fixed.

* v276 — Search and replace, Emacs-style
New *Replace* button next to Regex starts a real ~query-replace~/
~query-replace-regexp~ walk over the current document, using the same
minibuffer prompt vocabulary real Emacs uses: ~y~/Space replaces,
~n~/Delete skips, ~q~/Return stops, ~.~ replaces once then stops, ~!~
replaces everything remaining with no further asking. New
=src/query-replace.js= engine, restricted to text that can be safely
written back — heading titles, paragraphs, list items, table cells —
deliberately excluding tags, TODO state, priority, properties,
timestamps, and block content, since blind substitution into any of
those risks corrupting the document's own syntax rather than just its
content. Found and fixed two real bugs while building this: replacements
were initially silent no-ops (a variable mix-up), and multiple matches
within the same paragraph/cell weren't all being found, since a stale
node reference lingered past the point where the underlying edit
functions re-parse that heading's own body.

* v275 — Search's regex mode now uses real Emacs regex syntax
New =src/emacs-regex.js= module, written from scratch, converts Emacs's
own regex dialect to native JS RegExp. The single biggest practical
difference from raw JS regex: an unescaped ~( ) { } |~ is literal text
in Emacs syntax, not a special character — grouping needs ~\( \)~,
alternation needs ~\|~, interval counts need ~\{n,m\}~ — which is
exactly what makes an ordinary phrase containing parentheses "just
work" without escaping. Also supports backreferences, word/symbol
boundaries, POSIX character classes, and whole-string anchors distinct
from line-anchored ~^~/~$~; throws a specific, named error for the
handful of constructs that depend on a live buffer's own syntax table
and have no real equivalent here, rather than silently miscompiling
them. Wired into Search's existing regex-mode toggle. Search-and-replace
with an Emacs-style minibuffer prompt remains a separate, larger piece
not yet built.

* v274 — The actual table-highlight bug, found from a screenshot
Tapping a table cell sets keyboard focus to three things together: the
cell's own outline, the table row, and — separately — the table's own
containing heading. Tapping a completely different heading's title,
though, only ever toggled its action menu; it never touched that third
piece at all, so it stayed silently pointed at the table's heading,
masked until something later cleared the table-row state — at which
point that stale, wrong heading became visible as a highlight nobody
had actually asked for. Fixed at the source: a heading tap now
correctly claims keyboard focus for itself, the same way every other
tappable row already does, and clicking genuinely empty space now
clears the heading-level state too, not just the table-cell piece.
Re-confirmed Shift+arrow table navigation is still intact — the exact
thing an earlier attempt at this same underlying bug broke.

* v273 — Reverted a table-highlight change that broke Shift+arrow
The previous session's table-highlight fix (v272) cleared a cell's
keyboard-focus tracking the instant editing ended, chasing down a
"stays highlighted" complaint — but that's the exact moment Shift+arrow
table navigation needs that same state to already be intact, since a
browser can only deliver a keypress to one focused thing at a time (the
cell's own textarea, while it's focused, or a table-navigation handler,
once it isn't — never both). Nulling it out right as the textarea blurs

normally used, breaking desktop keyboard navigation entirely. Reverted

continued Shift+arrow use — while confirming what was actually correct
